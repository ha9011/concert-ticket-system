# Set 면접질문 — 단답형/이론형 33선

> 시나리오가 "사고력 면접" 대비라면, 이건 **"빠르게 답하는 단답형/이론형 면접" 대비**.
> 각 답은 30초~1분 내 말할 수 있는 분량.
>
> **사용법**: 질문만 먼저 보고 머릿속으로 답해본 뒤 ✅ 모범답안과 비교.
> 종이로 가리거나, 친구한테 질문만 읽어달라 부탁해도 좋음.
>
> 이 프로젝트에 적용하면:
> - **찜한 아티스트**: `favorite:user:{id}` — 사용자가 찜한 아티스트 집합
> - **아티스트 팬 목록**: `fans:artist:{id}` — 새 공연 알림 대상 집합
> - **태그 검색**: `concerts:tag:{name}` — 태그별 공연 집합
> - **공통 관심사**: `SINTER favorite:user:A favorite:user:B`
> - 단, 찜/권한/응모처럼 영구 의미가 있는 데이터는 **DB가 원본, Redis Set은 보조 인덱스**다.

## A. 기본 구조

### Q1. Redis Set을 한 문장으로 정의하라.

✅ **답**:

> **순서 없고 중복 없는 멤버들의 모음**. 멤버십 검사(`SISMEMBER`)가 빠르고, 교집합·합집합·차집합 같은 집합 연산을 명령 하나로 처리할 수 있다.

> 💡 꼬리질문 대비: "순서가 필요하면?" → List 또는 Sorted Set. "중복 없이 정렬까지 필요하면?" → Sorted Set.

---

### Q2. List와 Set의 핵심 차이 3가지는?

✅ **답**:

| 비교 | List | Set |
|---|---|---|
| 중복 | 허용 | 불가 |
| 순서 | 있음 | 없음 |
| 멤버십 검사 | `LPOS` O(N) | `SISMEMBER` O(1) |

→ **순서가 중요하면 List**, **있다/없다와 중복 제거가 중요하면 Set**, **정렬/랭킹이 필요하면 ZSet**.

---

### Q3. `SADD`의 반환값은 무엇인가? 왜 중요한가?

✅ **답**:

> **새로 추가된 멤버 수**를 반환한다. 이미 있던 멤버는 제외된다.

```redis
SADD favorite:user:1 artist:10  # 처음이면 1
SADD favorite:user:1 artist:10  # 이미 있으면 0
```

이 반환값으로 **중복 방지 + 이미 했는지 판단**을 동시에 할 수 있다. 좋아요, 찜, 투표 1회 제한의 핵심이다.

> 💡 단, 찜/응모처럼 영구 기록이 필요한 기능은 Redis 반환값만 믿지 말고 DB `UNIQUE` 제약을 최종 방어로 둔다.

---

### Q4. Set의 멤버가 모두 제거되면 키는 어떻게 되나?

✅ **답**:

> **키 자체가 자동 삭제**된다. Redis는 빈 컬렉션을 남기지 않는다. List/Set/Hash/ZSet 공통이다.

영향:
- 마지막 멤버를 `SREM` 또는 `SPOP`하면 `EXISTS key`는 0
- `SCARD key`도 0
- `TYPE key`는 `none`

> 💡 "찜을 다 취소한 사용자"는 `favorite:user:{id}` 키가 없는 것처럼 보인다. 이걸 데이터 손실로 오해하면 안 된다.

---

### Q5. `SCARD`의 시간복잡도는?

✅ **답**:

> **O(1)**. 멤버를 하나씩 세는 게 아니라 Redis가 들고 있는 메타데이터에서 바로 반환한다.

좋아요 수, 찜 수, 태그별 공연 수처럼 **정확한 개수만** 필요한 경우에 적합하다.

---

## B. 명령어 비교

### Q6. `SPOP`과 `SRANDMEMBER`의 차이는?

✅ **답**:

| 명령 | 동작 | 대표 용도 |
|---|---|---|
| `SPOP key [count]` | 랜덤 멤버를 반환하고 **제거** | 중복 없는 당첨자 확정 |
| `SRANDMEMBER key [count]` | 랜덤 멤버를 반환만 하고 **유지** | 후보 미리보기, 샘플링 |

→ **뽑힌 사람이 다시 뽑히면 안 되면 `SPOP`**, 풀을 유지해야 하면 `SRANDMEMBER`.

---

### Q7. `SRANDMEMBER key 5`와 `SRANDMEMBER key -5`의 차이는?

✅ **답**:

- `SRANDMEMBER key 5`: 중복 없이 **최대 5개** 반환. 집합이 3개면 3개만 반환.
- `SRANDMEMBER key -5`: 중복을 허용해서 **정확히 5개** 반환. 같은 멤버가 여러 번 나올 수 있다.

> 💡 count 부호가 함정이다. 양수는 "중복 없는 샘플", 음수는 "중복 허용 샘플".

---

### Q8. "이 값이 집합에 있나?"를 자주 검사한다. List와 Set 중 무엇을 쓰나?

✅ **답**:

> **Set**. `SISMEMBER`는 O(1), List의 `LPOS`는 O(N)이다.

차단 목록, 권한 목록, 이미 본 항목, 찜 여부, 응모 여부처럼 **순서는 필요 없고 있다/없다만 자주 묻는 데이터**는 Set이 표준이다.

---

### Q9. 여러 멤버의 존재 여부를 한 번에 검사하는 명령은?

✅ **답**:

> **`SMISMEMBER key member [member ...]`**. Redis 6.2+ 명령이다.

각 멤버에 대해 1/0 배열을 반환한다. 여러 번 `SISMEMBER`를 호출하는 것보다 네트워크 왕복을 줄일 수 있다.

```redis
SMISMEMBER blocked:users user:1 user:2 user:3
# => [1, 0, 1]
```

---

### Q10. 멤버를 한 집합에서 다른 집합으로 원자적으로 옮기는 명령은?

✅ **답**:

> **`SMOVE source destination member`**.

source에 멤버가 있으면 destination으로 이동하고 1을 반환한다. 없으면 0을 반환한다. 제거와 추가가 한 명령으로 처리되므로 중간 상태가 없다.

---

## C. 집합 연산

### Q11. `SINTER`, `SUNION`, `SDIFF`는 각각 무엇인가?

✅ **답**:

| 명령 | 의미 | 예 |
|---|---|---|
| `SINTER` | 교집합 | A와 B 모두에 있는 것 |
| `SUNION` | 합집합 | A 또는 B 어디든 있는 것 |
| `SDIFF` | 차집합 | 첫 번째 집합에는 있고 나머지에는 없는 것 |

태그 AND 검색은 `SINTER`, OR 검색은 `SUNION`, 제외 조건은 `SDIFF`로 표현할 수 있다.

---

### Q12. `SDIFF a b`와 `SDIFF b a`는 같은가?

✅ **답**:

> **다르다.** `SDIFF`는 **첫 번째 키 기준**이다.

```redis
SDIFF a b  # a에는 있고 b에는 없는 것
SDIFF b a  # b에는 있고 a에는 없는 것
```

차집합은 인자 순서가 결과를 바꾼다. 추천 후보를 만들 때 특히 중요하다.

---

### Q13. 교집합 결과를 새 키에 저장하려면?

✅ **답**:

> **`SINTERSTORE dest key [key ...]`**. 결과 집합을 `dest`에 저장하고, 반환값은 저장된 멤버 수다.

자주 쓰는 태그 조합이나 추천 후보를 캐싱할 때 쓴다. 단, 원본 태그/찜이 바뀌면 캐시 무효화나 짧은 TTL이 필요하다.

---

### Q14. 교집합의 "개수만" 필요할 때 효율적인 명령은?

✅ **답**:

> **`SINTERCARD numkeys key [key ...] [LIMIT n]`**. Redis 7.0+ 명령이다.

멤버 전체를 반환하지 않고 교집합 크기만 계산한다. `LIMIT`을 주면 일정 개수까지만 세고 멈출 수 있어 "공통 친구가 3명 이상인가?" 같은 판정에 유리하다.

---

### Q15. 없는 키와 `SINTER`/`SUNION`을 하면?

✅ **답**:

> Redis는 없는 Set 키를 **빈 집합**처럼 취급한다.

- `SINTER a missing` → 빈 집합
- `SUNION a missing` → `a`의 멤버들
- `SDIFF a missing` → `a`의 멤버들

---

### Q16. "(록 OR 재즈) AND 내한" 같은 복합 태그 필터는 어떻게 구현하나?

✅ **답**:

단계적으로 집합 연산을 조합한다.

```redis
SUNIONSTORE tmp:rock-jazz concerts:tag:rock concerts:tag:jazz
SINTER tmp:rock-jazz concerts:tag:overseas
EXPIRE tmp:rock-jazz 60
```

자주 쓰는 조합은 `STORE + TTL`로 캐싱한다. 태그 집합이 커지고 조건이 복잡해지면 검색 엔진으로 넘어갈 신호다.

---

### Q17. 큰 집합끼리 `SINTER`를 하면 무엇이 위험한가?

✅ **답**:

> 멤버 수에 비례해 비용이 커지고, Redis 단일 스레드를 오래 점유할 수 있다. 그동안 다른 명령도 밀린다.

대응:
1. 개수만 필요하면 `SINTERCARD`
2. 결과 재사용이면 `SINTERSTORE + TTL`
3. 후보를 먼저 줄인 뒤 계산
4. hot path에서 빼고 배치/비실시간으로 계산
5. 너무 크면 Redis 밖 검색/추천 시스템으로 이동

## D. 인코딩

### Q18. Set의 내부 인코딩 종류는?

✅ **답**:

대표적으로 다음 세 가지를 알아두면 된다.

| 인코딩 | 조건 | 특징 |
|---|---|---|
| `intset` | 멤버가 전부 정수이고 작음 | 정렬된 정수 배열, 메모리 효율 좋음 |
| `listpack` | 작은 문자열 Set | 작은 값 압축 저장 |
| `hashtable` | 커지거나 조건 초과 | O(1) 멤버십 검사에 적합 |

> 💡 Redis 버전과 설정에 따라 세부 인코딩/임계값은 달라질 수 있다. 핵심은 "작을 땐 압축, 커지면 hashtable"이다.

---

### Q19. intset에 문자열을 추가하면?

✅ **답**:

> 정수 전용 인코딩을 유지할 수 없으므로 다른 인코딩으로 전환된다.

예를 들어 정수만 있던 Set에 `"user:1"` 같은 문자열을 넣으면 intset으로 저장할 수 없다. 한 번 전환되면 보통 다시 intset으로 돌아가지 않는다.

---

### Q20. intset/listpack에서 hashtable로 전환되는 기준은?

✅ **답**:

> 멤버 수나 멤버 길이가 설정 임계값을 넘으면 hashtable로 전환된다.

관련 설정 예:
- `set-max-intset-entries`
- `set-max-listpack-entries`
- `set-max-listpack-value`

임계값 자체를 외우기보다, **작은 Set은 메모리 효율 인코딩, 커진 Set은 hashtable**이라는 방향을 이해하면 된다.

---

### Q21. intset이 메모리에 유리한 이유는?

✅ **답**:

> 해시 테이블처럼 버킷과 포인터를 많이 들고 있지 않고, 정수들을 정렬된 배열 형태로 연속 저장하기 때문이다.

작은 정수 ID 집합에는 메모리 효율이 좋다. 대신 문자열이 섞이거나 규모가 커지면 hashtable 계열로 전환된다.

## E. 유니크 카운트 비교 (Set vs Bitmap vs HyperLogLog)

### Q22. 정확한 유니크 카운트와 멤버 목록이 모두 필요하면?

✅ **답**:

> **Set**. `SADD`로 중복 없이 넣고, `SCARD`로 정확한 개수를 세며, `SISMEMBER`/`SMEMBERS`로 멤버를 확인할 수 있다.

단점은 멤버 수만큼 메모리가 증가한다는 것이다.

---

### Q23. Set과 HyperLogLog의 차이는?

✅ **답**:

| | Set | HyperLogLog |
|---|---|---|
| 정확도 | 정확 | 근사 |
| 오차 | 없음 | 약 0.81% 표준 오차 |
| 메모리 | 멤버 수 비례 | 최대 약 12KB |
| 멤버 조회 | 가능 | 불가 |

→ **누가 왔는지 알아야 하면 Set**, **대략 몇 명인지만 필요하면 HyperLogLog**.

---

### Q24. 사용자 ID가 촘촘한 정수이고 출석/접속을 초압축으로 세려면?

✅ **답**:

> **Bitmap**. `SETBIT active:{date} {userId} 1`로 표시하고, `BITCOUNT`로 개수를 센다.

```redis
SETBIT active:2026-06-24 42 1
BITCOUNT active:2026-06-24
```

단, ID가 너무 듬성듬성 크면 높은 offset 때문에 메모리가 커질 수 있다. **촘촘하고 상한이 예측 가능한 정수 ID**일 때 적합하다.

---

### Q25. HyperLogLog로 "주간 유니크"를 구하려면?

✅ **답**:

> 일별 HLL을 `PFMERGE`로 합친 뒤 `PFCOUNT` 한다.

```redis
PFMERGE visitors:week:2026w26 visitors:2026-06-22 visitors:2026-06-23 ...
PFCOUNT visitors:week:2026w26
```

단, HyperLogLog는 합집합 근사에는 좋지만 **교집합을 정확히 구할 수 없다**.

---

## F. 운영 함정

### Q26. 큰 Set 전체 조회 시 `SMEMBERS`를 쓰면 왜 위험한가?

✅ **답**:

> `SMEMBERS`는 O(N)이고, 전체 멤버를 한 번에 직렬화해서 반환한다. 큰 Set에서는 Redis 단일 스레드를 오래 점유하고 네트워크 응답도 커진다.

대안:
- 전체 목록이 정말 필요한지 먼저 확인
- 개수만 필요하면 `SCARD`
- 일부만 필요하면 `SRANDMEMBER`
- 순회가 필요하면 `SSCAN`

---

### Q27. big key Set을 삭제할 때 주의할 점은?

✅ **답**:

> 큰 Set을 `DEL`로 지우면 메모리 회수가 동기적으로 일어나 Redis가 멈칫할 수 있다.

운영에서는 큰 키 삭제에 **`UNLINK`**를 우선 고려한다. `UNLINK`는 키 연결을 끊고 실제 메모리 회수를 백그라운드로 넘긴다.

탐지:
```redis
MEMORY USAGE key
redis-cli --bigkeys
```

---

### Q28. `EXISTS`로 "사용자가 찜 목록을 가졌나" 판단하면 생기는 문제는?

✅ **답**:

> 사용자가 찜을 다 취소하면 Set이 비고, Redis는 빈 Set 키를 자동 삭제한다. 그러면 `EXISTS favorite:user:{id}`는 0이 된다.

이걸 "사용자 데이터가 손실됐다"로 오해하면 안 된다. **현재 찜 목록이 비어 있다**와 **과거에 찜 기능을 사용한 적이 없다**는 다른 의미다. 과거 이력은 DB로 판단해야 한다.

---

### Q29. Set 멤버마다 개별 TTL을 걸 수 있나?

✅ **답**:

> **불가능하다.** Redis TTL은 키 단위다. Set 안의 특정 멤버만 자동 만료시킬 수 없다.

대안:
- 기간제 차단: ZSet score에 만료시각 저장
- 멤버별 TTL이 중요: `blocked:user:{id}`처럼 별도 키로 분리
- 주기적 정리 작업으로 만료된 멤버 제거

---

### Q30. String 키에 `SADD`를 하면?

✅ **답**:

> **`WRONGTYPE Operation against a key holding the wrong kind of value`** 에러가 난다.

Redis는 키마다 타입이 고정된다. 같은 키를 String으로 쓰다가 Set 명령을 실행할 수 없다.

예방:
- 키 네이밍 컨벤션 유지
- `TYPE key`로 디버깅
- 도메인별 prefix 분리: `user:name:{id}` vs `favorite:user:{id}`

---

## G. 실전 응용

### Q31. "두 사용자의 공통 관심사"와 "추천"을 Set으로 어떻게 구현하나?

✅ **답**:

공통 관심사:
```redis
SINTER favorite:user:A favorite:user:B
```

추천 후보:
```redis
SDIFF favorite:user:B favorite:user:A
```

의미는 "B는 찜했지만 A는 아직 찜하지 않은 것"이다. 단, 대규모 추천에서는 모든 사용자와 실시간 `SINTER`를 하면 안 되고, 후보를 줄이거나 배치로 미리 계산한다.

---

### Q32. 중복 없는 당첨자 N명을 안전하게 뽑으려면?

✅ **답**:

> **`SPOP raffle N`** 한 번으로 뽑는다. `SPOP`은 반환과 제거가 한 명령이라, 같은 멤버가 다시 뽑히는 레이스를 막을 수 있다.

주의:
- `SRANDMEMBER` 후 `SREM`을 따로 하면 원자성이 깨진다.
- 감사가 필요한 이벤트는 후보 스냅샷, seed/난수 방식, 실행자, 결과를 DB에 남긴다.
- Redis 공식 문서 기준으로 `SPOP`은 완전한 균등 분포가 필요한 추첨에는 부적합하다.
- 가중 추첨은 Set이 아니라 ZSet 등 별도 설계가 필요하다.

---

### Q33. "아티스트 새 공연 알림"에서 Set과 List의 역할 분담은?

✅ **답**:

| 자료구조 | 역할 |
|---|---|
| Set | 누가 대상인가: `fans:artist:{id}` |
| List | 각자에게 시간순 전달: `feed:user:{id}` |

즉 **대상 선정은 Set, 전달은 List**다.

주의:
- 팬이 많으면 `SMEMBERS` 대신 `SSCAN`
- 쓰기는 batch/pipeline으로 묶기
- 셀럽은 fan-out-on-read 하이브리드 고려
- 알림 원본/발송 이력은 DB에 남겨야 재생성·감사가 가능

## 🎯 면접 직전 30초 체크리스트

암기보단 흐름으로:

1. **Set은 뭐에 좋은가** → 순서 없음, 중복 없음, 멤버십 O(1), 집합 연산
2. **List와 차이** → List=순서/중복, Set=중복 제거/있다없다
3. **SADD 반환값** → 신규 추가 수. 찜/좋아요/투표 1회 제한
4. **SISMEMBER/SMISMEMBER** → 단건/다건 멤버십 검사
5. **SPOP vs SRANDMEMBER** → 제거 vs 유지, count 양수/음수 함정
6. **집합 연산** → `SINTER` 공통, `SUNION` OR, `SDIFF` 추천/제외
7. **SINTERCARD** → 개수만 필요할 때, 큰 결과 반환 회피
8. **인코딩** → 작으면 intset/listpack, 커지면 hashtable
9. **유니크 카운트 선택** → 목록 필요=Set, 촘촘한 정수ID=Bitmap, 대략 수=HLL
10. **큰 Set 운영** → `SMEMBERS` 금지, `SSCAN`, big key 삭제는 `UNLINK`
11. **빈 Set** → 마지막 멤버 제거 시 키 소멸
12. **DB와 관계** → 찜/권한/응모는 DB가 원본, Redis Set은 효율·실시간 뷰

## 자주 나오는 후속 질문 패턴

면접관이 추가로 파고드는 단골 흐름:

```text
Q. 찜하기를 Redis Set으로만 관리해도 되나요?
→ 영구 데이터라 DB가 원본. DB UNIQUE로 최종 중복 방어, Redis는 빠른 조회/알림 대상 인덱스
Q. 그럼 쓰기 순서는?
→ 보통 DB 저장 성공 후 Redis SADD. Redis 실패는 재시도/재생성 가능
Q. Redis를 먼저 쓰는 경우는?
→ 중복 클릭 선검사로는 가능. 단 DB 실패 시 SREM 롤백이나 reconcile 필요
```

```text
Q. 공통 관심사 추천을 SINTER로 만들면 되나요?
→ 소규모는 가능
Q. 사용자가 수백만이면?
→ 모든 쌍 SINTER 금지. 후보 좁히기, SINTERCARD, 캐싱, 배치/ML 추천으로 이동
Q. Redis Cluster에서는?
→ multi-key 연산은 같은 hash slot 설계가 필요
```

```text
Q. 이벤트 당첨자는 SPOP이면 공정한가요?
→ 중복 없는 원자적 추출에는 적합
Q. 법적 감사가 필요한 추첨이면?
→ SPOP만으로 부족. 후보 스냅샷, seed/난수 방식, 실행자, 결과를 DB에 기록
Q. 가중 추첨이면?
→ Set이 아니라 ZSet 등 별도 설계
```

```text
Q. DAU는 Set으로 세면 되나요?
→ 정확한 목록까지 필요하면 Set
Q. 수억 규모라 메모리가 부담되면?
→ 대략 수만 필요하면 HyperLogLog, 촘촘한 정수 ID면 Bitmap
Q. HLL로 공통 방문자도 구할 수 있나요?
→ 정확한 교집합은 안 됨. Set/Bitmap 필요
```

→ **꼬리잡기 답을 미리 준비해두면 면접관이 "어, 이 친구 깊네" 하는 인상.**
