## 시나리오 1 (보스급 🔥) — "공통 관심사 추천이 갑자기 느려졌어요"

**상황**

찜 기반 "취향 비슷한 친구 추천"을 `SINTER favorite:user:A favorite:user:B`로 구현했다. 출시 초엔 빨랐는데, 헤비 유저(아티스트 5만 명 찜)가 늘면서 추천 API가 **수백 ms~초 단위로 느려지고**, 그동안 다른 Redis 명령도 같이 밀린다. 가끔 타임아웃도 난다.

**질문**: 무엇이 문제이고, 어떻게 풀겠는가?

<details>
<summary>펼쳐서 답 보기</summary>

### 원인

1. **SINTER는 O(작은 집합 크기 × 키 개수)** 에 가깝지만, 실제로는 멤버를 다 훑어 비교한다. 5만 × 5만 교집합은 수만 번 연산.
2. **Redis는 단일 스레드.** 무거운 SINTER 하나가 도는 동안 **다른 모든 명령이 대기** → 전체 지연(이게 "다른 명령도 밀린다"의 원인).
3. 추천 API가 **요청마다 실시간 SINTER** → 인기 사용자 조합에 부하 집중.

### 해결

1. **개수만 필요하면 `SINTERCARD ... LIMIT n`** (7.0+) — 유사도 점수는 "공통 몇 개"로 충분한 경우가 많다. 멤버 전체를 안 만들고 LIMIT으로 조기 종료.
2. **결과 캐싱** — `SINTERSTORE recommend:cache:A:B ...` + TTL. 같은 조합 재요청은 캐시 히트. 단 찜 변경 시 무효화.
3. **후보 좁히기** — 모든 사용자와 SINTER 하지 말고, "같은 아티스트를 찜한 사람"(역방향 `fans:artist:{id}`)으로 **후보를 먼저 줄인 뒤** 소수와만 계산.
4. **비실시간으로 이동** — 추천은 실시간일 필요가 적다. **배치(스케줄러)로 미리 계산**해 두고 조회만 실시간. 대규모는 ML 추천 시스템으로.
5. **큰 집합 자체를 경계** — 한 사용자가 5만 찜은 비정상. 상한을 두거나, 추천 계산엔 "최근 찜 N개"만 사용.

### 면접관 후속 질문 (보스전)

**Q1. "SINTERSTORE로 캐싱하면 찜이 바뀔 때 정합성은?"**
> 캐시는 stale 가능. (a) 찜 변경 시 관련 캐시 키 DEL(무효화), (b) 짧은 TTL로 자가 치유, (c) 추천은 약간 stale 해도 비즈니스상 허용되는 경우가 많음. 정확도 요구가 낮은 도메인이라 TTL 기반이 현실적. → String 챕터 Cache-Aside 무효화와 동일 고민.

**Q2. "단일 스레드라 무거운 연산이 전체를 막는다 했는데, 근본 회피책은?"**
> ① 무거운 연산을 작게 쪼개기(후보 좁히기·LIMIT), ② 미리 계산(배치), ③ replica에서 읽기 연산 분산(쓰기는 master), ④ 정말 크면 Redis 밖으로(검색엔진/전용 추천). 핵심은 "hot path에서 O(N) 큰 연산을 제거".

**Q3. "추천을 ZSet으로 하면 뭐가 좋아지나?"**
> 유사도에 **점수/랭킹**을 매겨 "가장 비슷한 친구 top 10"을 `ZREVRANGE`로 뽑을 수 있다. Set은 "공통이냐 아니냐"만, ZSet은 "얼마나 비슷한지" 정렬까지. 다음 챕터(Sorted Set)와 연결.

### 한 줄 교훈
> **큰 Set의 집합 연산은 단일 스레드를 오래 잡는다. 개수만(SINTERCARD)·캐싱(STORE)·후보 좁히기·배치로 hot path에서 큰 연산을 빼라.**

</details>

## 시나리오 2 (라이트) — "좋아요 수가 가끔 틀려요"

**상황**

좋아요를 `INCR likes:count:post:{id}`(String 카운터)로만 세는데, 같은 사용자가 여러 번 누르면 **중복 카운트**된다. 또 "내가 이미 눌렀나?"를 알 수가 없다.

**질문**: 어떻게 고치겠는가?

<details>
<summary>펼쳐서 답 보기</summary>

- **Set으로 누른 사람을 관리**: `SADD likes:post:{id} {userId}`.
  - 반환 1 → 신규(카운트 의미), 0 → 이미 누름(무시).
  - 좋아요 수 = `SCARD`, 내가 눌렀나 = `SISMEMBER`.
- INCR 카운터는 "중복 방지"를 못 한다(누른 사람을 기억 못 하니까). Set은 멤버를 기억해 중복을 원천 차단.

> 💡 **한 걸음 더**: 좋아요가 **수억 개**면 Set 멤버 저장 비용이 커진다. 그땐 "정확한 멤버 목록"이 필요한지 따져, 수만 필요하면 카운터 + 중복방지는 다른 계층(예: Bitmap, 사용자ID 정수일 때)으로. 보통 규모에선 Set이 정답.

</details>

## 시나리오 3 (라이트) — "차단 목록 검사가 느려요"

**상황**

차단된 사용자를 List(`blocked:list`)에 넣고, 요청마다 `LPOS`로 "차단됐나" 검사한다. 차단자가 늘면서 느려졌다.

**질문**: 무엇이 문제인가?

<details>
<summary>펼쳐서 답 보기</summary>

- **List의 멤버 검사 `LPOS`는 O(N)** — 차단자 10만이면 매 요청 10만 비교.
- **Set으로 바꾸면 `SISMEMBER` O(1)**: `SADD blocked:users {userId}` → `SISMEMBER blocked:users {userId}`.
- 차단 목록은 "순서 불필요 + 있다/없다만" → **Set의 교과서적 용례.**

> 💡 **한 걸음 더**: 차단을 여러 개 한 번에 검사(예: 친구 목록 50명 중 차단된 사람)면 `SMISMEMBER`(6.2+)로 왕복 1회. 또 차단이 "기간제"라면 Set 멤버에 TTL이 없으므로(개별 멤버 만료 불가) ZSet(score=만료시각) + 주기적 정리 또는 멤버별 키로 설계.

</details>

## 시나리오 4 (라이트) — "추첨에서 같은 사람이 두 번 당첨됐어요"

**상황**

당첨자 추첨을 `SRANDMEMBER raffle 1`로 한 명 뽑고, 따로 `SREM`으로 제거하는 식으로 3번 반복했다. 그런데 같은 사람이 두 번 뽑혔다.

**질문**: 왜? 어떻게 고치나?

<details>
<summary>펼쳐서 답 보기</summary>

- **SRANDMEMBER + SREM이 원자적이 아님** — 뽑고 지우는 사이, 또는 반복 사이에 같은 멤버가 다시 뽑힐 수 있다.
- **`SPOP raffle 3` 한 번**으로 해결: "랜덤 N개 꺼내며 제거"가 **원자적**이라 중복 불가.

```java
Set<String> winners = redisTemplate.opsForSet().pop("raffle:event:1", 3);  // 중복 없음
```

> 💡 **한 걸음 더**: 가중 추첨(응모 많이 한 사람 유리)은 Set으로 안 됨(균등 랜덤만). 가중치는 ZSet(누적 score) + 랜덤 값으로 구간 선택. 그리고 추첨 결과는 **감사(audit) 위해 DB에도 기록** — Redis는 휘발성이라 당첨 기록 단독 보관 금지.

</details>

## 시나리오 5 (라이트) — "태그 검색이 OR로만 돼요, AND가 필요해요"

**상황**

`#록`, `#내한` 태그로 공연을 검색하는데, 지금은 각 태그 공연을 합쳐서 보여준다(OR). "록이면서 내한"인 공연만(AND) 보고 싶다.

**질문**: 어떻게 구현하나?

<details>
<summary>펼쳐서 답 보기</summary>

- 양방향 인덱스: `SADD concerts:tag:rock concert:100 ...`, `SADD concerts:tag:overseas ...`
- **AND = 교집합**: `SINTER concerts:tag:rock concerts:tag:overseas`
- **OR = 합집합**: `SUNION ...`
- **NOT(제외) = 차집합**: `SDIFF concerts:tag:rock concerts:tag:standing` (록이지만 스탠딩 아닌)

> 💡 **한 걸음 더**: 복합 필터("(록 OR 재즈) AND 내한")는 `SUNIONSTORE tmp rock jazz` → `SINTER tmp overseas`로 단계 조합. 자주 쓰는 조합은 STORE+TTL 캐싱. 단 태그 집합이 수십만+ 이고 필터가 복잡해지면 **검색 엔진(ES)으로 갈 신호** — Redis Set 태그는 중소 규모 필터링의 가성비 좋은 선택.

</details>

## 시나리오 6 (라이트) — "찜 목록이 사라진 것 같아요"

**상황**

사용자가 찜을 다 취소했더니, `EXISTS favorite:user:{id}`가 0을 반환한다. 운영팀이 "이 사용자 데이터가 손실됐다"고 보고했다.

**질문**: 진짜 손실인가?

<details>
<summary>펼쳐서 답 보기</summary>

- **손실 아님.** Set은 **멤버가 0개가 되면 키 자체가 자동 삭제**된다(List/Hash/ZSet 공통). 찜을 다 취소 = 빈 집합 = 키 소멸.
- `EXISTS`가 0, `SCARD`도 0, `SMEMBERS`는 빈 결과. 정상 동작이다.
- "데이터 손실"과 "빈 컬렉션"을 구분해야. 찜이 원래 있었는지는 DB(영구 저장)로 확인.

> 💡 **한 걸음 더**: 그래서 **존재 여부로 상태를 판단하면 안 된다**. "이 사용자가 찜 기능을 써봤나" 같은 건 별도 플래그나 DB로. Redis Set은 "현재 찜 목록"의 캐시/실시간 뷰일 뿐, 영구 진실은 DB. (메모리 휘발 시 재생성 가능하게 설계)

</details>

## 시나리오 7 (라이트) — "SMEMBERS 한 번 호출에 서버가 멈칫해요"

**상황**

관리자 페이지에서 "이 아티스트 전체 팬 목록"을 `SMEMBERS fans:artist:{id}`로 가져온다. 인기 아티스트(팬 300만)에서 호출하니 Redis 전체가 잠깐 멈춘다.

**질문**: 무엇이 문제이고 어떻게?

<details>
<summary>펼쳐서 답 보기</summary>

- **SMEMBERS는 O(N)** — 300만 멤버를 한 번에 직렬화해 전송. 단일 스레드라 그동안 **다른 명령 전부 블로킹**. List의 `LRANGE 0 -1`과 같은 함정.
- **`SSCAN`으로 커서 순회**: 조금씩(`COUNT` 힌트) 나눠 가져와 블로킹 회피.
- 애초에 "전체 목록"이 정말 필요한지 재검토. 보통 **개수(SCARD)**나 **샘플(SRANDMEMBER)**, **페이지(SSCAN)** 로 충분.

> 💡 **한 걸음 더**: big key는 삭제도 위험 — `DEL`은 동기 블로킹, `UNLINK`로 비동기. 모니터링은 `redis-cli --bigkeys`나 `MEMORY USAGE`. 근본적으로 멤버 300만 단일 키는 샤딩(여러 키로 분할) 고려.

</details>

## 시나리오 8 (라이트) — "유니크 방문자 수, 메모리가 너무 커요"

**상황**

일별 유니크 방문자를 `SADD visitors:{date} {userId}`로 정확히 센다. 그런데 방문자가 수천만이 되니 날짜별 Set이 메모리를 많이 먹는다. 사실 **정확한 수까지 필요 없고 "대략 몇 명"**이면 된다.

**질문**: 어떤 대안?

<details>
<summary>펼쳐서 답 보기</summary>

- **HyperLogLog**: `PFADD visitors:{date} {userId}` → `PFCOUNT`. **12KB 고정**으로 수억 유니크를 ±0.81% 오차로 근사. 멤버 목록은 못 보지만 "대략 수"엔 완벽.
- 사용자 ID가 **정수**라면 **Bitmap**도 후보: `SETBIT` + `BITCOUNT`. 정확하면서 압축적(1명=1비트).
- 선택: **목록·정확 = Set / 정수ID = Bitmap / 대규모 근사 = HyperLogLog.**

> 💡 **한 걸음 더**: HLL은 합집합도 됨 — `PFMERGE`로 "주간 유니크"(7일 HLL 병합)를 근사 계산. Set의 SUNION을 무거운 비용 없이 흉내. 단 교집합(공통 방문자)은 HLL로 정확히 안 되니 그건 Set/Bitmap.

</details>

## 시나리오 9 (라이트) — "권한 체크를 매번 DB로 해서 느려요"

**상황**

사용자의 역할/권한(`ROLE_ADMIN`, `CAN_REFUND` 등)을 매 요청마다 DB 조회로 확인한다. 트래픽이 늘며 DB 부하가 커졌다.

**질문**: Set으로 어떻게 개선하나?

<details>
<summary>펼쳐서 답 보기</summary>

- 사용자 권한을 Set으로 캐싱: `SADD perms:user:{id} "CAN_REFUND" "CAN_EXPORT"`.
- 검사 = `SISMEMBER perms:user:{id} "CAN_REFUND"` O(1). 여러 개면 `SMISMEMBER`.
- 권한 변경 시 Set 갱신(SADD/SREM) + 또는 TTL로 주기적 재동기화.

> 💡 **한 걸음 더**: 권한은 **정합성이 중요**(잘못 허용하면 보안 사고). 그래서 Redis는 캐시일 뿐 **진실은 DB**, 권한 변경은 DB→Redis 동기화 + 짧은 TTL. 민감한 작업(환불 실행)은 Redis 캐시만 믿지 말고 **최종 확인은 DB**로 한 겹 더. → [도구 선택 가이드](../../MESSAGING_TOOL_GUIDE.md): "진실은 DB, Redis는 효율".

</details>

## 시나리오 10 (라이트) — "WRONGTYPE 에러가 떠요"

**상황**

`favorite:user:{id}`에 `SADD`를 했는데 `WRONGTYPE Operation against a key holding the wrong kind of value` 에러가 난다.

**질문**: 원인과 예방책?

<details>
<summary>펼쳐서 답 보기</summary>

- **그 키가 이미 다른 타입**(String/List 등)으로 존재. Redis는 키 단위로 타입이 고정 → Set 명령을 String 키에 쓰면 WRONGTYPE.
- 흔한 원인: ① 같은 키 이름을 다른 용도로 재사용, ② 어디선가 `SET favorite:user:{id} ...`로 String을 써버림, ③ 직렬화 실수.
- 예방: **네이밍 컨벤션으로 타입 분리**(`favorite:user:{id}`=Set 전용), 키 용도 문서화. 디버깅은 `TYPE key`로 실제 타입 확인.

> 💡 **한 걸음 더**: 마이그레이션 중 타입을 바꿔야 하면 새 키로 만들고 전환(rename)하거나, 기존 키 DEL 후 재생성. 운영 중 `TYPE`으로 사전 점검하는 헬스체크를 두면 조기 발견.

</details>

## 마무리

10개를 다 봤으면 → **`03-면접질문.md`** 로 단답 점검.

> 관통 주제 3가지:
> 1. **멤버십(SISMEMBER O(1))·중복방지(SADD 반환값)** 가 Set의 일상 용도.
> 2. **집합 연산(SINTER/SDIFF)** 은 강력하지만 **큰 Set에선 비싸다** — 개수만/캐싱/후보좁히기/배치.
> 3. **빈 Set=키 소멸, SMEMBERS=big key 함정, 진실은 DB.** Set은 효율·실시간 뷰.
