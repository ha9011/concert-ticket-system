# Set 실무 — 실제 서비스에서 어떻게 쓰는가

> 요약에서 명령어를 정리했다면, 여기선 **"이 명령어들을 조합해 실제 기능을 어떻게 만드나"**가 주제.
> 무대는 이 프로젝트(콘서트 티켓)의 **찜한 아티스트 / 공통 관심사 / 알림 대상 / 태그 / 중복 방지.**

## 이 문서에서 다루는 7대 패턴

1. **중복 방지 / 1회 제한** — SADD 반환값 (좋아요·투표·찜)
2. **멤버십 검사** — SISMEMBER (차단·권한·이미 본 항목)
3. **태그 시스템 (양방향 인덱스)** — SADD + SINTER
4. **공통 관심사 / 추천** — SINTER / SDIFF (협업 필터링 기초)
5. **랜덤 추첨** — SPOP / SRANDMEMBER
6. **출석 체크 / 유니크 카운트** — Set vs Bitmap vs HyperLogLog
7. **알림 대상 집합** — Set + List Fan-out 연결

---

# §1. 중복 방지 / 1회 제한 — SADD 반환값

## 문제

"한 사람당 한 번만" 해야 하는 동작: 게시글 좋아요, 투표, 찜, 출석. 동시에 여러 요청이 와도 정확히 1회만 카운트돼야 한다.

## 패턴 — SADD 반환값(1/0)으로 판단

```java
// 좋아요 — 이미 눌렀으면 무시
Long added = redisTemplate.opsForSet().add("likes:post:" + postId, userId);
// SADD likes:post:123 user:42
if (added == 1) {
    // 신규 좋아요 → 카운트 증가, 알림 등
} else {
    // 이미 누름 (added == 0) → "이미 좋아요한 게시글입니다"
}

long count = redisTemplate.opsForSet().size("likes:post:" + postId);  // SCARD = 좋아요 수
boolean liked = redisTemplate.opsForSet().isMember("likes:post:" + postId, userId); // SISMEMBER
```

## 왜 Set인가

- **원자성**: `SADD`는 단일 명령이라 동시에 1000명이 같은 글에 좋아요 눌러도 **정확히 한 번**만 신규로 처리(단일 스레드 직렬화). DB `INSERT ... UNIQUE`로도 되지만 Redis가 빠르고, 락이 필요 없다.
- **3-in-1**: "중복 방지 + 이미 했는지 판단 + 누른 사람 목록"을 한 자료구조로.

## 이 프로젝트 적용 — 찜하기

```java
// AuthService/FavoriteService 가정
Long added = redisTemplate.opsForSet().add("favorite:user:" + userId, "artist:" + artistId);
if (added == 0) {
    throw new CustomException(ErrorCode.ALREADY_FAVORITED);  // 이미 찜함
}
// 역방향 인덱스도 같이 (알림용)
redisTemplate.opsForSet().add("fans:artist:" + artistId, "user:" + userId);
```

> ⚠ **좋아요 수를 SCARD로 매번 셀지, 별도 카운터(INCR)로 둘지**는 트레이드오프. SCARD는 O(1)이라 보통 충분. 단 멤버 목록이 필요 없고 수만 필요하면 String INCR + 주기적 동기화가 메모리 이득일 수 있다.

# §2. 멤버십 검사 — SISMEMBER

## 문제

"이 사용자가 차단됐나?", "이 IP가 화이트리스트에 있나?", "이미 본 상품인가?", "이 기능 권한 있나?" — **O(1)로 빠르게 있다/없다.**

## 패턴

```java
// 차단 목록
boolean blocked = redisTemplate.opsForSet().isMember("blocked:users", userId);
if (blocked) throw new CustomException(ErrorCode.FORBIDDEN);

// 이미 본 상품 (최근 본과 다름 — 여긴 "봤다/안 봤다"만)
redisTemplate.opsForSet().add("viewed:user:" + userId, "product:" + pid);
boolean seen = redisTemplate.opsForSet().isMember("viewed:user:" + userId, "product:" + pid);
```

## 왜 Set인가 (List와 비교)

| | Set | List |
|---|---|---|
| "있나?" 검사 | `SISMEMBER` **O(1)** | `LPOS` **O(N)** |
| 중복 | 자동 제거 | 그대로 쌓임 |
| 순서 | 없음 | 있음 |

→ **"순서는 필요 없고 있다/없다만 자주 검사"면 무조건 Set.** 차단·권한·플래그류의 표준.

> 💡 여러 개를 한 번에 검사하면 `SMISMEMBER`(6.2+)로 왕복 절약. 예: 장바구니 상품 10개가 각각 품절 집합에 있는지 한 번에.

# §3. 태그 시스템 — 양방향 인덱스 + 집합 연산

## 문제

공연에 태그(`#록`, `#내한`, `#스탠딩`)를 붙이고, "록이면서 내한인 공연"처럼 **여러 태그의 교집합**으로 검색.

## 패턴 — 양방향 인덱스

```java
// 공연 → 태그들
SADD tags:concert:100 "rock" "overseas" "standing"
// 태그 → 공연들 (역방향)
SADD concerts:tag:rock      "concert:100" "concert:205"
SADD concerts:tag:overseas  "concert:100" "concert:301"
```

## 태그 AND 검색 = 교집합

```java
// "rock AND overseas" 공연 = 두 태그 집합의 교집합
Set<String> result = redisTemplate.opsForSet()
        .intersect("concerts:tag:rock", "concerts:tag:overseas");
// SINTER concerts:tag:rock concerts:tag:overseas → concert:100

// 개수만 필요하면 (7.0+)
// SINTERCARD 2 concerts:tag:rock concerts:tag:overseas
```

- **AND 검색** = `SINTER` (교집합)
- **OR 검색** = `SUNION` (합집합)
- **NOT(제외)** = `SDIFF` (차집합) — "rock이지만 standing은 아닌"

> 💡 자주 쓰는 조합은 `SINTERSTORE`로 결과를 캐싱하고 TTL을 걸어 재사용. 단, 태그가 바뀌면 캐시 무효화 필요.

> 🚨 태그별 공연 집합이 수십만 개로 커지면 SINTER 비용↑. 그땐 검색 엔진(Elasticsearch)으로 넘어갈 신호. Redis Set 태그는 **중소 규모 필터링**에 적합.

# §4. 공통 관심사 / 추천 — SINTER / SDIFF (협업 필터링 기초)

## 문제

"나와 취향이 비슷한 사용자", "친구는 찜했지만 나는 안 찜한 아티스트 추천".

## 공통 관심사 = 교집합

```java
// 두 사용자가 함께 찜한 아티스트
Set<String> common = redisTemplate.opsForSet()
        .intersect("favorite:user:1", "favorite:user:2");
// SINTER favorite:user:1 favorite:user:2

// 취향 유사도 = 공통 개수 (멤버 안 가져옴, 효율적)
// SINTERCARD 2 favorite:user:1 favorite:user:2
```

## 추천 = 차집합

```java
// "비슷한 친구(user:2)는 찜했지만 나(user:1)는 아직 안 찜한 아티스트" → 추천 후보
Set<String> recommend = redisTemplate.opsForSet()
        .difference("favorite:user:2", "favorite:user:1");
// SDIFF favorite:user:2 favorite:user:1
```

## 왜 이게 추천인가 (협업 필터링 기초)

> "나와 취향이 겹치는(SINTER 큰) 사람이 좋아하는데(그의 집합) 내가 아직 모르는(SDIFF) 것" = **사람들이 실제로 쓰는 추천의 가장 단순한 형태.** 넷플릭스·스포티파이 추천의 출발점이 이 집합 연산이다.

> 🚨 사용자가 수백만이면 모든 쌍의 SINTER는 불가능. 실무는 **후보를 좁힌 뒤**(같은 아티스트 찜한 사람만) 부분적으로 계산하거나, 배치/ML로 미리 계산. Redis 집합 연산은 **실시간 소규모 + 후보 좁히기**에 적합.

# §5. 랜덤 추첨 — SPOP / SRANDMEMBER

## 문제

이벤트 응모자 중 당첨자 N명 추첨. 공정하게, 중복 없이.

## 패턴 — 중복 없는 당첨자 = SPOP

```java
// 응모
SADD raffle:event:1 "user:1" "user:2" ... "user:1000"

// 당첨자 3명 (뽑힌 사람은 풀에서 제거 → 중복 당첨 없음)
Set<String> winners = redisTemplate.opsForSet().pop("raffle:event:1", 3);
// SPOP raffle:event:1 3
```

## SPOP vs SRANDMEMBER 선택

| 목적 | 명령 | 이유 |
|---|---|---|
| 당첨자 확정 (중복 X, 풀에서 제거) | `SPOP k N` | 뽑힌 사람 재추첨 방지 |
| 후보 미리보기 (풀 유지) | `SRANDMEMBER k N` (양수) | 안 지움, 중복 없이 |
| 중복 허용 샘플 (주사위) | `SRANDMEMBER k -N` (음수) | 같은 멤버 또 가능 |

> ⚠ **추첨은 SPOP이 정석** — SRANDMEMBER로 뽑고 따로 SREM 하면, 그 사이 같은 사람이 또 뽑힐 수 있다(원자성 깨짐). SPOP은 "뽑기+제거"가 원자적.

> 🪤 단, SPOP은 **공정성**을 균등 랜덤으로 보장하지만 "가중 추첨"(응모 많이 한 사람 유리)은 안 됨. 가중치 추첨은 ZSet(score=누적 가중치) + 랜덤 score 조회로.

# §6. 출석 체크 / 유니크 카운트 — Set vs Bitmap vs HyperLogLog

## 문제

"오늘 접속한 순수 사용자 수(DAU)", "이벤트 7일 연속 출석", "페이지 유니크 방문자".

## 패턴 ① 정확 + 목록 필요 → Set

```java
// 오늘 접속자
SADD active:2026-06-15 "user:42"
SCARD active:2026-06-15            // 정확한 DAU
SISMEMBER active:2026-06-15 "user:42"  // 이 사람 오늘 왔나

// 7일 연속 출석 = 7일 집합의 교집합
SINTER active:2026-06-09 active:2026-06-10 ... active:2026-06-15
```

## 패턴 ② 정수 ID + 초압축 → Bitmap

```
# 사용자 ID가 정수일 때, 1비트로 표현
SETBIT active:2026-06-15 42 1     # user 42 접속
BITCOUNT active:2026-06-15        # 접속자 수
BITOP AND result 0609 0610 ...    # 연속 출석 = 비트 AND
```

## 패턴 ③ 대규모 근사 카운트 → HyperLogLog

```
PFADD visitors:2026-06-15 "user:42"
PFCOUNT visitors:2026-06-15       # 유니크 방문자 (±0.81% 오차, 12KB 고정)
```

## 선택 기준

| 상황 | 선택 | 이유 |
|---|---|---|
| 누가 왔는지 목록도 필요, 정확해야 | **Set** | SMEMBERS/SISMEMBER 가능 |
| 사용자 ID가 정수, 초절약 | **Bitmap** | 1명=1비트 (1000만명≈1.2MB) |
| 수억 유니크의 "대략 수"만 | **HyperLogLog** | 12KB 고정, 멤버 조회 불가 |

> 핵심: **목록·정확도 = Set / 정수ID 출석 = Bitmap / 대규모 근사 = HyperLogLog.** "유니크 카운트"라고 다 Set이 아니다.

# §7. 알림 대상 집합 — Set + List Fan-out 연결

## 문제

아티스트가 새 공연을 등록하면, 그를 찜한 모든 사용자에게 알림.

## 패턴 — Set(대상) → List(개인 피드)로 Fan-out

```java
// 1) 누가 이 아티스트의 팬인지 = Set (§1에서 역방향 인덱스로 쌓아둠)
Set<String> fans = redisTemplate.opsForSet().members("fans:artist:" + artistId);
// 운영에선 SMEMBERS 대신 SSCAN (팬 많으면)

// 2) 각 팬의 개인 피드(List)에 공연 ID 뿌리기 = Fan-out on write (List 챕터)
for (String fan : fans) {
    redisTemplate.opsForList().leftPush("feed:" + fan, "concert:" + concertId);
    redisTemplate.opsForList().trim("feed:" + fan, 0, 999);  // 최근 1000개
}
```

## 자료구조 분업

- **Set** = "누가 대상인가" (찜한 사람들, 중복 없이) — 멤버십·교집합
- **List** = "각자에게 시간순으로 전달" (개인 피드) — 순서·Fan-out

> 💡 이게 Set과 List가 협업하는 대표 예. **"대상 선정은 Set, 전달은 List."** (List 챕터 §5 Fan-out과 직결)

> 🚨 팬이 1000만이면 SMEMBERS로 다 끌어와 루프 = 위험. SSCAN으로 나눠 처리하거나, 셀럽은 Fan-out on read로(List 챕터 셀럽 문제). [도구 선택 가이드](../../MESSAGING_TOOL_GUIDE.md) 참고.

# §8. 프로젝트 적용 미션 (선택)

이 프로젝트(`api-server`)에 Set을 직접 이식해보는 미션:

1. **찜 기능 추가** — `POST /api/favorites` → `SADD favorite:user:{id} artist:{id}` + 반환값으로 중복 차단. 역방향 `fans:artist:{id}`도 갱신.
2. **공통 관심사 API** — `GET /api/users/{a}/common/{b}` → `SINTER`로 함께 찜한 아티스트.
3. **추천 API** — `GET /api/users/{id}/recommend` → 취향 비슷한 사용자 찾아 `SDIFF`로 추천.
4. **새 공연 알림** — 공연 등록 시 `fans:artist:{id}`(Set) → 각 팬 `feed:user:{id}`(List)로 Fan-out.
5. **유니크 방문자** — 공연 상세 페이지 DAU를 Set 또는 HyperLogLog로.

## 핵심 요약 (실무 한 줄씩)

| 패턴 | 명령 | 키 예시 |
|---|---|---|
| 중복 방지/1회 제한 | `SADD` 반환값 | `likes:post:{id}`, `favorite:user:{id}` |
| 멤버십 검사 | `SISMEMBER` | `blocked:users`, `viewed:user:{id}` |
| 태그 AND 검색 | `SINTER` (양방향 인덱스) | `concerts:tag:{name}` |
| 공통 관심사 | `SINTER`/`SINTERCARD` | `favorite:user:{id}` |
| 추천 | `SDIFF` | `favorite:user:{id}` |
| 추첨 | `SPOP count` | `raffle:event:{id}` |
| 유니크 카운트 | `SCARD`/Bitmap/HLL | `active:{date}` |
| 알림 대상 | `SMEMBERS`/`SSCAN` → List | `fans:artist:{id}` |
