## 🛡️ 다층 방어 (Defense in Depth)

한 가지로는 못 막는다. 3~4개 층을 쌓는 게 정석.

### Layer 1: "유효한 코드 있으면 재발급 금지" (가장 강력, 가장 싸다)

```
SET auth:{email} {code} NX EX 180
└─ NX 실패 = 이미 발급된 코드가 살아있음 → "기존 코드를 확인해주세요"
```

**효과**: 같은 이메일은 **3분에 1번만** 발송. 한 줄 변경으로 99% 차단.
**현재 코드 변경 포인트**: `AuthService.java:39` 의 `set()` → `setIfAbsent()`.

> 💡 **디테일 — 제약의 "재발송 UX"와 충돌하지 않나?**
> `NX EX 180`은 *유효한 코드가 살아있는 3분간 모든 재발송을 차단*한다. 그런데 사용자가 메일을 못 받았거나(스팸함) 지웠으면? 3분 묶이면 CS가 터진다. 그래서 실무는 **"코드 유효기간"과 "재발송 쿨다운"을 분리**한다:
> - `auth:{email}` = 코드 본체, TTL 180초 (검증용)
> - `auth:cooldown:{email}` = 재발송 쿨다운, TTL 30~60초 (이 키 있으면 "잠시 후 다시 시도하세요")
>
> 이러면 코드는 3분 유효하되, 재발송 버튼은 60초 후 다시 눌러 **새 코드 발급(덮어쓰기)** 이 가능하다. 즉 Layer 1을 "발송 자체 차단"이 아니라 "쿨다운"으로 운영하는 변형. 어느 쪽이든 본질은 *"한 번 보낸 직후 곧바로 또 보내는 것"을 원자적으로 막는다*는 것.

### Layer 2: 이메일별 시간당 발송 횟수

```java
String key = "auth:rl:email:" + email;
Long count = redis.opsForValue().increment(key);
if (count == 1) redis.expire(key, 1, TimeUnit.HOURS);
if (count > 5) throw new TooManyRequestsException();
```

**효과**: Layer 1을 우회한 정상 재발송도 시간당 5회로 캡.

### Layer 3: IP별 분당 발송 횟수 (봇 차단)

```java
String key = "auth:rl:ip:" + clientIp + ":" + nowMinute();
Long count = redis.opsForValue().increment(key);
if (count == 1) redis.expire(key, 60, TimeUnit.SECONDS);
if (count > 10) throw new TooManyRequestsException();
```

**효과**: 한 IP에서 이메일을 바꿔가며 봇질하는 패턴 차단.

### Layer 4 (필요 시): CAPTCHA

위 3개로 모자라면 마지막에 reCAPTCHA. UX 비용이 큼.

## 🪤 면접관이 깊이 파고들면

### Q1. "IP가 NAT 뒤면 같은 IP에 정상 사용자가 여러 명 있을 수 있는데요?"

→ IP 제한은 분당 10회처럼 **느슨하게**. 이메일 제한이 본진. IP는 보조 방어.

### Q2. "Redis가 다운되면 인증 코드 발송도 다 막힐 텐데, 어떻게 처리하시겠어요?"

→ **fail-open vs fail-closed** 트레이드오프.
- fail-open: Redis 죽으면 모든 발송 허용 (UX 우선, 보안 약화)
- fail-closed: Redis 죽으면 모든 발송 거부 (보안 우선, UX 망함)
- 인증 코드는 **fail-open이 일반적** (사용자가 가입을 못 하는 게 더 큰 문제).
- 대신 Redis 헬스체크 + 알람 + Sentinel/Cluster로 가용성 확보.

### Q3. "Layer 2의 Fixed Window는 경계 직전에 폭주 가능하잖아요?"

→ **시나리오**: 10:59:59에 5번, 11:00:00에 5번 → 2초 만에 10번 발송.
→ **해법**: Sliding Window. String만으론 정확히 못 만들고 Sorted Set 필요. ([[redis-sorted-set]] 단계에서 다룸)
→ **실무 절충**: 대부분 인증 코드 수준에선 Fixed Window로 충분.

### Q4. "Layer 1이 그렇게 좋으면 Layer 2~3은 왜 필요해요?"

→ 공격자가 **이메일을 매번 바꿔서** 시도하면 Layer 1은 매번 통과. Layer 2(이메일별)도 통과. Layer 3(IP별)에서 막힘.

### Q5. "INCR + EXPIRE 두 줄로 나누면 원자성 깨지는 거 아니에요?"

→ 동시 요청 시 둘 다 1로 INCR되어 둘 다 EXPIRE 호출 — 큰 문제는 없음.
→ **완벽한 원자성을 원하면 Lua**:
```lua
local v = redis.call('INCR', KEYS[1])
if v == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return v
```

## 🎯 핵심 takeaway

> **"막는 건 한 줄로 안 된다. 층층이 쌓아라. 가장 싼 방어를 가장 앞에 둬라."**
>
> - Layer 1 (`SET NX EX`) 은 비용 0, 효과 99% — 무조건 먼저
> - 모든 Layer는 Redis 명령어 1~2개로 구현됨
> - 인증 코드 보안 = **"`NX EX` 한 줄과 `INCR + EXPIRE` 패턴의 조합"**

# 🎬 시나리오 2. "프로필을 고쳤는데 옛날 정보가 안 바뀌어요" (+ 메모리 누수)

## 📋 상황

월요일 오전, 두 가지 제보가 거의 동시에 들어왔다.

> **CS 팀**: "사용자가 닉네임을 바꿨는데 며칠째 옛날 닉네임이 그대로 보인대요. 새로고침해도 안 바뀐대요."
> **인프라**: "Redis 메모리가 주말 사이 계속 우상향했어요. `user:*` 키가 줄지를 않아요."

코드를 봤더니 누군가 어제 이런 PR을 머지했다:

```java
public void updateProfile(Long userId, ProfileDto dto) {
    User user = userRepository.findById(userId).orElseThrow();
    user.update(dto);
    userRepository.save(user);

    // 캐시 갱신
    redisTemplate.opsForValue().set("user:" + userId, toJson(user));   // ← 이 한 줄
}
```

원래 이 프로젝트의 캐시 키 `user:{id}` 는 **10분 TTL**로 운영되고 있었다.

## ❓ 질문

이 한 줄이 어떻게 "옛날 데이터가 안 바뀜"과 "메모리 누수" 두 증상을 **동시에** 만들었나? 어떻게 고치겠나?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

**문제**: `set(key, value)` 에 **`EX`/`KEEPTTL` 옵션이 없음** → 값을 덮어쓰는 순간 **기존 10분 TTL이 사라지고 영구 키(TTL -1)가 된다.**

Redis의 `SET`은 기본적으로 "키를 새로 쓴다"는 의미라, 명시하지 않으면 **TTL 같은 부가 메타데이터를 리셋**한다. 직접 찍어보면:

```
> SET user:1 "old" EX 600
> TTL user:1
(integer) 597          ← 10분 카운트다운 중

> SET user:1 "new"     ← 옵션 없이 덮어씀
> TTL user:1
(integer) -1           ← TTL 증발. 이제 영구 키
```

### 왜 증상이 두 개인가

영구 키(TTL -1)가 되면 두 가지가 동시에 터진다:

1. **메모리 누수** — `user:*` 키가 만료되지 않고 계속 쌓인다. 가입자·수정자가 늘수록 영원히 우상향(→ 시나리오 8과 같은 뿌리). **이건 무조건 터지는 확실한 피해.**

2. **stale data가 영원히 박제됨** — 단, 이건 *조건부* 피해다. 바로 아래에서 따로 본다.

#### 🤔 잠깐 — "프로필 수정할 때마다 `set` 으로 덮는데 왜 옛날 값이 보이지?"

맞는 의문이다. **`updateProfile` 를 타면 캐시는 새 값으로 덮이니, 그 경로에선 stale이 안 생긴다.** stale은 **캐시를 안 건드리는 *다른* 경로** 때문에 생기고, TTL이 사라지면 그게 영구화되는 것이다.

먼저 **TTL의 진짜 역할 = 자동 복구 안전망**. 캐시는 DB의 사본이고, 사본은 언젠가 원본과 어긋난다. TTL 10분은 "어쩌다 어긋나도 최대 10분만 틀리고 다시 맞춰진다"는 *지우개*다:

```
캐시가 어쩌다 stale → 10분 뒤 만료 → 다음 조회 = 캐시 미스 → DB에서 fresh 재적재 → 정합 복구
```

영구 키가 되면 이 지우개가 사라져 **한 번 어긋나면 영원히** 어긋난다. 그럼 "어긋나는 경로"는 둘:

**① `updateProfile` 를 우회하는 쓰기** — 관리자 배치 잡, 다른 마이크로서비스, 운영자가 DB 콘솔에서 직접 UPDATE, 탈퇴/정지 같은 다른 도메인 로직. 이들은 **DB만 바꾸고 `redis.set` 은 아무도 안 부른다** → 캐시는 옛값 그대로.

**② 동시 수정 레이스** (`updateProfile` 하나만 써도 발생) — `save()` 후 `redis.set()` 순서라, 두 요청이 거의 동시에 들어오면 캐시 쓰기 순서가 DB와 엇갈릴 수 있다:

```
시각   요청A (닉네임="가")        요청B (닉네임="나")
t1     save(가) → DB=가
t2                                save(나) → DB=나      ← DB 최종 = "나" (정답)
t3                                redis.set(나)          ← 캐시 = "나"
t4     redis.set(가)  ← 늦게 도착                        ← 캐시 = "가" (DB와 역전!)
```

DB는 "나"인데 캐시는 "가"로 끝난다. A의 `redis.set` 이 B보다 늦게 도착해 더 옛 값으로 덮은 것. TTL 있으면 10분 뒤 자가 치유, 영구 키면 "가"가 **영원히** 박제.

> 💡 이게 아래 *"갱신(set)보다 무효화(delete)가 더 안전"* 의 진짜 이유다. `delete` 는 캐시를 비워 *다음 조회가 DB에서 최신을 가져오게* 하므로 이 역전 레이스가 아예 안 생긴다.

**정직하게**: `updateProfile` 가 유일 경로 + 동시성 없음이면 영구 키의 피해는 **메모리 누수뿐**이고 stale은 안 생긴다. 하지만 우회 경로나 동시 수정이 하나라도 있으면(= 현실) **메모리 누수 + stale 영구 박제** 둘 다 터진다. 그래서 메모리 누수는 *확실한* 피해, stale은 *조건부* 피해다. CS가 본 "안 바뀌는 닉네임"이 후자.

> 핵심: 이 한 줄은 캐시를 *사라지게* 한 게 아니라 **_영구로 만들어버려서_ TTL의 자가 치유 능력을 없앤 것**이다.

## ✅ 올바른 패턴 (3가지)

```java
// (1) 매번 TTL 다시 주기 (가장 흔함, 명시적)
redisTemplate.opsForValue().set(key, json, 10, TimeUnit.MINUTES);

// (2) KEEPTTL — 값만 교체하고 기존 TTL 유지
redisTemplate.execute((RedisCallback<Boolean>) c ->
    c.set(key.getBytes(), json.getBytes(),
          Expiration.keepTtl(), RedisStringCommands.SetOption.UPSERT));

// (3) 갱신 대신 무효화 — 다음 조회 때 DB에서 다시 캐싱 (Cache-Aside 정석)
redisTemplate.delete(key);
```

> 💡 사실 write 시엔 **갱신(set)보다 무효화(delete)가 더 안전**하다. 갱신은 "DB 저장 ↔ 캐시 쓰기" 사이 race로 stale을 만들 수 있지만, 무효화는 다음 조회가 알아서 최신값을 채운다. 쓰기 빈도가 높지 않으면 (3)이 기본기.

## 🪤 함정 한 줄

> **TTL 있는 키를 옵션 없이 `SET`으로 덮어쓰면 TTL이 -1(영구)로 날아간다.** 영구 키는 (1) 메모리 누수 (2) TTL 자가 치유 상실을 동시에 부른다. 갱신엔 `EX` 재지정 또는 `KEEPTTL`, 아니면 아예 `DEL` 무효화. (→ 03-면접질문.md Q27)

</details>

# 🎬 시나리오 3. 좌석 예매 oversell — 같은 자리 2명 결제됨

## 📋 상황

콘서트 티켓 오픈 1분 만에 CS 문의 100건. "같은 좌석 A-15 에 저랑 다른 사람 둘 다 결제됐어요."

DB를 확인하니 좌석 A-15에 대한 `Booking` 레코드가 진짜 2개 있다. 결제도 둘 다 성공.

코드는 이렇다:
```java
public void bookSeat(Long concertId, String seatNo, Long userId) {
    Seat seat = seatRepository.findByConcertAndNo(concertId, seatNo);
    if (seat.isBooked()) throw new AlreadyBookedException();
    seat.book(userId);
    seatRepository.save(seat);
}
```

## ❓ 질문

이 코드가 왜 같은 좌석에 2명 부킹을 허용하나? 어떻게 막을래?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

**문제**: `findByConcertAndNo` → `isBooked()` 체크 → `save()` 사이에 다른 요청이 끼어들 수 있음 (TOCTOU race condition). api-server가 2대면 자바 `synchronized`도 무용지물.

## ✅ Redis 분산락 적용

```java
public void bookSeat(Long concertId, String seatNo, Long userId) {
    String lockKey = "lock:seat:" + concertId + ":" + seatNo;
    String owner = UUID.randomUUID().toString();

    Boolean acquired = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, owner, 10, TimeUnit.SECONDS);   // NX EX 10s

    if (!Boolean.TRUE.equals(acquired)) {
        throw new SeatLockedException();
    }

    try {
        Seat seat = seatRepository.findByConcertAndNo(concertId, seatNo);
        if (seat.isBooked()) throw new AlreadyBookedException();
        seat.book(userId);
        seatRepository.save(seat);
    } finally {
        // 반드시 owner 검증 후 해제 (Lua)
        redisTemplate.execute(releaseScript, List.of(lockKey), owner);
    }
}
```

**핵심 3가지**:
1. `NX EX 10s`: 락 획득과 TTL을 원자적으로
2. `owner = UUID`: 내가 잡은 락인지 식별 (DEL 시 검증)
3. Lua로 안전한 해제: TTL 만료 후 다른 클라이언트가 락 잡았을 때 내가 잘못 지우는 사고 방지

### 💡 한 걸음 더 — 왜 깨지나, 그리고 이게 최선일까?

**왜 2명이 통과하나 (정확히)**: `find → isBooked() 검사 → save()` 는 전형적인 **Check-Then-Act**다. 두 요청이 거의 동시에 들어오면 *둘 다* `isBooked() == false` 를 본다(아직 아무도 `save` 안 함) → *둘 다* 통과해 각자 `save` → oversell. api-server가 2대라 JVM `synchronized`·`ReentrantLock`은 **프로세스 경계를 못 넘어** 무용지물 — 그래서 *프로세스 밖 공유 저장소(Redis)* 의 락이 필요한 것.

**하지만 Redis 분산락이 "유일한 정답"은 아니다.** 좌석 oversell은 사실 **DB 한 겹으로도 막히고, 그게 더 정확하다**:

| 해법 | 메커니즘 | 정합성 | 비고 |
|---|---|---|---|
| **DB unique 제약** | `UNIQUE(concert_id, seat_no)` 에 `Booking` insert | ★ 최강 (DB가 물리적으로 2행 거부) | 가장 단순·확실. 2번째 insert는 `DuplicateKeyException` |
| **비관적 락** | `SELECT ... FOR UPDATE` 로 좌석 행 잠금 | ★ 강 | 단일 DB면 충분, 트랜잭션 경계 안에서 |
| **낙관적 락** | `@Version` 컬럼, 충돌 시 재시도 | ★ 강 | 경합 낮을 때 유리 |
| **Redis 분산락** | `SET NX EX` + owner | △ (failover 시 중복 가능) | DB 부하 분산·빠른 실패엔 좋지만 **단독으로 정확성 보장은 아님** |

→ **핵심 원칙**: *Redis 락은 "효율"(DB까지 안 가고 앞단에서 빠르게 쳐내기 + 대기열 UX), 정합성의 마지막 보루는 DB 제약.* 비동기 복제라 failover 순간 두 클라이언트가 같은 락을 쥘 수 있기 때문(→ 시나리오 7, 03-면접질문 Q33 Redlock 논쟁). **실무 정석은 둘 다 쓰는 다층 방어**: Redis 락으로 대부분의 경합을 앞단에서 빠르게 막고, **DB unique 제약을 fencing으로 한 겹 더** 깔아 "락이 뚫려도 DB가 최종적으로 2번째를 거부"하게 한다. 이 프로젝트처럼 좌석=한정 자원이면 unique 제약은 사실상 필수.

## 🪤 함정 한 줄

> **락 해제를 그냥 `DEL` 로 하면 다른 클라이언트의 락을 지운다.** 반드시 Lua로 owner 검증. 그리고 **분산락만 믿지 말고 DB unique 제약을 최종 방어로** — 락은 효율, 제약은 정합성.

PG사 답변: "네트워크 타임아웃 시 우리는 at-least-once로 재시도합니다. 멱등성은 가맹점 책임이에요."

## ❓ 질문

같은 콜백이 N번 와도 1번만 처리하려면?

<details>
<summary>💭 펼치기</summary>

## 💡 답안

PG사 콜백에는 거의 항상 **고유 트랜잭션 ID** 가 들어 있다. 그걸 멱등성 키로 사용.

```java
public void handlePaymentCallback(PaymentCallback cb) {
    String idemKey = "idem:payment:" + cb.getTxId();

    Boolean isFirst = redisTemplate.opsForValue()
        .setIfAbsent(idemKey, "PROCESSING", 24, TimeUnit.HOURS);

    if (!Boolean.TRUE.equals(isFirst)) {
        log.info("Duplicate callback ignored: {}", cb.getTxId());
        return;   // 멱등성: 두 번째부터 무시
    }

    try {
        processPayment(cb);   // 포인트 적립, 주문 상태 변경 등
        redisTemplate.opsForValue().set(idemKey, "DONE", 24, TimeUnit.HOURS);
    } catch (Exception e) {
        redisTemplate.delete(idemKey);   // 실패 시 재시도 허용
        throw e;
    }
}
```

**왜 24시간 TTL?**: 24시간 안에는 같은 콜백 재시도가 도착해도 차단. 그 이후는 메모리 회수.

### 💡 한 걸음 더 — 이 코드의 미묘한 빈틈 3가지

1. **`"PROCESSING"`/`"DONE"` 값이 사실 안 읽힌다.** 이 코드는 `setIfAbsent` 의 *존재 여부*만으로 중복을 판단할 뿐, 저장된 값을 다시 `GET` 해서 분기하지 않는다. 그래서 `"PROCESSING"` 이든 `"DONE"` 이든 기능상 차이가 없다 — 값은 사실상 장식. *제대로 된 멱등성*은 상태를 **읽어서** "처리 중이면 409 + `Retry-After`, 완료면 첫 응답을 그대로 재생(replay)" 으로 분기한다. (풀 상태머신 버전은 `부록-멱등성.md` 참고)

2. **실패 시 `delete` 의 양면성.** `catch` 에서 키를 지워 재시도를 허용하는 건 맞다. 하지만 첫 처리가 **PROCESSING 동안 도착한 중복**은 무시됐는데, 그 직후 첫 처리가 실패해 키를 지우면 그 중복분의 작업도 사라진다 — 다행히 PG가 at-least-once로 *또* 재시도하니 결국 처리되지만, "무시 → 실패 → 키 삭제 → 다음 재시도"의 타이밍을 이해하고 있어야 한다.

3. **`processPayment` 자체가 멱등이면 더 안전.** Redis 키는 *보조* 방어다. Redis가 죽거나 키가 evict되면 뚫린다. 그래서 결제처럼 틀리면 안 되는 건 *DB 레벨에서도* `payment_tx(tx_id UNIQUE)` 제약을 두는 다층 방어가 표준(→ 시나리오 3과 같은 "Redis=효율, DB=정합성" 원칙).

## 🪤 함정 한 줄

> **처리 실패 시 멱등성 키를 안 지우면 영구 차단**. 재시도가 영영 막힘. (단 Redis 키는 보조 방어 — 결제 정합성의 최종 보루는 DB의 `tx_id UNIQUE`)

# 🎬 시나리오 5. 새벽 3시 DB 부하 폭증 — 캐시 스탬피드

## 📋 상황

매일 새벽 3시 정각에 DB CPU가 80%로 튀어오른다. 사용자 트래픽은 새벽인데도 왜?

조사해보니 인기 콘서트 목록 캐시 `cache:concerts:popular` 의 TTL이 정확히 1시간이라, **자정·1시·2시·3시 정각마다 동시 만료** 되고 있다. 만료 직후 수천 개 요청이 한꺼번에 DB로 몰려서 같은 쿼리를 동시에 수천 번 때린다.

## ❓ 질문

이 "캐시 스탬피드(Cache Stampede)" 어떻게 막을래?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안 (3가지 접근, 조합 가능)

### 1. TTL Jitter (가장 간단, 즉시 적용 가능)

```java
int baseSec = 3600;
int jitter = ThreadLocalRandom.current().nextInt(300);   // 0~5분 랜덤
redisTemplate.opsForValue().set(key, json, baseSec + jitter, TimeUnit.SECONDS);
```

→ 모든 키의 만료 시점이 흩어짐. 정각 폭주 사라짐.

### 2. 분산락으로 "DB 조회는 한 명만"

```java
String cached = redis.get(key);
if (cached != null) return cached;

String lockKey = "lock:cache:" + key;
Boolean ok = redis.setIfAbsent(lockKey, "1", 5, TimeUnit.SECONDS);
if (ok) {
    try {
        String data = queryDB();   // 나만 DB 호출
        redis.set(key, data, 1, TimeUnit.HOURS);
        return data;
    } finally { redis.delete(lockKey); }
} else {
    Thread.sleep(50);
    return redis.get(key);   // 다른 사람이 채워준 캐시 읽기
}
```

→ 캐시 미스 시 DB 호출이 1번만 일어나도록 강제.

### 3. PER (Probabilistic Early Recomputation)

만료 직전(예: TTL의 90%)부터 일부 요청이 미리 재계산. 만료 시점에 캐시가 이미 갱신돼 있도록.

→ 구현 복잡. Caffeine 같은 라이브러리가 이 패턴 지원.

### 💡 한 걸음 더 — 왜 "동시 만료"가 재앙이고, 각 해법의 본질은?

스탬피드의 본질은 **"캐시 미스의 동기화"**다. TTL이 정각으로 같으면 수천 요청이 *같은 순간* 미스 → *같은 쿼리* 를 동시에 DB로 쏜다. 미스 1건이 아니라 미스 수천 건이 한꺼번에 — 이걸 **thundering herd** 라고도 부른다. 평소엔 캐시가 막아주던 부하가 만료 순간 한 점에 응축돼 터지는 것.

- **Jitter** = 미스 *시점을 흩뜨려서* 동기화를 깬다. 가장 싸지만 **단일 초인기 키**(예: 메인 배너 1개)는 못 막는다 — 그 키 하나가 만료되는 순간은 여전히 한 점이라 거기에 몰린다.
- **분산락** = 미스가 나도 *DB 조회는 1명만* 하도록 직렬화. 단일 인기 키에 효과적. 단, 코드의 `Thread.sleep(50)` **한 번**은 DB가 50ms 안에 안 끝나면 `null` 을 반환한다 — 실무는 **재시도 루프 + 타임아웃 fallback** 또는 Redisson의 pub/sub 대기를 쓴다(→ 시나리오 7과 같은 "sleep 한 번의 함정").
- **PER** = 만료를 기다리지 않고 *만료 직전에 확률적으로 미리* 갱신. 대표 수식(XFetch)은 `now - delta*beta*ln(rand()) >= expiry` — `delta`(재계산 소요시간)가 크거나·TTL 끝에 가까울수록 미리 갱신할 확률이 오른다. 만료 자체가 없어 미스가 안 생긴다.

→ 실무 조합: **Jitter 기본 + 초인기 키엔 분산락(Redisson)**. PER은 재계산 비용이 큰 소수 키에 선택적으로.

## 🪤 함정 한 줄

> **인기 캐시일수록 TTL에 무작위 jitter 필수**. 정확한 1시간 TTL이 미덕이라는 환상을 버려라.

</details>

# 🎬 시나리오 6. 큐 컨슈머가 같은 이메일을 2번 보냈어요

## 📋 상황

`queue-server`의 `EmailMultiWorker`가 같은 이메일을 두 번 보낸 사용자가 보고됐다. 로그를 보니 워커 스레드 두 개가 같은 메시지를 처리했다.

원인: 디스패처가 `rightPop`으로 꺼낸 메시지를 워커에게 넘기는 사이에 워커가 실패→재큐잉→다시 처리됐다. 또는 워커가 처리 도중 죽고 다른 워커가 같은 작업을 잡았다.

큐 시스템의 본질: **at-least-once 전달** — 적어도 1번은 보장하지만 2번 이상도 가능.

## ❓ 질문

컨슈머 레벨에서 **"정확히 1번만 처리"** 보장하려면?

---

<summary>💭 펼치기</summary>

## 💡 답안 — dedup 키 (멱등성 키와 같은 발상)

**Step 1**: 메시지에 UUID 박기 (프로듀서 측, `AuthService.java:85`)
```java
String messageId = UUID.randomUUID().toString();
redisTemplate.opsForList().leftPush("mail:queue",
    new EmailMessage(messageId, email));
```

**Step 2**: 컨슈머에서 dedup
```java
public void processEmail(EmailMessage msg) {
    String dedupKey = "dedup:email:" + msg.getMessageId();

    Boolean isFirst = redisTemplate.opsForValue()
        .setIfAbsent(dedupKey, "1", 1, TimeUnit.DAYS);

    if (!Boolean.TRUE.equals(isFirst)) {
        log.info("Skip duplicate message: {}", msg.getMessageId());
        return;
    }

    try {
        sendEmail(msg.getEmail());
        emailLogRepository.save(...);
    } catch (Exception e) {
        redisTemplate.delete(dedupKey);   // ★ 실패 시 키 회수 → 재시도 허용
        throw e;
    }
}
```

**왜 1일 TTL?**: 큐 재시도가 그렇게 늦게 도착하는 경우는 거의 없지만, 안전 마진. 메모리 부담은 작음.

### 💡 한 걸음 더 — `try/catch` 가 핵심인 이유 (놓치기 쉬운 버그)

위 코드의 `try/catch` 가 없으면 — 즉 `setIfAbsent` 성공 직후 `sendEmail()` 을 부르고 **실패해도 키를 안 지우면** — dedup 키는 그대로 남는다. 그러면 메시지가 재큐잉돼 재시도돼도 `setIfAbsent` 가 `false` → **영원히 스킵 → 이메일이 아예 안 나간다.** at-least-once 큐를 쓰는 의미가 무색해지고, 사실상 **at-most-once(유실 가능)** 로 바뀐다. "멱등성을 넣었더니 메일이 사라진다"는 전형적 함정.

여기엔 **피할 수 없는 트레이드오프**가 있다 — dedup 키를 *언제* 박느냐에 따라 크래시 시 결과가 갈린다:

| 전략 | dedup 시점 | 프로세스 크래시 시 결과 |
|---|---|---|
| **보내기 전 set + 실패 시 삭제** (위 코드) | 처리 전 선점 | send 후 save 전에 죽으면: 메일은 나갔는데 키는 남음 → 재시도 시 스킵(중복은 막되 로그만 유실) |
| 보내기 전 set + **실패해도 미삭제** | 처리 전 선점 | send 실패 시 메일 **영구 유실** ← 위험 |
| **보낸 후 set** | 성공 후 기록 | send 직후 죽으면 키 없음 → 재시도 시 **중복 발송** |

→ 도메인이 정한다: "절대 누락 불가"(결제 영수증·OTP)면 **보낸 후 set + 약간의 중복 감수**가, "중복 절대 불가"(쿠폰 1회 지급)면 **보내기 전 set + 작업 자체를 멱등하게**가 맞다. 이메일은 보통 *중복보다 누락이 더 나쁘다*고 보고 **실패 시 삭제(위 코드)** 또는 보낸 후 set을 택한다. 즉 "exactly-once"는 환상이고, **at-least-once(중복 감수) ↔ at-most-once(유실 감수)** 중 무엇이 덜 치명적이냐를 고르는 문제다.

## 🪤 함정 한 줄

> **at-least-once 큐 = 컨슈머 측 멱등성이 의무.** 단, dedup 키를 "처리 전"에 박고 실패 시 안 지우면 멱등성이 *유실*로 둔갑한다 — `try/catch` 로 실패 시 키를 회수하거나 "보낸 후 기록" 중 도메인에 맞는 쪽을 택하라.

</details>

## 💡 답안

### (a) TTL 늘리기의 함정

TTL을 30초로 늘리면? → 평소 1초 작업도 30초 동안 락 점유. 동시성 망함.

- ❌ 못 막는 것: **TTL 만료 후 다른 클라이언트가 락을 잡아서 같은 자원에 동시 접근하는 것**

→ owner 검증은 "락 해제 안전성"만 보장. "임계 영역 안전성"은 보장 못 함.

### 진짜 해법

#### 1. 락 안에서 외부 API 호출하지 않기 (구조 변경)

```
[Before] 락 획득 → DB 조회 → 외부 결제 → DB 저장 → 락 해제
[After]  락 획득 → DB 좌석만 점유 → 락 해제 → 외부 결제 → DB 결제 결과 반영
```

→ 락 점유 시간을 가장 짧게.

#### 2. Redisson의 watchdog

Redisson `RLock`은 락 잡은 클라이언트가 살아있는 동안 **TTL을 백그라운드에서 자동 연장**.

```java
RLock lock = redisson.getLock("lock:seat:1:A1");
lock.lock(10, TimeUnit.SECONDS);   // 기본 watchdog 켜짐
try { /* 시간이 30초여도 락 유지됨 */ }
finally { lock.unlock(); }
```

→ 작업이 30초 걸려도 클라이언트가 살아있으면 락 유지. 클라이언트 죽으면 watchdog도 죽으니 자연스럽게 만료.

### 💡 한 걸음 더 — 이게 바로 Kleppmann이 지적한 그 문제

여기서 벌어진 일("작업 중 TTL 만료 → 다른 클라이언트가 락 획득 → 동시 진입")은 단순 설정 실수가 아니라 **분산락의 근본 한계**다. 외부 API뿐 아니라 **GC stop-the-world, 스레드 스케줄링 지연, 네트워크 지연** 어느 것이든 "내가 락을 쥐었다고 믿는 사이 TTL이 만료"되는 창을 만든다 — 이걸 *process pause* 문제라고 부른다.

- **owner 검증(Lua)** 이 막는 건 "남의 락을 *지우는*" 사고뿐. "남이 락을 쥔 채 내가 임계영역에 *들어가는*" 건 못 막는다. (**해제 안전성 ≠ 상호배제**)
- **watchdog** 은 "내가 *살아있는 동안*" TTL을 늘려 이 창을 줄이지만, 내가 *멈춘(GC pause) 동안* 엔 watchdog도 멈춰 갱신을 못 하므로 **완벽한 보장은 아니다.**
- 진짜 정확성을 원하면 Kleppmann은 **fencing token**(단조 증가하는 번호를 락과 함께 발급, 보호 자원이 더 낮은 번호의 쓰기를 거부)을 제안한다. Redis 단독으론 어려워 실무는 **owner 검증 + DB 제약(낙관락/유니크)** 으로 대체한다(→ 시나리오 3).

→ 결론: *분산락은 "대부분의 경우 동시 작업을 막는 효율 장치"이지 "정확성 보장 장치"가 아니다.* 돈·재고처럼 틀리면 안 되는 건 DB 제약을 최종 방어로. (03-면접질문 Q33)

## 🪤 함정 한 줄

> **분산락 TTL은 "정답이 없는 추측" — Redisson watchdog 또는 짧은 락 + 구조 분리가 정석.** 그리고 watchdog조차 process pause엔 못 버티니, 정확성은 DB 제약으로 마무리.

</details>

뭐가 의심되는가? 어떻게 조사할래?

## 💡 답안

### 의심 시나리오

1. **`auth:*` 키 12,847개 + 3분 TTL** = 분당 4000개 발급?
   → SMS 비용도 같이 폭증했을 것. 봇 공격 의심.
   → **`auth:*` 중 TTL이 -1인 키가 있는지 확인** (시나리오 2처럼 누군가 옵션 없이 SET 호출했을 수도).

2. **`cache:concert:1` 이 142 KB**
   → 콘서트 1개 캐시가 142 KB? big key. 메모리 압박 + 조회 시 네트워크 부담.
   → 구조 분해 (HASH로 필드별 분리) 또는 압축 필요.

### 조사 명령어

```bash
# TTL -1 키 찾기 (메모리 누수 원인 1순위)
> SCAN 0 MATCH auth:* COUNT 100
# 반환된 각 키에 대해
> TTL auth:xxx
# -1 나오면 메모리 누수 의심

# 키별 메모리 사용량
> MEMORY USAGE cache:concert:1

# 전체 메모리 통계
> INFO memory
```

### 조치

1. **TTL -1 키들 식별 → 코드의 SET 호출에서 TTL 누락한 곳 찾아 수정**
2. **big key는 UNLINK로 비동기 삭제** (DEL은 블로킹)
3. **maxmemory-policy 설정 확인** — `allkeys-lru` 같은 eviction 정책이 켜져 있어야 비상 시 자동 회수

### 💡 한 걸음 더 — `--bigkeys` 와 카운트를 어떻게 읽나

- **`--bigkeys` 는 "타입별 최대 키 1개씩"만 샘플링**한다(전수조사 아님, 내부적으로 SCAN 기반이라 운영 중에도 안전). `cache:concert:1 = 142 KB` 가 떴다는 건 *그 타입에서 제일 큰 게 이것* 이란 뜻 — String 142KB는 그 자체로도 문제(조회마다 142KB 네트워크 왕복)지만, "비슷한 게 213개 더 있다(`cache:concert:* = 214개`)"는 신호일 수 있다. 그러면 그게 메모리의 주범.
- **누수 vs 정상 증가 구분이 진짜 진단의 핵심**: 메모리 우상향이 *가입자 증가에 비례*하면 정상, *TTL 있어야 할 키가 -1로 쌓이는* 거면 누수. 그래서 1순위 조사가 `auth:*` 의 TTL 점검이다(→ 시나리오 2와 동일 뿌리). `auth:*` 12,847개가 전부 3분 TTL이면 곧 사라질 정상치지만, 그중 `-1` 이 섞여 있으면 그게 범인.
- **big key 분해**: 142KB가 콘서트 1개 전체 JSON이면, 자주 바뀌는 필드(잔여석)와 거의 안 바뀌는 필드(공연 정보)를 나누거나 Hash로 쪼개 *필요한 필드만* 조회(→ 03-면접질문 Q7: String 통짜 vs Hash).
- **삭제는 `UNLINK`**: 142KB는 작지만, 수백만 원소 컬렉션이면 `DEL` 은 단일 스레드를 수 초 블로킹(→ 시나리오 10과 같은 원리). 운영 정석은 `UNLINK`.

## 🪤 함정 한 줄

> **메모리 누수의 99%는 "TTL을 줘야 할 키에 안 준 것"**. SET에 EX 빠진 곳을 찾아라.

# 🎬 시나리오 9. "5회 틀리면 잠금" 어떻게 만들죠

## 📋 상황

PM 요구사항: "사용자가 비밀번호를 5회 연속 틀리면 30분간 로그인 잠금. 분산 환경이고, 정확히 5회여야 함."

DB로 `failed_attempts` 컬럼? → 매 로그인 시도마다 UPDATE → 락 경합. 게다가 30분 후 자동 해제도 별도 스케줄러 필요.

## ❓ 질문

Redis로 어떻게 짤래?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

```java
public void login(String email, String password) {
    String lockKey = "login:lock:" + email;
    String attemptKey = "login:attempts:" + email;

    // 1. 잠금 상태 확인
    if (Boolean.TRUE.equals(redisTemplate.hasKey(lockKey))) {
        Long ttl = redisTemplate.getExpire(lockKey, TimeUnit.SECONDS);
        throw new AccountLockedException(ttl);
    }

    // 2. 비번 검증
    if (!verifyPassword(email, password)) {
        Long count = redisTemplate.opsForValue().increment(attemptKey);
        if (count == 1) redisTemplate.expire(attemptKey, 30, TimeUnit.MINUTES);

        if (count >= 5) {
            redisTemplate.opsForValue().set(lockKey, "1", 30, TimeUnit.MINUTES);
            redisTemplate.delete(attemptKey);
            throw new AccountLockedException(1800L);
        }
        throw new InvalidPasswordException(5 - count);
    }

    // 3. 성공 시 카운터 초기화
    redisTemplate.delete(attemptKey);
}
```

**키 설계 핵심**:
- `login:attempts:{email}` — 실패 카운터, TTL 30분 (그 안에 안 틀리면 자동 리셋)
- `login:lock:{email}` — 잠금 플래그, TTL 30분 (자동 해제)
- 둘 다 TTL 기반 → **별도 스케줄러 불필요**

### 더 안전하게 (Lua)

INCR과 잠금 처리를 분리하면 동시 요청 시 6번째 시도가 잠금 직후 들어올 수 있음. Lua로 묶기:

```lua
local attempts = redis.call('INCR', KEYS[1])
if attempts == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
if tonumber(attempts) >= tonumber(ARGV[2]) then
    redis.call('SET', KEYS[2], '1', 'EX', ARGV[3])
    redis.call('DEL', KEYS[1])
    return 'LOCKED'
end
return attempts
```

### 💡 한 걸음 더 — "이메일로 잠그면" 생기는 보안 함정

이 설계엔 잘 알려진 약점이 있다: **계정 잠금 자체가 공격 도구(account-lockout DoS)가 된다.** 공격자가 피해자 이메일로 일부러 5번 틀리면, 피해자는 비밀번호를 알아도 30분간 로그인 불가. 대량으로 돌리면 서비스 마비. 즉 "정확히 5회 잠금"은 PM 요구사항을 만족하지만, 그 잠금 메커니즘이 곧 무기가 된다.

실무 완화책:
- **잠금 키를 `email` 단독이 아니라 `email + IP`(또는 디바이스 핑거프린트)로** — 공격자 IP만 잠기고 피해자 본인은 정상 로그인.
- **하드 잠금 대신 점증 지연(exponential backoff)** — 1·2·4·8초… 틀릴수록 느리게. 정상 사용자 영향 최소, 봇엔 비용 부과.
- **N회 후 CAPTCHA** — 잠그는 대신 사람 검증. 자동화만 차단.
- **잠겼을 때 사용자에게 알림** — "비정상 로그인 시도 감지" 메일로 본인이 인지·대응.

→ *시니어는 "그 잠금이 악용되면?"* 까지 본다. 보통 **IP 결합 + backoff + 알림** 조합이 단순 email 하드 잠금보다 안전하다. (구현은 위 Redis 패턴 그대로, 키만 `login:lock:{email}:{ip}` 로 바꾸면 시작점)

## 🪤 함정 한 줄

> **"실패 카운터"는 TTL이 본체다.** TTL 없이 카운트만 올리면 영구히 누적되어 모든 사용자가 결국 잠긴다. 그리고 **email 단독 잠금은 DoS 도구가 된다 — IP 결합/backoff로 완화.**

</details>

# 🎬 시나리오 10. KEYS 한 번 쳤다가 운영 멈춤

## 📋 상황

신입 개발자가 운영 Redis에 접속해서 디버깅 중이었다.

```
prod-redis:6379> KEYS user:*
```

그 순간부터 약 8초 동안 Redis가 응답하지 않았다. api-server의 모든 요청이 타임아웃. 알람 폭발. 신입은 패닉.

원인: Redis는 단일 스레드. `KEYS *` 같은 명령이 들어오면 그동안 다른 모든 명령이 대기. 키가 천만 개 있으면 8초든 30초든 걸린다.

## ❓ 질문

(a) 지금 당장 어떻게 복구? (b) 같은 일이 다시 일어나지 않게 하려면?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

### (a) 지금 당장

- KEYS 실행 중인 클라이언트가 끝날 때까지 기다리는 것 외엔 방법 없음 (이미 진입한 명령은 중단 불가에 가까움).
- **KILL** 명령으로 클라이언트 강제 종료 가능하지만 KEYS 실행 자체를 중간에 끊지는 못함.
- 교훈: **운영에서 KEYS는 한 번이라도 치면 끝.**

### (b) 재발 방지

#### 1. KEYS / FLUSHALL / FLUSHDB 명령 비활성화

`redis.conf`:
```
rename-command KEYS ""
rename-command FLUSHALL ""
rename-command FLUSHDB ""
rename-command CONFIG ""
```

→ 명령 자체를 사용 불가로 만듦. 신입이든 누구든 절대 못 침.

#### 2. ACL로 권한 분리 (Redis 6+)

```
ACL SETUSER devops on >password ~* +@all -keys -flushall -flushdb
ACL SETUSER app    on >password ~user:* +get +set +del +expire
```

→ 애플리케이션 계정엔 KEYS 권한 자체를 안 줌.

#### 3. 진짜 키 검색이 필요하면

```bash
# SCAN을 항상 사용 (블로킹 없음, 점진적)
> SCAN 0 MATCH user:* COUNT 100
# 또는 redis-cli 헬퍼
$ redis-cli --scan --pattern 'user:*'
```

### 💡 한 걸음 더 — 왜 KEYS 하나가 전체를 멈추나 & SCAN의 원리

- **단일 스레드라서**: Redis는 명령을 한 줄로 직렬 실행한다(→ 03-면접질문 Q17~18). `KEYS *` 는 *전체 키스페이스를 한 명령 안에서* 훑으므로, 그 수 초~수십 초 동안 **뒤에 줄 선 모든 GET/SET이 대기**한다. CPU가 노는 게 아니라 *한 명령이 스레드를 통째로 점유*하는 것. 그래서 "조심히 쓰면 된다"가 성립 안 한다 — 한 번이면 끝.
- **`CLIENT KILL` 로도 못 끊는 이유**: 이미 실행에 들어간 명령은 중간 양보 지점이 없다. 연결을 끊어도 서버 스레드는 그 KEYS를 끝까지 돈다.
- **SCAN이 안전한 원리**: 커서를 돌려주는 **점진적(incremental)** 명령이다. `SCAN 0` → 일부 키 + 다음 커서 반환, 다음 호출에서 이어감. 한 번에 조금씩만 보므로 다른 명령이 사이사이 끼어든다. `COUNT 100` 은 "한 번에 대략 이만큼 보라"는 *힌트*(보장 아님). 단점: 스캔 도중 변경된 키는 누락/중복될 수 있어 **약한 일관성** — 그래서 정확한 집합이 필요하면 SCAN이 아니라 **인덱스(Set)** 를 따로 유지하는 게 정석(→ 03-면접질문 Q14).
- **`redis-cli --scan`** 은 내부적으로 SCAN을 반복 호출해주는 래퍼라 운영에서도 안전.

## 🪤 함정 한 줄

> **운영 Redis에 KEYS, FLUSHALL은 비활성화가 정답.** "조심해서 쓴다"는 약속은 깨진다.

</details>
