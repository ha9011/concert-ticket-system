# List 실무 — 7대 핵심 패턴 + 이 프로젝트 적용 가이드

> 명령어를 안다 ≠ 실무에서 쓸 줄 안다. 이 문서는 **"실제 서비스가 마주치는 문제 → Redis List로 어떻게 해결하는가"**에 집중.
> 모든 예제는 이 프로젝트(`concert-ticket-system/backend`)의 실제 코드와 엮음.
> 특히 이 프로젝트의 **이메일 큐**(`mail:queue`)가 List의 거의 모든 패턴을 관통하는 살아있는 교재다.

## 다루는 7가지

1. **메시지 큐 (FIFO)** — LPUSH + BRPOP. 이 프로젝트 `mail:queue` 직결
2. **Reliable Queue (신뢰성 큐)** ⭐ 가장 중요 — 메시지 유실 0%로 만들기 (LMOVE/processing 백업)
3. **DLQ (Dead Letter Queue)** — 재시도 초과 메시지 격리 + 멱등성
4. **최근 N개 (Capped List)** — LPUSH + LTRIM, 메모리 자동 제한
5. **피드 타임라인 (Fan-out on write)** — LPUSH feed + LTRIM
6. **우선순위 큐 / 다중 큐** — BRPOP 여러 키
7. **배치 소비** — LPOP count / LRANGE+LTRIM으로 한 번에 N개

> 📌 List 명령어 자체의 동작(LPUSH/RPUSH/LPOP/LRANGE/LREM/LTRIM/LMOVE/BRPOP …)이 가물가물하면
> 먼저 [`01-실습.md`](01-실습.md) / [`01-요약.md`](01-요약.md)를 빠르게 훑고 오자. 이 문서는 "그걸 어디에 쓰는가"에 집중한다.

# §0. 왜 이 프로젝트에 List를 깔고 가야 하나

이 프로젝트는 이미 List를 **메시지 큐**로 쓰고 있다. 두 줄이 핵심이다.

```java
// [Producer] api-server — AuthService.java:85
// 회원가입 성공 → 환영 메일을 큐에 적재
redisTemplate.opsForList().leftPush(MAIL_QUEUE, request.getEmail());   // = LPUSH mail:queue {email}

// [Consumer] queue-server — EmailMultiWorker.java:44
// 디스패처 스레드가 큐에서 블로킹으로 꺼냄
String email = redisTemplate.opsForList().rightPop(MAIL_QUEUE, Duration.ofSeconds(10)); // = BRPOP mail:queue 10
```

```
api-server (Producer)              Redis List "mail:queue"           queue-server (Consumer)
─────────────────────              ───────────────────────           ───────────────────────
LPUSH mail:queue "a@x.com"  ──▶   head [ c, b, a ] tail        ◀──   BRPOP mail:queue 10
   (왼쪽으로 밀어넣음)               왼쪽 push / 오른쪽 pop              (오른쪽에서 꺼냄)
```

## LPUSH(왼쪽) + BRPOP(오른쪽) = FIFO 보장

가장 먼저 들어온 `a`가 가장 먼저 나간다. 왜 그런지 한 번 직접 따라가 보자.

```
LPUSH mail:queue a   →  [a]
LPUSH mail:queue b   →  [b, a]        (b가 head 쪽에 꽂힘)
LPUSH mail:queue c   →  [c, b, a]
                                       ┌ head            tail ┐
BRPOP mail:queue     →  a 반환,  [c, b]   ← tail(오른쪽)에서 a가 먼저 나감 = 먼저 들어온 게 먼저 = FIFO
BRPOP mail:queue     →  b 반환,  [c]
BRPOP mail:queue     →  c 반환,  []      ← 비면 키 자체가 사라짐 (EXISTS=0)
```

> **반대 조합도 FIFO다.** RPUSH(오른쪽 push) + LPOP(왼쪽 pop)도 FIFO.
> 한 쪽으로 넣고 **반대쪽**으로 빼면 FIFO, **같은 쪽**으로 넣고 빼면 LIFO(스택).
> 이 프로젝트는 "왼쪽 push / 오른쪽 pop"을 골랐을 뿐, 본질은 "넣는 쪽과 빼는 쪽이 반대"라는 것.

| 넣기 | 빼기 | 결과 | 쓰임 |
|---|---|---|---|
| LPUSH | RPOP / BRPOP | **FIFO** (이 프로젝트) | 작업 큐, 메시지 큐 |
| RPUSH | LPOP / BLPOP | FIFO | 작업 큐 (방향만 거울) |
| LPUSH | LPOP | LIFO (스택) | 최근 것 먼저 처리 |

이제 이 큐를 가지고 실무가 마주치는 7가지 문제를 푼다.

# §1. 메시지 큐 (FIFO) — 폴링 vs 블로킹

## 문제 상황

```
회원가입이 몰리는 콘서트 오픈 직전, 1초에 환영 메일 수백 통이 쌓인다.
api-server는 메일을 직접 보내면 응답이 느려진다(SMTP 왕복 + 재시도).
→ "일단 큐에 던지고(빠른 응답), 메일 발송은 뒤에서 천천히" = 비동기 처리.
```

이게 이 프로젝트의 구조다. `AuthService`는 큐에 넣고 즉시 200을 반환, `queue-server`가 뒤에서 처리.
질문은 하나: **컨슈머는 큐를 어떻게 "기다릴" 것인가?**

## 표준 패턴 — 왜 폴링이 아니라 블로킹인가

### ❌ 안티패턴: 폴링 루프 (RPOP을 계속 호출)

```java
while (running) {
    String email = redisTemplate.opsForList().rightPop(MAIL_QUEUE);  // = RPOP (non-blocking)
    if (email != null) {
        process(email);
    } else {
        Thread.sleep(100);   // 큐 비었으면 100ms 쉬고 다시 시도
    }
}
```

문제:
- 큐가 비어 있어도 **100ms마다 Redis를 두드림** → CPU·네트워크 낭비 (busy-wait)
- `sleep(100)` 때문에 메시지가 들어와도 **최대 100ms 지연** 후에야 처리 (지연 ↔ 부하 트레이드오프)
- sleep을 줄이면 지연은 줄지만 헛조회가 폭증

### ✅ 표준: 블로킹 팝 (BRPOP) — 이 프로젝트가 쓰는 방식

```java
// EmailMultiWorker.java:44
String email = redisTemplate.opsForList().rightPop(MAIL_QUEUE, Duration.ofSeconds(10)); // = BRPOP mail:queue 10
```

`Duration`을 넘기면 RedisTemplate이 **블로킹** 버전(BRPOP)을 쓴다.

- 큐에 값이 있으면 **즉시** 반환 (지연 0)
- 비어 있으면 **최대 10초까지 Redis 커넥션 위에서 잠듦** → 헛조회 없음
- 값이 들어오는 순간 Redis가 깨워줌 (서버가 푸시해주는 느낌)
- 10초 동안 아무것도 안 오면 `null` 반환 → 루프 한 바퀴 돌고(인터럽트 체크) 다시 BRPOP

> **왜 10초인가? (무한 대기 timeout=0 안 쓰는 이유)**
> BRPOP은 `timeout 0`이면 무한 대기다. 무한 대기는 편하지만:
> - 스레드를 **깔끔하게 종료**할 수 없다(인터럽트/셧다운 플래그를 영영 못 본다).
> - 커넥션을 한 개 무한 점유.
> 10초 타임아웃을 두면 최소 10초마다 루프 상단으로 돌아와 `Thread.currentThread().isInterrupted()`를
> 확인할 기회가 생긴다 → **graceful shutdown 가능**. 실무에서 블로킹 큐 워커는 거의 항상 유한 타임아웃을 준다.

### 폴링 vs 블로킹 정리

| 항목 | 폴링 (RPOP loop) | 블로킹 (BRPOP) |
|---|---|---|
| 빈 큐일 때 부하 | 높음 (계속 조회) | 거의 없음 (잠듦) |
| 메시지 도착 후 지연 | sleep 간격만큼 | 거의 0 |
| 커넥션 점유 | 짧게 자주 | timeout 동안 1개 점유 |
| 셧다운 | 쉬움 | timeout 유한해야 가능 |
| 결론 | ❌ 특별한 이유 없으면 X | ✅ 메시지 큐 표준 |

## 디스패처 + 워커풀 구조 (이 프로젝트의 선택)

`EmailMultiWorker`는 그냥 BRPOP만 도는 게 아니라 **디스패처 1 + 워커풀 3** 패턴이다.

```java
// EmailMultiWorker — 핵심만
private final ExecutorService dispatcher  = Executors.newSingleThreadExecutor();  // 큐에서 꺼내는 1명
private final ExecutorService workerPool  = Executors.newFixedThreadPool(3);       // 실제 처리 3명

private void dispatch() {
    while (!Thread.currentThread().isInterrupted()) {
        String email = redisTemplate.opsForList().rightPop(MAIL_QUEUE, Duration.ofSeconds(10)); // BRPOP
        if (email != null) {
            workerPool.submit(() -> processEmail(email));   // 꺼내자마자 워커에게 넘기고, 디스패처는 다음 BRPOP
        }
    }
}
```

**왜 이렇게 나눴나?**
- 메일 발송 한 건이 5초 걸린다(`processEmail`의 `sleep(5)`). 디스패처가 직접 처리하면 5초 동안 다음 메시지를 못 꺼낸다.
- 디스패처는 "꺼내서 넘기기"만 빠르게, 무거운 처리는 워커 3명이 **동시에**. → 처리량 3배.

**왜 BRPOP을 디스패처 1명만 하나? (워커 3명이 각자 BRPOP 하면 안 되나?)**
- 워커가 각자 BRPOP을 해도 동작은 한다. Redis는 BRPOP 대기자가 여럿이면 **한 명에게만** 값을 준다(원자적).
- 다만 "꺼내기"와 "처리"를 분리해두면 워커풀 크기/백프레셔/큐잉 정책을 한 곳(디스패처)에서 통제하기 쉽다. 설계 취향.

### ⚠️ 디스패처+워커풀의 숨은 함정: unbounded submit

```java
workerPool.submit(() -> processEmail(email));   // 워커가 다 바빠도 일단 큐에 쌓임
```

`Executors.newFixedThreadPool(3)`는 내부적으로 **무한 크기 LinkedBlockingQueue**를 쓴다.
워커 3명이 전부 5초짜리 작업 중이면, 디스패처가 BRPOP으로 꺼낸 메시지들이 **JVM 힙 안의 큐에 무제한으로 쌓인다**.

```
Redis mail:queue 에는 메시지가 줄어드는데(이미 BRPOP으로 꺼냄),
JVM 안 workerPool 큐에는 무한정 쌓임 → 이 순간 서버가 죽으면 그 메시지들 전부 증발.
```

→ 이게 §2 신뢰성 문제와 직결된다. **"꺼냈지만 아직 처리 안 한" 메시지가 Redis 밖(JVM 힙)에 떠 있는 구간**이 바로 유실 구간.
→ 실무에선 워커풀 큐를 유한 크기로 두고 `CallerRunsPolicy`(디스패처가 직접 처리=백프레셔) 등을 건다.

## 흔한 함정 표

| 함정 | 결과 | 해법 |
|---|---|---|
| 폴링 + `sleep` 으로 큐 감시 | CPU/네트워크 낭비, 지연 발생 | BRPOP(블로킹 팝) 사용 |
| `BRPOP timeout 0`(무한 대기) | 스레드 종료 불가, 커넥션 무한 점유 | 유한 타임아웃(예: 10초)으로 인터럽트 체크 기회 확보 |
| LPUSH/LPOP 같은 쪽으로 넣고 뺌 | FIFO인 줄 알았는데 LIFO(역순 처리) | 넣는 쪽과 빼는 쪽을 **반대로** |
| `LPUSH key a b c` 로 여러 개 한 번에 | 리스트가 `[c,b,a]` 역순으로 들어감 | 순서 중요하면 RPUSH로 넣거나 하나씩 |
| 블로킹 명령을 MULTI/EXEC·Lua 안에서 | 블로킹 안 되고 **즉시** 동작(빈 큐면 nil) | 트랜잭션/스크립트 밖에서 BRPOP |
| 워커풀 `submit` 무제한 | 처리 못한 메시지가 힙에 쌓임 → 죽으면 유실 | 유한 큐 + 백프레셔(CallerRunsPolicy 등) |

## 🎯 이 프로젝트 적용 포인트

- 이미 **잘 하고 있는 것**: BRPOP(`rightPop` + Duration) 사용, 디스패처/워커 분리, LPUSH+BRPOP FIFO. → 기본기는 OK.
- **다음 단계로 가야 할 것**: 위 "unbounded submit" 함정 + 아래 §2의 **유실 문제**. 지금 구조는 "한 건도 잃으면 안 되는" 메시지엔 부족하다. 환영 메일이야 한 통 빠져도 괜찮지만, 이 패턴을 **결제 완료 알림·정산 트리거**에 쓰는 순간 유실은 사고가 된다.

# §2. Reliable Queue (신뢰성 큐) ⭐ 이 문서의 핵심

## 문제 상황 — "꺼내는 순간 사라진다"

이 프로젝트의 가장 중요한 실무 결함이다. `EmailWorker.java:72`의 주석이 이미 자백하고 있다.

```java
} catch (Exception e) {
    log.error("이메일 발송 실패: {}", email, e);
    // 실패 시 다시 큐에 넣거나(DLQ), 별도 처리가 필요함   ← 바로 이 줄
}
```

무슨 일이 벌어지나:

```
1. BRPOP mail:queue   → "a@x.com" 반환    이 순간 Redis에서 "a@x.com"은 영구히 사라짐.
2. processEmail("a@x.com")  실행 중...
3. 💥 이 순간 서버가 죽음 (OOM, 배포 재시작, k8s가 파드 강제 종료, DB save 예외 …)
4. 재시작 → mail:queue 에는 "a@x.com"이 없음. 아무도 모름.
   → 그 사용자는 영원히 환영 메일을 못 받는다. (메시지 영구 유실)
```

원인은 단순하다. **BRPOP은 "꺼내기"와 "삭제"를 한 번에 한다.** 꺼내는 순간 Redis에는 흔적이 없다.
"내가 이 메시지를 처리 중"이라는 상태가 **Redis 어디에도 기록되지 않는다.**
처리 성공/실패를 컨슈머가 Redis에 되돌려주는 **ack(확인 응답) 개념이 List에는 없다.**

이걸 **at-most-once**(최대 한 번 — 유실 가능, 중복 없음) 전달이라 부른다.

## 표준 패턴 — processing 백업 리스트 + 원자 이동

핵심 아이디어: **꺼내면서 동시에 "처리 중" 리스트에 백업을 남긴다.** 그 둘을 **원자적으로** 한다.

```
main 큐                processing 큐 (백업)         완료
──────                 ───────────────────         ────
[c,b,a]
  │  BLMOVE main processing RIGHT LEFT  (a를 원자적으로 옮김)
  ▼
[c,b]                  [a]                          처리 시작
                         │  (작업 성공)
                         │  LREM processing 1 a     ← 처리 끝나면 백업에서 제거
                         ▼
[c,b]                  []                           ✅ 깔끔히 사라짐
```

서버가 2단계와 3단계 사이에서 죽으면? `a`는 **processing 큐에 그대로 남아 있다** → 재시작 시 복구 가능. **유실 0.**

### 핵심 명령: LMOVE / BLMOVE (구버전 RPOPLPUSH / BRPOPLPUSH)

```
BLMOVE main processing RIGHT LEFT 10
        │     │          │     │   │
        │     │          │     │   └ 블로킹 타임아웃(초)
        │     │          │     └ 목적지에 넣을 위치(LEFT=head)
        │     │          └ 출발지에서 뺄 위치(RIGHT=tail) ← FIFO 유지
        │     └ 목적지 = 처리 중 백업 리스트
        └ 출발지 = 원래 큐
```

- `RPOPLPUSH src dst` / `BRPOPLPUSH src dst timeout` 은 6.2부터 **deprecated** → `LMOVE` / `BLMOVE` 사용.
- 핵심은 **pop + push가 단일 원자 연산**이라는 것. "꺼냈는데 백업 넣기 전에 죽는" 틈이 없다.

### Java/Spring 코드 — Before / After

**Before (현재 `EmailMultiWorker` — 유실 가능)**

```java
// 디스패처
String email = redisTemplate.opsForList().rightPop(MAIL_QUEUE, Duration.ofSeconds(10)); // BRPOP
if (email != null) {
    workerPool.submit(() -> processEmail(email));   // 처리 중 죽으면 끝 → 유실
}
```

**After (신뢰성 큐 — 유실 0)**

```java
private static final String MAIL_QUEUE      = "mail:queue";
private static final String MAIL_PROCESSING = "mail:queue:processing";   // 처리 중 백업

private void dispatch() {
    while (!Thread.currentThread().isInterrupted()) {
        // 1) 꺼내면서 동시에 processing 백업에 남김 (원자적)
        //    BLMOVE mail:queue mail:queue:processing RIGHT LEFT 10
        String email = redisTemplate.opsForList()
                .move(MAIL_QUEUE, RIGHT, MAIL_PROCESSING, LEFT, Duration.ofSeconds(10));
        // 구버전: redisTemplate.opsForList().rightPopAndLeftPush(MAIL_QUEUE, MAIL_PROCESSING, Duration.ofSeconds(10));

        if (email != null) {
            workerPool.submit(() -> processEmail(email));
        }
    }
}

private void processEmail(String email) {
    try {
        sendAndSave(email);   // 실제 처리 (발송 + DB save)

        // 2) 처리 성공 → 백업에서 제거 (이제 정말 끝)
        //    LREM mail:queue:processing 1 email
        redisTemplate.opsForList().remove(MAIL_PROCESSING, 1, email);

    } catch (Exception e) {
        log.error("처리 실패, processing 큐에 남겨둠(나중에 복구): {}", email, e);
        // ❗ 여기서 LREM 하지 않는다. processing에 남겨두면 reaper가 재처리하거나 DLQ로 보냄(§3)
    }
}
```

> `opsForList().move(...)`의 인자 `RIGHT`/`LEFT`는 `RedisListCommands.Direction`. 정적 import 하면 위처럼 깔끔하다.
> 구버전 Redis(6.2 미만)거나 옛 API를 쓰면 `rightPopAndLeftPush(src, dst, timeout)`(= BRPOPLPUSH)로 동일하게 구현된다.

### 죽은 워커 복구 — Stale 메시지 Reaper

문제: 서버가 처리 중 죽으면 `mail:queue:processing`에 메시지가 **영원히** 남는다(아무도 LREM 안 함).
그래서 **별도 청소부(reaper)**가 필요하다.

```java
// 주기적으로(예: 1분마다) processing 큐를 점검
@Scheduled(fixedDelay = 60_000)
public void reapStaleMessages() {
    // processing에 남아있는 모든 항목을 본다 (LRANGE processing 0 -1)
    List<String> stuck = redisTemplate.opsForList().range(MAIL_PROCESSING, 0, -1);
    if (stuck == null || stuck.isEmpty()) return;

    for (String email : stuck) {
        // "너무 오래 processing에 머문" 메시지만 골라 main 큐로 되돌림
        // → 다시 LPUSH 해서 재처리 기회를 줌
        log.warn("Stale 메시지 복구: {}", email);
        redisTemplate.opsForList().leftPush(MAIL_QUEUE, email);   // 큐로 환원
        redisTemplate.opsForList().remove(MAIL_PROCESSING, 1, email);
    }
}
```

> **"너무 오래"를 어떻게 아나?** 위 코드는 단순화 버전이라 시간 판단이 빠져 있다. 실무에선:
> - 메시지 자체에 **타임스탬프/워커ID를 박아서** payload로 넣고(JSON), reaper가 `now - enqueuedAt > 임계값`을 검사.
> - 또는 processing을 **List 대신 Sorted Set**(score=처리시작시각)으로 둬서 "오래된 것만" 효율적으로 스캔. → ZSet 단계에서 다룸.
> 단순 List reaper는 "정상 처리 중인 메시지"까지 되돌릴 위험(중복 처리)이 있으니 **시간 판단이 핵심**이다.

## 흔한 함정 표

| 함정 | 결과 | 해법 |
|---|---|---|
| BRPOP 단독 사용 (백업 없음) | 처리 중 죽으면 메시지 영구 유실(at-most-once) | LMOVE/BLMOVE로 processing 백업 |
| processing에서 LREM 잊음 | 백업 리스트가 무한정 커짐(메모리 누수), reaper가 정상 메시지도 재처리 | 성공 시 반드시 LREM, reaper에 시간 판단 |
| reaper 없음 | 죽은 워커가 남긴 메시지가 영영 처리 안 됨 | 주기적 reaper로 stale 복구 |
| reaper가 시간 판단 없이 복구 | 정상 처리 중인 메시지를 중복 처리 | enqueuedAt 타임스탬프 비교 또는 ZSet |
| 재처리 후 컨슈머 멱등성 없음 | 같은 메일 2번 발송, DB 중복 row | dedup 키(§3), 멱등 처리 의무 |
| `LMOVE`/`BLMOVE`를 6.2 미만에서 호출 | 명령 없음 에러 | `RPOPLPUSH`/`BRPOPLPUSH` 사용 |

## at-most-once vs at-least-once vs exactly-once

신뢰성 큐를 설계하면 이 세 단어를 피할 수 없다.

| 전달 보장 | 의미 | List로 구현하면 | 대가 |
|---|---|---|---|
| **at-most-once** | 최대 1번 (유실 가능, 중복 없음) | **현재 프로젝트** (BRPOP 단독) | 유실 위험 |
| **at-least-once** | 최소 1번 (유실 없음, **중복 가능**) | processing 백업 + reaper 재처리 | 중복 처리 가능 → 멱등성 필요 |
| **exactly-once** | 정확히 1번 | 메시징만으로는 사실상 불가 | "처리+ack"를 트랜잭션으로 묶어야 근사치 |

> **실무 결론**: 분산 메시징에서 진짜 exactly-once는 거의 불가능하다(네트워크는 언제든 끊긴다).
> 현실적 목표는 **"at-least-once 전달 + 컨슈머 멱등성"** = "여러 번 와도 결과는 한 번처럼" → 사실상 exactly-once처럼 보이게.
> 즉 신뢰성 큐를 켜는 순간, **컨슈머 멱등성은 옵션이 아니라 의무**가 된다. (멱등성 구현은 [`../01-string/부록-멱등성.md`](../01-string/부록-멱등성.md))

## 🎯 이 프로젝트 적용 포인트

- `EmailMultiWorker`를 `BRPOP` → `BLMOVE(main → processing)`로 바꾸고, 성공 시 `LREM`, reaper 추가 → **at-most-once를 at-least-once로 격상**.
- 동시에 컨슈머에 dedup 키(`dedup:email:{email}:{date}`)를 박아 재처리 중복을 흡수(§3).
- 단, 솔직하게: 환영 메일 하나에 이 모든 걸 까는 건 과하다. **이 패턴의 진짜 가치는 "결제·정산·티켓 발급 알림" 같은 유실 불가 메시지**로 확장할 때 드러난다. 지금은 학습용으로 이메일 큐에 적용해보고, 운영에선 데이터 중요도에 맞춰 선택.

# §3. DLQ (Dead Letter Queue)

## 문제 상황

at-least-once로 재처리를 켜면 새 문제가 생긴다. **"고칠 수 없는 메시지"가 무한 재시도 루프에 빠진다.**

```
"poison@.com" 같은 잘못된 주소 → 발송 실패 → reaper가 큐로 환원 → 또 실패 → 또 환원 …
→ 이 한 건이 워커를 영원히 붙잡고, 로그를 도배하고, 뒤 메시지를 굶긴다.
```

해법: **재시도 N회를 넘긴 메시지는 본 큐에서 빼서 "죽은 편지함(DLQ)"으로 격리.**
사람이 보거나, 별도 배치로 분석·재처리한다.

## 표준 패턴

메시지에 재시도 횟수를 들고 다녀야 하므로, 보통 **payload를 JSON으로** 바꾼다.

```
payload = {"email":"a@x.com", "retry":0, "enqueuedAt": 1718000000}
```

```java
private static final String MAIL_QUEUE = "mail:queue";
private static final String MAIL_DLQ   = "mail:queue:dlq";
private static final int    MAX_RETRY  = 3;

private void processEmail(String raw) {
    Msg msg = parse(raw);   // JSON → 객체
    try {
        sendAndSave(msg.getEmail());
        redisTemplate.opsForList().remove(MAIL_PROCESSING, 1, raw);   // 성공 → 백업 제거

    } catch (Exception e) {
        redisTemplate.opsForList().remove(MAIL_PROCESSING, 1, raw);   // 일단 백업에서 빼고

        if (msg.getRetry() + 1 >= MAX_RETRY) {
            // 재시도 한도 초과 → DLQ로 격리
            //   LPUSH mail:queue:dlq {원본}
            redisTemplate.opsForList().leftPush(MAIL_DLQ, raw);
            log.error("DLQ로 격리(재시도 {}회 초과): {}", MAX_RETRY, msg.getEmail());
        } else {
            // 재시도 카운트 올려서 본 큐로 되돌림
            msg.setRetry(msg.getRetry() + 1);
            redisTemplate.opsForList().leftPush(MAIL_QUEUE, serialize(msg));
        }
    }
}
```

### DLQ 운영

```
mail:queue:dlq 를 사람이 본다:
  LLEN mail:queue:dlq        → 격리된 메시지 수 (모니터링/알람 대상)
  LRANGE mail:queue:dlq 0 9  → 최근 10건 내용 확인 (왜 실패했나)

원인 고친 뒤 재투입:
  LMOVE mail:queue:dlq mail:queue LEFT LEFT   → DLQ에서 하나씩 본 큐로 되돌려 재처리
```

## DLQ와 멱등성은 한 몸

재시도/DLQ 재투입은 본질적으로 **같은 메시지를 또 처리**하는 행위다. 멱등성이 없으면:

```
재시도 1: 메일 발송 성공 → 그런데 DB save에서 예외 → "실패"로 간주 → 재시도
재시도 2: 메일 또 발송(중복!) → 사용자에게 환영 메일 2통
```

→ 컨슈머는 "이미 처리했나?"를 먼저 묻고 들어가야 한다(dedup 키).

```java
String dedupKey = "dedup:email:" + msg.getEmail() + ":" + LocalDate.now();
Boolean isFirst = redisTemplate.opsForValue().setIfAbsent(dedupKey, "1", Duration.ofDays(1));
if (!Boolean.TRUE.equals(isFirst)) {
    log.info("중복 skip: {}", msg.getEmail());
    redisTemplate.opsForList().remove(MAIL_PROCESSING, 1, raw);
    return;   // 이미 처리됨 → 조용히 종료
}
```

> dedup/멱등성의 상태 머신·응답 재생·TTL 설계는 [`../01-string/부록-멱등성.md`](../01-string/부록-멱등성.md) 참고.

## 흔한 함정 표

| 함정 | 결과 | 해법 |
|---|---|---|
| 재시도 한도 없음 | poison 메시지가 무한 재시도, 큐를 굶김 | MAX_RETRY 도입 + 초과 시 DLQ |
| DLQ에 넣기만 하고 모니터링 X | 조용히 메시지가 쌓이다 발견 못 함 | `LLEN dlq` 알람, 대시보드 노출 |
| 재시도 카운트를 키 밖(메모리)에 보관 | 서버 재시작 시 카운트 리셋 → 무한 재시도 | payload(JSON)에 retry 포함해 메시지와 함께 이동 |
| 멱등성 없이 재시도 | 같은 작업 중복 실행(메일 2통, DB 중복) | dedup 키 + 멱등 처리 |
| 단순 문자열 payload로 메타데이터 못 실음 | retry/enqueuedAt 못 들고 다님 | payload를 JSON으로 |

## 🎯 이 프로젝트 적용 포인트

- 현재 `mail:queue` payload는 **순수 이메일 문자열**이다(`leftPush(MAIL_QUEUE, email)`). DLQ/재시도를 제대로 하려면 **JSON payload로 전환**이 선행되어야 한다.
- `mail:queue:dlq`를 만들고, `LLEN`을 헬스 지표로 노출하면 "조용한 실패"를 잡아낼 수 있다.
- 멱등성은 §2에서 이미 의무가 됐으므로 dedup 키와 함께 묶어 적용.

# §4. 최근 N개 — Capped List (LPUSH + LTRIM)

## 문제 상황

"최근 검색어 10개", "최근 본 콘서트 20개", "최근 로그인 기록 50개", "디버깅용 최근 에러 100건".
공통점: **새 항목을 앞에 쌓되, 일정 개수만 유지**하고 싶다. 무한히 쌓이면 메모리가 터진다.

DB로 하면? insert + `DELETE ... WHERE id NOT IN (최근 N개)` → 매번 쓰기 두 번 + 정렬. 비싸다.

## 표준 패턴 — LPUSH 후 LTRIM

```
LPUSH recent:user:42 "concert:100"     →  [c100]
LPUSH recent:user:42 "concert:101"     →  [c101, c100]
LPUSH recent:user:42 "concert:102"     →  [c102, c101, c100]
LTRIM recent:user:42 0 9               →  앞에서 10개(0~9)만 남기고 나머지 잘라냄
```

`LTRIM key 0 N-1` 한 줄이 **"최대 N개 유지"**를 보장한다(양끝 inclusive라 `0 9`면 10개).

```java
public void addRecentlyViewed(Long userId, Long concertId) {
    String key = "recent:user:" + userId;
    redisTemplate.opsForList().leftPush(key, "concert:" + concertId);   // LPUSH 맨 앞에
    redisTemplate.opsForList().trim(key, 0, 9);                          // LTRIM 최근 10개만 유지
    redisTemplate.expire(key, Duration.ofDays(30));                      // 30일 미사용 시 자동 정리
}

public List<String> getRecentlyViewed(Long userId) {
    // LRANGE recent:user:42 0 -1  → 최신순(LPUSH라 head가 최신)으로 전체
    return redisTemplate.opsForList().range("recent:user:" + userId, 0, -1);
}
```

> **메모리 자동 제한이 핵심.** LTRIM이 없으면 리스트가 무한히 자라 한 사용자가 평생 본 콘서트가 다 쌓인다.
> LTRIM은 O(잘라내는 개수)라 매번 살짝 자르는 비용은 미미하다.

### "중복 제거하고 최근 N개"가 필요하면?

같은 콘서트를 또 보면 List엔 중복으로 쌓인다. "최근 본 것, 중복 없이"가 필요하면:

```java
redisTemplate.opsForList().remove(key, 0, "concert:" + concertId);   // LREM: 기존 동일 항목 전부 제거
redisTemplate.opsForList().leftPush(key, "concert:" + concertId);    // 맨 앞에 다시 추가
redisTemplate.opsForList().trim(key, 0, 9);
```

> 다만 "유니크 + 점수(최근성) + 자동 정렬"이 정말 필요하면 List보다 **Sorted Set**(score=timestamp)이 정석이다.
> List capped는 "중복 허용해도 되는 단순 최근 목록"에 가장 잘 맞는다.

## 흔한 함정 표

| 함정 | 결과 | 해법 |
|---|---|---|
| LTRIM 안 함 | 리스트 무한 증가 → 메모리 누수 | LPUSH 직후 항상 LTRIM |
| LTRIM 범위 오해(`0 N`은 N+1개) | 의도보다 1개 많이 남음 | `0 N-1`로 정확히 N개 (양끝 inclusive) |
| 넣는 방향과 읽는 방향 불일치 | 최신/최오래된 순서가 뒤집힘 | LPUSH+LRANGE(0..)면 head=최신 |
| 같은 항목 중복 누적 | "최근 본 것"에 같은 게 여러 번 | LREM 후 LPUSH, 또는 ZSet |
| TTL 없음 | 비활성 사용자 키가 영구 잔존 | expire로 미사용 자동 정리 |

## 🎯 이 프로젝트 적용 포인트

| 대상 | 키 | 패턴 |
|---|---|---|
| 사용자가 최근 본 콘서트 | `recent:concert:{userId}` | LPUSH + LTRIM 0 19 + TTL 30일 |
| 최근 로그인 IP/기기 이력 | `recent:login:{userId}` | LPUSH + LTRIM 0 4 (최근 5개) |
| 발송 워커의 최근 에러 로그 | `log:mail:errors` | LPUSH + LTRIM 0 99 (운영 디버깅용) |

→ 특히 마지막 것은 `EmailMultiWorker`의 `catch` 블록에 한 줄 추가하면 "최근 실패 100건"을 Redis에서 바로 볼 수 있어 디버깅에 유용.

# §5. 피드 타임라인 — Fan-out on write (LPUSH feed + LTRIM)

## 문제 상황

SNS 홈 피드: 내가 팔로우한 사람들의 새 글이 시간순으로 보인다.
"팔로워가 새 글을 읽을 때 매번 모든 팔로잉의 글을 조인·정렬(Fan-out on read)"하면 읽기가 비싸다(특히 읽기 >> 쓰기인 SNS에서 치명적).

## 표준 패턴 — Fan-out on write

**글을 쓰는 순간**, 그 글 ID를 팔로워 각각의 **개인 피드 리스트에 미리 뿌려둔다.** 읽기는 자기 리스트만 보면 끝(O(1) 조회).

```java
// 사용자 U가 글 P를 작성 → U의 팔로워 전원의 피드에 push
public void onNewPost(Long authorId, Long postId) {
    List<Long> followers = followRepository.findFollowerIds(authorId);
    for (Long followerId : followers) {
        String key = "feed:" + followerId;
        redisTemplate.opsForList().leftPush(key, "post:" + postId);   // LPUSH 각자 피드 맨 앞
        redisTemplate.opsForList().trim(key, 0, 999);                 // LTRIM 최근 1000개만
    }
}

// 팔로워가 홈 피드 열기 → 자기 리스트만 읽으면 끝
public List<String> getFeed(Long userId, int page, int size) {
    int start = page * size;
    return redisTemplate.opsForList().range("feed:" + userId, start, start + size - 1); // LRANGE 페이지네이션
}
```

`LRANGE key start stop`이 **페이지네이션**까지 공짜로 해준다(0~19, 20~39 …).

## Fan-out on write vs on read — 트레이드오프

| 방식 | 쓰기 | 읽기 | 약점 |
|---|---|---|---|
| **on write** (push 모델) | 비쌈 (팔로워 수만큼 LPUSH) | 쌈 (내 리스트만 LRANGE) | **셀럽 문제**: 팔로워 1000만이면 글 1개에 LPUSH 1000만 번 |
| **on read** (pull 모델) | 쌈 | 비쌈 (매번 조인·정렬) | 읽기 폭증 시 DB 부담 |

> **실무는 보통 하이브리드**: 일반 사용자는 on-write로 미리 뿌리고, **셀럽(팔로워 초대형)은 on-read**로 읽을 때 합친다.
> Twitter/Instagram이 쓰는 고전적 접근. List는 이 "개인 피드 캐시"의 자료구조로 딱 맞는다.

## 흔한 함정 표

| 함정 | 결과 | 해법 |
|---|---|---|
| 셀럽도 on-write로 fan-out | 글 1개에 LPUSH 수백만 번, 쓰기 폭발 | 셀럽은 on-read 하이브리드 |
| LTRIM 없음 | 피드 리스트 무한 증가 | 최근 N개만 유지(LTRIM) |
| 피드를 영구 진실로 취급 | Redis 휘발 시 피드 소실 | DB가 원본, 피드는 캐시(재생성 가능하게) |
| 글 삭제 시 피드에서 안 지움 | 삭제된 글이 피드에 유령으로 | LREM으로 제거 또는 읽을 때 필터 |

## 🎯 이 프로젝트 적용 포인트

콘서트 티켓 시스템에 SNS 피드는 없지만, **개념은 그대로 이식**된다:

- **"내가 찜한 아티스트의 새 공연 알림 피드"**: 아티스트가 공연을 등록하면 → 그 아티스트를 찜한 사용자들의 `feed:user:{id}`에 LPUSH. 사용자는 자기 피드만 LRANGE.
- **"콘서트별 실시간 활동 로그"**: `feed:concert:{id}`에 예매/취소 이벤트를 LPUSH + LTRIM → 관리자 대시보드가 최근 활동을 빠르게 표시.

→ 둘 다 "쓰기 시점에 미리 뿌려두고 읽기는 싸게"라는 fan-out 사고방식.

# §6. 우선순위 큐 / 다중 큐 (BRPOP 여러 키)

## 문제 상황

모든 메일이 동등하지 않다. **"비밀번호 재설정 메일"은 즉시**, **"마케팅 뉴스레터"는 천천히**.
하나의 큐에 섞으면 마케팅 1만 건 뒤에 낀 비번 재설정 메일이 한참 굶는다.

## 표준 패턴 — 큐를 우선순위별로 나누고, BRPOP에 여러 키

`BRPOP`/`BLPOP`은 **여러 키를 받으며, 앞 키를 우선**한다.

```
BRPOP mail:queue:high mail:queue:low 10
       │                │
       │                └ low 큐 (둘 다 비면 여기서 대기)
       └ high 큐 먼저 검사 → 있으면 무조건 high부터
```

```java
// 반환은 (어느 키에서 나왔는지, 값) 2-element
List<String> result = redisTemplate.execute((RedisCallback<List<String>>) conn ->
    conn.bRPop(10, "mail:queue:high".getBytes(), "mail:queue:low".getBytes())
        .stream().map(String::new).toList()
);
// result.get(0) = 꺼낸 큐 이름, result.get(1) = 값
```

- high에 일감이 있는 한 low는 절대 안 꺼낸다(엄격한 우선순위).
- 둘 다 비면 10초 블로킹.

> **함정: 기아(starvation).** high가 끊임없이 들어오면 low는 영영 처리 안 됨.
> → 완화책: 별도 워커가 low 전용으로 한 명 더 돌거나, 가중치 라운드로빈, 또는 진짜 우선순위가 중요하면 **Sorted Set(score=우선순위)** 기반 큐로 전환.

### 다중 큐의 또 다른 용도: 큐 샤딩

같은 우선순위라도 처리량을 늘리려고 큐를 여러 개로 쪼개고(`mail:queue:0..9`), 워커가 `BRPOP`로 여러 큐를 동시에 감시 → 부하 분산.

> Redis 7.0+에는 `LMPOP`/`BLMPOP numkeys key... LEFT|RIGHT`가 있어 "여러 키 중 첫 비어있지 않은 리스트에서 (여러 개) 팝"을 더 깔끔하게 한다.

## 흔한 함정 표

| 함정 | 결과 | 해법 |
|---|---|---|
| BRPOP 키 순서 = 우선순위 무시 | 우선순위가 안 먹음 | 높은 우선순위 큐를 **앞 인자**로 |
| high 폭주 시 low 기아 | low 메시지 영영 처리 안 됨 | low 전용 워커, 가중치, 또는 ZSet 큐 |
| BRPOP 반환을 단일 값으로 파싱 | 결과가 (키, 값) 2-element라 깨짐 | 두 원소로 받기 |
| 큐만 늘리고 워커는 1개 | 다중 큐 효과 없음 | 워커도 늘리거나 LMPOP로 다중 감시 |

## 🎯 이 프로젝트 적용 포인트

- 메일 유형(`EmailLog.EmailType.WELCOME` 등)에 따라 큐를 나눈다: `mail:queue:high`(비번 재설정·결제 알림), `mail:queue:low`(환영·마케팅).
- `EmailMultiWorker`의 디스패처가 `BRPOP mail:queue:high mail:queue:low 10`으로 우선순위 소비.
- 현재는 단일 `mail:queue`라 모든 메일이 동급 — 메일 종류가 늘면 자연스럽게 필요해지는 확장.

# §7. 배치 소비 — 한 번에 N개 꺼내기

## 문제 상황

한 건씩 꺼내 한 건씩 DB save 하면, 메시지 1000건 = 네트워크 왕복 1000번 + DB insert 1000번.
**한 번에 100건씩 묶어서** 꺼내고, `saveAll`로 한 번에 적재하면 처리량이 수직 상승한다.

## 표준 패턴

### 방법 A: LPOP/RPOP count (Redis 6.2+) — 가장 단순

```
RPOP mail:queue 100   →  최대 100개를 한 번에 꺼내 반환 (큐에 100개 미만이면 있는 만큼)
```

```java
// 한 번에 최대 100개 꺼내기 (BRPOP과 달리 블로킹 아님 → 빈 큐면 null)
List<String> batch = redisTemplate.opsForList().rightPop(MAIL_QUEUE, 100);
if (batch != null && !batch.isEmpty()) {
    List<EmailLog> logs = batch.stream().map(this::toLog).toList();
    emailLogRepository.saveAll(logs);   // DB 한 방에 적재
}
```

> `LPOP/RPOP count`도 결국 **꺼내는 순간 사라진다** → 배치 처리 중 죽으면 그 100건 통째 유실.
> 유실이 문제면 §2의 신뢰성과 결합해야 한다(아래 방법 B 또는 배치 단위 processing 백업).

### 방법 B: LRANGE + LTRIM (들여다보고 잘라내기)

```
LRANGE mail:queue -100 -1   →  tail 쪽(오래된) 100개를 "보기만" (삭제 안 함)
LTRIM  mail:queue 0 -101     →  방금 본 100개를 잘라내 큐에서 제거
```

`LRANGE`로 먼저 읽고 처리에 성공한 뒤 `LTRIM`으로 지우면, 처리 실패 시 아직 큐에 남아 있어 재시도 가능. 다만 `LRANGE`+`LTRIM` 두 명령 사이는 원자가 아니므로 동시 컨슈머가 있으면 **Lua로 묶어야** 안전하다.

> Lua로 "N개 읽고 + 잘라내기"를 한 번에 묶는 패턴은 [`../01-string/부록-lua-스크립트.md`](../01-string/부록-lua-스크립트.md)의 원자 연산 개념을 그대로 적용하면 된다.

## 배치 크기 트레이드오프

| 배치 크기 | 처리량 | 지연 | 유실 시 손실 | 메모리 |
|---|---|---|---|---|
| 작음 (1~10) | 낮음 | 낮음 | 적음 | 적음 |
| 큼 (100~1000) | 높음 | 높음(모을 때까지 대기) | 큼(한 번에 다 날림) | 큼 |

→ 보통 **"N개 모이거나 T밀리초 지나면 flush"**(size+time 둘 중 먼저) 하이브리드. 실시간성과 처리량의 균형.

## 흔한 함정 표

| 함정 | 결과 | 해법 |
|---|---|---|
| `LPOP count`를 블로킹으로 오해 | 빈 큐면 null, 바쁜 폴링 됨 | 배치는 BRPOP로 1건 깨운 뒤 LPOP count로 나머지 긁기 |
| LRANGE+LTRIM 비원자 | 동시 컨슈머가 같은 메시지 중복 소비 | Lua로 read+trim 원자화 |
| 배치 처리 중 죽음 | 배치 통째 유실 | 배치 단위 processing 백업 또는 LRANGE 후 처리 성공 시에만 LTRIM |
| 배치 크기만 키움 | 지연 폭증, OOM 위험 | size+time 하이브리드 flush |

## 🎯 이 프로젝트 적용 포인트

- `EmailMultiWorker`가 메일 발송은 외부 I/O라 1건씩이 자연스럽지만, **DB 로그 저장(`emailLogRepository.save`)은 배치가 이득**이다.
  → 처리한 `EmailLog`들을 모아 `saveAll`로 묶으면 DB 왕복이 급감.
- "BRPOP로 1건 깨어난 뒤, `RPOP count`로 나머지 큐를 한 번에 긁어 배치 처리"는 **블로킹의 즉시성 + 배치의 효율**을 둘 다 취하는 흔한 실전 조합.

# §8. 솔직한 실무 평가 — Redis List 큐 vs 전용 메시지 브로커

여기까지 List로 신뢰성 큐, DLQ, 우선순위까지 만들었다. 그런데 이걸 다 손으로 짜고 나면 드는 의문:
**"이쯤 되면 그냥 Kafka/RabbitMQ 쓰는 게 낫지 않나?"** — 맞다. 경계를 분명히 알아야 한다.

## Redis List 큐가 못 하는 것 (구조적 한계)

| 한계 | 설명 |
|---|---|
| **재소비 불가** | 꺼내면 사라진다. "어제 메시지 다시 보기", 새 컨슈머가 과거부터 재생 → 불가능 |
| **컨슈머 그룹 없음** | "같은 메시지를 그룹 A와 그룹 B가 각자 한 번씩" 같은 fan-out 소비 불가. 한 메시지는 한 컨슈머만 |
| **ack 개념 없음** | "처리 완료 확인"을 큐가 모름. §2처럼 processing+LREM을 **손으로** 흉내내야 함 |
| **순서 보장 범위 좁음** | 단일 리스트 내 FIFO는 되지만, 파티션/키별 순서·재정렬은 직접 |
| **내구성 약함** | Redis는 인메모리. RDB/AOF로 보완해도 디스크 우선 브로커보다 유실 위험 큼(failover 순간 등) |
| **백프레셔·라우팅 빈약** | 토픽 라우팅, 익스체인지, 컨슈머 랙 모니터링 등 운영 기능이 없음 |

## 그래서 언제 List, 언제 브로커?

| 상황 | 선택 |
|---|---|
| 가벼운 비동기 작업(메일·썸네일·알림), 유실 약간 허용, 이미 Redis 있음, 인프라 추가 싫음 | ✅ **Redis List** (이 프로젝트) |
| 트래픽 작고 컨슈머 1종류, 빠른 구현 우선 | ✅ **Redis List** |
| 유실 절대 불가, 재처리/재생 필요, 여러 소비 그룹, 이벤트 소싱/로그 | ✅ **Kafka** |
| 복잡한 라우팅, ack/재시도/DLQ를 인프라가 보장, 트랜잭션 메시징 | ✅ **RabbitMQ** |
| 대규모·장기 보존·스트림 분석 | ✅ **Kafka** |

> **한 줄 결론**: List 큐는 "**작고 단순한 비동기 작업 큐**"에 최적이다. §2~§3처럼 신뢰성을 손으로 덧대기 시작하면, 그건 "곧 전용 브로커가 필요하다"는 신호다. 손으로 만든 ack/DLQ/reaper는 **버그의 온상**이다.

## 그런데 Redis 안에도 답이 있다 — List vs Stream

"Redis는 쓰고 싶은데 신뢰성 큐가 진짜 필요"하면, List를 손으로 보강하기 전에 **Redis Stream**(`XADD`)을 먼저 봐라.
Stream은 **컨슈머 그룹·ack(XACK)·재처리(XPENDING/XCLAIM)·재소비**를 Redis가 **기본 제공**한다.

| | List 큐 | Redis Stream |
|---|---|---|
| ack | ❌ (수동 processing+LREM) | ✅ XACK |
| 컨슈머 그룹 | ❌ | ✅ XGROUP |
| 재처리(죽은 컨슈머) | ❌ (수동 reaper) | ✅ XPENDING + XCLAIM |
| 재소비/재생 | ❌ | ✅ (메시지 보존) |
| 구현 난이도 | 단순(하지만 신뢰성은 직접) | 약간 복잡(대신 신뢰성 내장) |

> **실무 결론**: "FIFO 작업 큐, 유실 약간 OK" → **List**. "신뢰성 큐가 진짜 필요" → List를 손으로 흉내내지 말고 **Stream**(이름만 기억, 깊이는 별도 단계). 그래도 안 되면 Kafka/RabbitMQ.
> 이 프로젝트의 환영 메일 큐는 **List로 충분**하다. 다만 "왜 충분한지"를 위 기준으로 설명할 수 있어야 한다.

# §9. 일곱 패턴 종합 비교표

| 패턴 | 핵심 명령어 | 키 예시 | 한 줄 요약 |
|---|---|---|---|
| **메시지 큐 (FIFO)** | `LPUSH` + `BRPOP` | `mail:queue` | 넣는 쪽/빼는 쪽 반대 = FIFO, 블로킹으로 대기 |
| **신뢰성 큐** | `BLMOVE` + `LREM` + reaper | `mail:queue` + `:processing` | 꺼내며 백업, 성공 시 제거, 죽으면 복구 |
| **DLQ** | `LPUSH dlq` + `LMOVE` | `mail:queue:dlq` | 재시도 초과 메시지 격리, 멱등성 필수 |
| **최근 N개 (Capped)** | `LPUSH` + `LTRIM 0 N-1` | `recent:user:42` | 앞에 쌓고 N개만 유지, 메모리 자동 제한 |
| **피드 타임라인** | `LPUSH feed` + `LTRIM` + `LRANGE` | `feed:user:42` | 쓰기 때 미리 뿌리고 읽기는 싸게 |
| **우선순위/다중 큐** | `BRPOP k1 k2` | `mail:queue:high`/`low` | 앞 키 우선, 기아 주의 |
| **배치 소비** | `RPOP count` / `LRANGE`+`LTRIM` | `mail:queue` | 한 번에 N개 묶어 처리량↑ |

> 👀 **공통 뼈대 3가지**:
> 1. **방향이 곧 의미** — 넣는 쪽/빼는 쪽이 반대면 FIFO, 같으면 LIFO.
> 2. **LTRIM = 메모리 안전벨트** — 무한 증가하는 리스트는 거의 다 LTRIM으로 길들인다.
> 3. **꺼내면 사라진다** — 이 한 문장이 신뢰성 큐·DLQ·배치 유실 문제의 뿌리. ack가 없으니 손으로 만든다(아니면 Stream).

# §10. 이 프로젝트에서 다음 학습 미션 (선택)

### 미션 1: 신뢰성 큐로 격상 (난이도 ★★★) ⭐ 가장 추천
`EmailMultiWorker`의 `BRPOP`을 `BLMOVE(mail:queue → mail:queue:processing)`로 바꾸고,
성공 시 `LREM`, `@Scheduled` reaper로 stale 메시지 복구. → at-most-once를 at-least-once로.

### 미션 2: DLQ + 멱등성 (난이도 ★★★)
payload를 JSON으로 전환(retry/enqueuedAt 포함) → MAX_RETRY 초과 시 `mail:queue:dlq`로 격리 →
컨슈머에 `dedup:email:{email}:{date}` 멱등 키 추가. (멱등성: [`../01-string/부록-멱등성.md`](../01-string/부록-멱등성.md))

### 미션 3: 최근 본 콘서트 (난이도 ★)
`recent:concert:{userId}` 에 LPUSH + `LTRIM 0 19` + TTL 30일. 조회 API는 LRANGE.

### 미션 4: 우선순위 메일 큐 (난이도 ★★)
`mail:queue:high`/`low`로 분리하고 디스패처를 `BRPOP high low`로. 기아 방지책도 같이 고민.

### 미션 5: 배치 DB 저장 (난이도 ★★)
BRPOP로 1건 깨운 뒤 `RPOP count`로 나머지 긁어 `emailLogRepository.saveAll`로 묶기.
