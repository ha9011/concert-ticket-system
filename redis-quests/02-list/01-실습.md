# List 실습 — 명령어 드릴 74선

> 직접 redis-cli에 한 줄씩 입력하며 결과를 확인하라.
> **답을 보지 말고** 먼저 추측 → 입력 → 결과 비교 → 헷갈리면 메모.
> 다 풀면 Claude에게 "List 실습 완료" → 함정(🪤) 위주 채점.

## 표기 규칙

- ★ ~ ★★★★★ : 난이도
- 🪤 : 함정 문제 (대부분 헷갈림)
- 🔁 : 큐/스택 패턴
- 🧱 : 블로킹 명령
- ⚠ : 실무에서 자주 실수하는 포인트
- `>` : redis-cli 입력 프롬프트

## 사전 준비

```bash
> FLUSHDB        # ⚠ 현재 DB만 비움. 다른 데이터 있으면 주의!
> DBSIZE         # 0 인지 확인
```

> 💡 별도 터미널에서 `redis-cli MONITOR`를 켜두면 큐 동작이 한눈에 보인다.

## §1. LPUSH / RPUSH — 방향이 전부다

### Q1. ★ 가장 기본
```
> RPUSH q "a"
> RPUSH q "b"
> RPUSH q "c"
> LRANGE q 0 -1            ← 순서는? a b c? c b a?
```
=> a b c
---

### Q2. ★ 반대 방향
```
> DEL q
> LPUSH q "a"
> LPUSH q "b"
> LPUSH q "c"
> LRANGE q 0 -1            ← 이번엔 순서가?
```
=> c b a
---

### Q3. ★★ 🪤 여러 값 한 번에 push
```
> DEL q
> RPUSH q "a" "b" "c"
> LRANGE q 0 -1            ← a b c

> DEL q
> LPUSH q "a" "b" "c"      ← 한 번의 LPUSH로 a, b, c
> LRANGE q 0 -1            ← 결과는? a b c 일까 c b a 일까?
```
=> c b a
> 함정: `LPUSH q a b c`는 a를 넣고, 그 앞에 b, 또 그 앞에 c. 마지막 인자가 맨 앞.

---

### Q4. ★ 반환값의 의미
```
> DEL q
> RPUSH q "x"             ← 반환값? 1
> RPUSH q "y"             ← 반환값? 2
> RPUSH q "z" "w"         ← 반환값? 4
```
LPUSH/RPUSH의 반환값은 무엇인가?
=> 길이
---

### Q5. ★★ 🔁 FIFO 큐 만들기 (이 프로젝트 mail:queue)
```
> DEL mail:queue
> LPUSH mail:queue "user1@test.com"      ← Producer (AuthService.java:85와 동일)
> LPUSH mail:queue "user2@test.com"
> LPUSH mail:queue "user3@test.com"
> RPOP mail:queue                         ← Consumer가 먼저 받는 건 누구?
> RPOP mail:queue
> RPOP mail:queue
```
"LPUSH + RPOP" 이면 user1, user2, user3 중 누가 먼저 나오나? (FIFO?)
=> user1@test.com

---

### Q6. ★★ 🔁 LIFO 스택 만들기
```
> DEL stack
> LPUSH stack "1"
> LPUSH stack "2"
> LPUSH stack "3"
> LPOP stack                              ← 같은 쪽에서 빼면? 3
> LPOP stack
```
"LPUSH + LPOP" = 스택. 먼저 나오는 건?
=> 3

## §3. LLEN / LRANGE / LINDEX — 비우지 않고 들여다보기

### Q12. ★ LLEN
```
> DEL q
> RPUSH q "a" "b" "c"
> LLEN q
> LLEN nope               ← 없는 키의 길이는?
```
=> 0
---

### Q13. ★★ LRANGE는 양끝 inclusive
```
> DEL q
> RPUSH q "a" "b" "c" "d" "e"
> LRANGE q 0 2            ← 몇 개? a~b? a~c?
> LRANGE q 0 0
> LRANGE q 0 -1          ← 전체 조회 관용구
```
=> a b c 
---

### Q14. ★★ 음수 인덱스
```
> DEL q
> RPUSH q "a" "b" "c" "d" "e"
> LRANGE q -3 -1         ← 뒤에서 3개
> LRANGE q -1 -1         ← 마지막 1개
> LRANGE q -100 100      ← 범위 초과는?
```
=> 다 나옴
---

### Q15. ★★ 🪤 start > stop
```
> DEL q
> RPUSH q "a" "b" "c"
> LRANGE q 2 0           ← 시작이 끝보다 큼. 에러? 빈 배열?
```
=> 빈 배열
---
### Q16. ★★ LINDEX
```
> DEL q
> RPUSH q "a" "b" "c" "d"
> LINDEX q 0             ← 첫 원소
> LINDEX q -1            ← 마지막 원소
> LINDEX q 100           ← 범위 밖은? 에러? nil?
```
=> nil
> ⚠ LINDEX는 O(N). 큰 리스트 중간을 자주 LINDEX 하면 느리다 (이유는 §9).

---

### Q17. ★★★ 🪤 ⚠ LRANGE 0 -1 의 위험
```
> DEL big

> LRANGE big 0 -1
```
질문: 만약 `big`에 원소가 **100만 개**라면 `LRANGE big 0 -1`은 왜 위험한가?
(힌트: 단일 스레드 + 100만 개 직렬화)

## §4. 빈 리스트와 키 생명주기 ⚠🪤 (List 최대 함정)

### Q18. ★★★ 🪤 빈 리스트는 키가 사라진다
```
> DEL q
> RPUSH q "x"
> EXISTS q               ← 1
> LPOP q                 ← "x"
> EXISTS q               ← ??? 0? 1?
> LLEN q                 ← ???
> TYPE q                 ← ???
```
=> 0
=> 0 
=> none
> **Redis List/Set/Hash/ZSet 공통 규칙**: 컬렉션이 비면 **키 자체가 자동 삭제**된다.
> → 빈 리스트라는 상태는 존재하지 않는다.

---

### Q19. ★★ 🪤 모니터링 함정
```
> DEL mail:queue
> LLEN mail:queue        ← 0
> KEYS mail:*            ← mail:queue 키가 보이나?
```
질문: 큐가 비었을 때 `KEYS mail:queue`로 키를 찾으면 안 보인다. "큐가 없어진 건가?" 오해할 수 있다. 왜 이런 일이 생기나?
=> 콜렉션같은 경우는 비어있을때 키가 사라지기 떄문이다.
---

### Q20. ★★ TTL과 리스트
```
> DEL q
> RPUSH q "a" "b"
> EXPIRE q 100
> TTL q
> RPUSH q "c"            ← 원소 추가하면 TTL은?  (유지? 사라짐?)
> TTL q
```

> 함정: String의 SET은 TTL을 날리지만, List의 RPUSH/LPUSH는 **기존 키에 추가**이므로 TTL을 건드리지 않는다. (단, 키가 사라졌다 다시 생기면 TTL 없음)

---

### Q21. ★★★ 🪤 비웠다가 다시 채우면 TTL은?
```
> DEL q
> RPUSH q "a"
> EXPIRE q 100
> LPOP q                 ← 비어서 키 삭제됨
> RPUSH q "b"            ← 새 키 생성
> TTL q                  ← ??? (-1? 100?)
```
=> -1

## §5. LPUSHX / RPUSHX / LPOS — 조건부 삽입과 검색

### Q22. ★★ LPUSHX / RPUSHX (키 있을 때만)
```
> DEL q
> RPUSHX q "a"           ← 키 없는데 RPUSHX. 결과? (반환값?)
> EXISTS q
> RPUSH q "a"
> RPUSHX q "b"           ← 이제 키 있음. 성공?
> LRANGE q 0 -1
```
=> 성공
> 💡 "큐가 살아있을 때만 추가"하고 싶을 때. 새 큐를 만들고 싶지 않은 경우.

---

### Q23. ★★ LPOS — 값의 위치 찾기 (Redis 6.0.6+)
```
> DEL q
> RPUSH q "a" "b" "c" "b" "a"
> LPOS q "b"             ← 첫 번째 "b"의 인덱스?
> LPOS q "b" RANK -1     ← 뒤에서부터 첫 "b"?
> LPOS q "b" COUNT 0     ← 모든 "b"의 인덱스 (COUNT 0 = 전부)
> LPOS q "z"             ← 없는 값은?
```
=> 1, 3, [1, 3], nil

## §6. LINSERT / LSET / LREM / LTRIM — 수정

### Q24. ★★ LINSERT
```
> DEL q
> RPUSH q "a" "c"
> LINSERT q BEFORE "c" "b"     ← "c" 앞에 "b" 삽입
> LRANGE q 0 -1                 ← a b c?
> LINSERT q AFTER "c" "d"
> LRANGE q 0 -1
```
=> a b c, a b c d
---

### Q25. ★★ 🪤 LINSERT pivot 없으면?
```
> DEL q
> RPUSH q "a" "b"
> LINSERT q BEFORE "zzz" "new"  ← 존재하지 않는 pivot. 반환값?
> LINSERT nope BEFORE "a" "x"   ← 키 자체가 없으면? 반환값?
> LRANGE q 0 -1
```
=> 에러
=> 0 
---

### Q26. ★★ LSET (인덱스 덮어쓰기)
```
> DEL q
> RPUSH q "a" "b" "c"
> LSET q 1 "B"
> LRANGE q 0 -1                 ← a B c
> LSET q -1 "C"                 ← 음수 인덱스도 됨?
> LRANGE q 0 -1
```
=> 응 됨
---

### Q27. ★★ 🪤 LSET 범위 밖
```
> DEL q
> RPUSH q "a" "b"
> LSET q 5 "x"                  ← 인덱스 5는 없음. 에러? 자동 확장?
```
=> 에러
> String의 SETRANGE는 null 패딩으로 늘어났지만, LSET은? 직접 확인.

---

### Q28. ★★★ LREM — count 부호의 의미
```
> DEL q
> RPUSH q "a" "b" "a" "c" "a"   ← "a"가 3개
> LREM q 2 "a"                  ← count 2(양수): head(왼쪽)부터 2개 제거
> LRANGE q 0 -1                 ← 결과는?
```
=> b c a
---

### Q29. ★★★ 🪤 LREM 음수 count
```
> DEL q
> RPUSH q "a" "b" "a" "c" "a"
> LREM q -2 "a"                 ← count -2: tail(오른쪽)부터 2개 제거
> LRANGE q 0 -1                 ← 결과는? (Q28과 어디가 다른가)
```
=> a b c
---

### Q30. ★★ LREM count 0 (전부 제거)
```
> DEL q
> RPUSH q "a" "b" "a" "c" "a"
> LREM q 0 "a"                  ← count 0: 모든 "a" 제거
> LRANGE q 0 -1
> LREM q 0 "zzz"                ← 없는 값 제거 반환값?
```
=> b c
=> 0
> 💡 LREM의 반환값 = 실제로 제거한 개수.

---

### Q31. ★★★ 🔁 LTRIM — 범위만 남기고 자르기 (capped list 핵심)
```
> DEL q
> RPUSH q "a" "b" "c" "d" "e"
> LTRIM q 0 2                   ← 인덱스 0~2만 남김
> LRANGE q 0 -1                 ← 결과는?
```
=> a, b, c
---

### Q32. ★★★ 🪤 "최근 N개 유지" 관용구
```
> DEL recent
> LPUSH recent "item1"
> LTRIM recent 0 2              ← 최근 3개만 유지
> LPUSH recent "item2"
> LTRIM recent 0 2
> LPUSH recent "item3"
> LTRIM recent 0 2
> LPUSH recent "item4"          ← 4번째. item1이 밀려나야 함
> LTRIM recent 0 2
> LRANGE recent 0 -1            ← 무엇이 남았나?
```
=> [item4, item3, item2]
> 이 "LPUSH + LTRIM 0 N-1" 조합이 **최근 본 상품 / 최근 알림 / 피드 타임라인**의 표준 패턴.

---

### Q33. ★★ 🪤 LTRIM으로 비우기
```
> DEL q
> RPUSH q "a" "b" "c"
> LTRIM q 1 0                   ← start > stop. 어떻게 되나?
> EXISTS q                      ← 키는?
```
=> 사라짐

## §7. 블로킹 명령 🧱 BLPOP / BRPOP

### Q34. ★★ 🧱 BRPOP 즉시 케이스
```
> DEL q
> RPUSH q "a" "b"
> BRPOP q 5                     ← 데이터 있으면 바로? 반환 형태는?
```
=> q, b
> 함정: BRPOP/BLPOP 반환은 단일 값이 아니라 **(키 이름, 값)** 2-element 배열.

---

### Q35. ★★★ 🧱 BRPOP 블로킹 (두 터미널 필요)
```
[터미널 1]
> DEL q
> BRPOP q 30                    ← 데이터 없음. 여기서 멈춰서 대기

[터미널 2]
> LPUSH q "hello"               ← push 하는 순간

[터미널 1]
                                 ← 즉시 깨어나서 받아옴
```
질문: 일반 RPOP은 빈 큐에서 즉시 nil. BRPOP은 왜, 어떻게 다른가? (이 프로젝트가 BRPOP 쓰는 이유)

---

### Q36. ★★ 🧱 BRPOP 타임아웃
```
> DEL q
> BRPOP q 3                     ← 3초 기다려도 데이터 없으면? 반환값?
```
nil
---

### Q37. ★★★ 🧱 BRPOP 여러 키 — 우선순위 큐
```
> DEL high low
> RPUSH low "low-job"
> BRPOP high low 5              ← high 먼저 확인, 비었으면 low. 무엇이 나오나?
> RPUSH high "high-job"
> RPUSH low "low-job2"
> BRPOP high low 5              ← 이번엔?
```

> 💡 "VIP 큐 먼저, 일반 큐 나중" = `BRPOP vip normal 0`.

---

### Q38. ★★★ 🪤 🧱 BLPOP timeout 0
```
> DEL q
> BLPOP q 0                     ← timeout 0의 의미는? (즉시? 무한?)
```

> ⚠ `0`은 "즉시"가 아니라 **"무한 대기"**. 클라이언트가 영영 안 풀릴 수 있다.

## §8. 원자적 이동 — RPOPLPUSH / LMOVE / BLMOVE 🔁 (Reliable Queue의 심장)

### Q39. ★★★ RPOPLPUSH
```
> DEL src dst
> RPUSH src "a" "b" "c"
> RPOPLPUSH src dst             ← src 오른쪽에서 빼서 dst 왼쪽으로. 반환값?
> LRANGE src 0 -1
> LRANGE dst 0 -1
```
=> c
---

### Q40. ★★★ 🪤 RPOPLPUSH는 deprecated → LMOVE
```
> DEL src dst
> RPUSH src "a" "b" "c"
> LMOVE src dst RIGHT LEFT      ← RPOPLPUSH와 동일 (src RIGHT→dst LEFT)
> LRANGE src 0 -1
> LRANGE dst 0 -1
```
질문: `LMOVE src dst LEFT RIGHT`는 어떻게 동작할까? 방향 4조합을 직접 실험해보라.

---

### Q41. ★★★★ 🪤 같은 키로 RPOPLPUSH (회전)
```
> DEL ring
> RPUSH ring "a" "b" "c"
> RPOPLPUSH ring ring           ← src와 dst가 같으면? (오른쪽 끝을 왼쪽으로 회전)
> LRANGE ring 0 -1
> RPOPLPUSH ring ring
> LRANGE ring 0 -1
```

> 💡 같은 키로 돌리면 **원형 리스트(round-robin)**. 헬스체크 라운드로빈 등에 활용.

---

### Q42. ★★★★ 🧱 BLMOVE — Reliable Queue의 표준
```
[터미널 1]
> DEL mail:queue mail:queue:processing
> BLMOVE mail:queue mail:queue:processing LEFT RIGHT 30
                                 ← 큐에서 빼서 "처리중" 리스트로 백업하며 대기

[터미널 2]
> LPUSH mail:queue "user@test.com"

[터미널 1]
                                 ← 깨어나서 mail:queue:processing 으로 옮김
> LRANGE mail:queue:processing 0 -1     ← 작업이 백업됨
```
질문: 왜 그냥 BRPOP이 아니라 BLMOVE로 "처리중" 리스트에 백업하나? 워커가 여기서 죽으면 어떻게 복구하나?

---

### Q43. ★★★ 🔁 처리 완료 후 정리
```
> DEL mail:queue:processing
> RPUSH mail:queue:processing "user@test.com"
> LREM mail:queue:processing 1 "user@test.com"   ← 처리 끝났으니 백업에서 제거
> LLEN mail:queue:processing                      ← 0이면 모든 작업 정상 처리됨
```

> Reliable Queue 한 사이클: **BLMOVE(큐→처리중) → 작업 → LREM(처리중에서 제거)**.

## §9. 인코딩 / 운영 / 함정

### Q44. ★★★ 내부 인코딩 확인
```
> DEL small
> RPUSH small "a" "b" "c"
> OBJECT ENCODING small         ← listpack? quicklist?

> DEL big
> (큰 값이나 많은 원소를 넣어보면)
> RPUSH big <128개 넘게 또는 큰 값>
> OBJECT ENCODING big           ← quicklist로 바뀌는 경계 찾기
```

> 작은 리스트 = `listpack`(연속 메모리), 커지면 = `quicklist`(listpack 노드들의 이중 연결 리스트). 경계는 `list-max-listpack-size`(기본 128).

---

### Q45. ★★★ 🪤 WRONGTYPE
```
> DEL k
> SET k "i am a string"
> LPUSH k "x"                   ← String 키에 LPUSH. 어떤 에러?
> RPUSH k "y"
```

> Redis는 키 단위로 타입 고정. String 키에 List 명령 = WRONGTYPE.

---

### Q46. ★★ 🪤 블로킹 명령은 트랜잭션 안에서 블로킹 안 한다
```
> DEL q
> MULTI
> BRPOP q 10                    ← 트랜잭션 안의 BRPOP
> EXEC
```
질문: MULTI/EXEC 안에서 `BRPOP q 10`은 10초 기다릴까? (힌트: 트랜잭션은 멈출 수 없다)

---

### Q47. ★★ UNLINK로 큰 리스트 삭제
```
> DEL big
> RPUSH big a b c d e           ← (큰 리스트 흉내)
> UNLINK big                    ← DEL 대신 비동기 삭제
> EXISTS big
```

> ⚠ 원소 수십만~수백만 개 리스트를 `DEL`하면 단일 스레드가 그동안 막힌다. `UNLINK`로 비동기 회수.

### Q48. ★★ LMPOP (Redis 7.0+)
```
> DEL q1 q2
> RPUSH q2 "a" "b" "c"
> LMPOP 2 q1 q2 LEFT            ← q1,q2 중 첫 비어있지 않은 리스트에서 LEFT pop
> LMPOP 2 q1 q2 LEFT COUNT 2    ← 한 번에 2개
> LRANGE q2 0 -1
```

## §10. 종합 미션 🔁 — mail:queue 흐름 재현

### Q49. ★★★ 단순 큐 (현재 프로젝트 방식)
이 프로젝트의 현재 동작을 redis-cli로 재현하라.
```
[Producer — AuthService]
> DEL mail:queue
> LPUSH mail:queue "a@test.com"
> LPUSH mail:queue "b@test.com"
> LPUSH mail:queue "c@test.com"
> LLEN mail:queue                ← 대기 3건

[Consumer — EmailMultiWorker (BRPOP)]
> RPOP mail:queue                ← 누가 먼저? (FIFO 확인)
> RPOP mail:queue
> RPOP mail:queue
> EXISTS mail:queue              ← 다 처리하면 키는?
```
=> a@test.com
=> 0
---

### Q50. ★★★★ 🪤 유실 시나리오 재현
현재 방식의 약점을 직접 보라.
```
> DEL mail:queue
> LPUSH mail:queue "important@test.com"
> RPOP mail:queue                ← 워커가 꺼냄. "important@..." 받음
                                  ← 이 순간 워커가 죽었다고 가정 (DB 저장 못 함)
> LLEN mail:queue                ← 0. 큐에도 없고, 처리도 안 됨 = 영구 유실!
```
질문: 이 메일은 어디에도 없다. 어떻게 막을 수 있을까? (→ Q51)

---

### Q51. ★★★★★ 🔁 Reliable Queue 한 사이클 (해법)
```
[1. 안전하게 꺼내기 — 처리중 리스트에 백업]
> DEL mail:queue mail:queue:processing
> LPUSH mail:queue "important@test.com"
> LMOVE mail:queue mail:queue:processing RIGHT LEFT
                                 ← 큐에서 빼면서 동시에 백업
> LLEN mail:queue                ← 0 (큐에선 빠짐)
> LRANGE mail:queue:processing 0 -1   ← 여기 백업돼 있음

[2. 워커가 죽어도 처리중 리스트에 남아있음 → 복구 가능]

[3. 처리 성공 후 백업에서 제거]
> LREM mail:queue:processing 1 "important@test.com"
> LLEN mail:queue:processing     ← 0. 안전하게 완료
```

질문:
- (a) 1번과 3번 사이에 워커가 죽으면, 다른 워커는 어디를 보고 복구하나?
- (b) 복구된 작업을 다시 처리하면 메일이 2번 갈 수 있다. 어떻게 막나? (힌트: 멱등성/dedup)

---

### Q52. ★★★ 🔁 우선순위 큐 미션
VIP 회원 메일을 먼저 보내고 싶다.
```
> DEL mail:vip mail:normal
> LPUSH mail:normal "normal1@test.com"
> LPUSH mail:normal "normal2@test.com"
> LPUSH mail:vip "vip@test.com"
> BRPOP mail:vip mail:normal 5   ← 무엇이 먼저 나오나?
> BRPOP mail:vip mail:normal 5
> BRPOP mail:vip mail:normal 5
```
=>vip@test.com
