# List 실습 — 개념 정리 & 실무 활용 요약

> 74문항 실습 후 가볍게 읽으며 머릿속 정리용. 명령어 문법보다 **"왜 이 명령어가 있고, 실무에서 어떻게 쓰이는가"**에 무게.
> List는 한 문장으로: **"순서가 보장되는 값들의 줄(line). 양끝이 빠르다."**

---

## §0. List란 무엇인가 — 한 장 정리

```
        head                              tail
         │                                 │
   LPUSH ▶ [ A ][ B ][ C ][ D ][ E ] ◀ RPUSH
   LPOP  ◀                           ▶ RPOP
```

- **내부 구조**: `quicklist` — 작은 `listpack`(연속 메모리 배열) 조각들을 **이중 연결 리스트**로 엮은 것.
  - 그래서 **양끝(head/tail) 삽입·삭제는 O(1)** — 큐/스택에 최적.
  - 반대로 **가운데 접근(LINDEX/LINSERT/LSET/LREM)은 O(N)** — 노드를 따라가야 함.
- **순서 보장**: 넣은 순서가 유지된다. (Set은 순서 없음, ZSet은 score 정렬)
- **중복 허용**: 같은 값을 여러 번 넣을 수 있다. (Set은 중복 불가)
- **빈 컬렉션 = 키 삭제**: 원소가 0개가 되면 키 자체가 사라진다. List에 "빈 상태"는 없다.

> 💡 String이 "값 1칸"이라면, List는 "값 여러 칸이 순서대로 줄 선 것". **큐가 필요하면 거의 항상 List가 1순위 후보.**

## §1. 삽입 — LPUSH / RPUSH / LPUSHX / RPUSHX

### 문법 한눈에

| 명령어 | 동작 | 반환값 |
|---|---|---|
| `LPUSH k v [v...]` | head(왼쪽)에 삽입 | 삽입 후 리스트 길이 |
| `RPUSH k v [v...]` | tail(오른쪽)에 삽입 | 삽입 후 리스트 길이 |
| `LPUSHX k v` | **키가 있을 때만** head 삽입 | 길이 (없으면 0) |
| `RPUSHX k v` | **키가 있을 때만** tail 삽입 | 길이 (없으면 0) |

### 핵심 포인트

- **여러 값 push 시 순서 주의** — `LPUSH k a b c` → 리스트는 `[c, b, a]`. 인자를 왼쪽에 차례로 꽂으니 **마지막 인자가 맨 앞**. `RPUSH k a b c` → `[a, b, c]` (직관적).
- **반환값은 길이** — 카운터 겸용으로 쓸 수 있다 (push 후 길이로 큐 깊이 즉시 파악).
- **PUSHX는 "큐 살아있을 때만"** — 새 큐를 실수로 만들고 싶지 않을 때. (예: 세션이 살아있는 동안만 이벤트 적재)
- **키가 없으면 자동 생성** — LPUSH/RPUSH는 키가 없으면 새 리스트를 만든다 (PUSHX 제외).

## §2. 추출 — LPOP / RPOP

### 문법 한눈에

| 명령어 | 동작 | 비고 |
|---|---|---|
| `LPOP k [count]` | head에서 추출 | count는 Redis 6.2+ |
| `RPOP k [count]` | tail에서 추출 | count는 Redis 6.2+ |

### 핵심 포인트

- **빈 큐에서 POP → nil** (에러 아님). 안심하고 호출 가능.
- **count 옵션** — `LPOP k 10`으로 한 번에 10개 (배치 소비). 남은 게 적으면 있는 만큼만 반환. 없으면 nil.
- **마지막 원소 POP → 키 삭제** — POP으로 리스트가 비면 키가 사라진다 (§0 규칙).

### 큐 vs 스택 — 방향 조합 (가장 중요)

| 조합 | 자료구조 | 동작 |
|---|---|---|
| `LPUSH` + `RPOP` | **FIFO 큐** | 먼저 넣은 게 먼저 나옴 ← **이 프로젝트 mail:queue** |
| `RPUSH` + `LPOP` | **FIFO 큐** | (위와 같음, 방향만 반대) |
| `LPUSH` + `LPOP` | **LIFO 스택** | 마지막 넣은 게 먼저 나옴 |
| `RPUSH` + `RPOP` | **LIFO 스택** | (위와 같음) |

> 💡 **"같은 쪽이면 스택, 반대 쪽이면 큐."** 이 한 줄만 외우면 평생 안 헷갈린다.

## §3. 조회 — LLEN / LRANGE / LINDEX / LPOS (비우지 않고 보기)

### 문법 한눈에

| 명령어 | 동작 | 복잡도 | 비고 |
|---|---|---|---|
| `LLEN k` | 길이 | O(1) | 없는 키는 0 |
| `LRANGE k start stop` | 구간 조회 | O(S+N) | **양끝 inclusive**, 음수 인덱스 OK |
| `LINDEX k i` | 단건 조회 | O(N) | 범위 밖은 nil |
| `LPOS k v [RANK r] [COUNT n]` | 값의 위치 | O(N) | 6.0.6+ |

### 핵심 포인트

- **LRANGE는 양끝 포함** — `LRANGE k 0 2`는 3개(0,1,2). `LRANGE k 0 -1`은 전체 조회 관용구.
- **음수 인덱스** — `-1`=마지막, `-3 -1`=뒤 3개. `start > stop`이면 빈 배열(에러 아님).
- **🚨 `LRANGE k 0 -1`은 큰 리스트에서 위험** — 원소 100만 개면 전부 직렬화해서 네트워크로 쏟아냄. 단일 스레드 블로킹 + 대역폭 폭발. → 페이지네이션(`LRANGE k 0 99`)으로.
- **LINDEX는 O(N)** — quicklist 노드를 따라가므로 가운데 접근이 느리다. 큰 리스트 중간을 자주 인덱싱하면 List가 잘못된 선택일 수 있음 (→ Sorted Set/Hash 고려).

## §4. 빈 리스트와 키 생명주기 ⚠ (List 최대 함정)

```
RPUSH q "x"   →  q 존재 (EXISTS=1)
LPOP q        →  q 비어서 자동 삭제 (EXISTS=0, TYPE=none, LLEN=0)
```

### 핵심 포인트

- **컬렉션이 비면 키가 자동 삭제** — List/Set/Hash/ZSet 공통. "빈 리스트" 상태는 존재하지 않는다.
- **모니터링 함정** — 큐가 비면 `KEYS mail:queue`로 안 잡힌다. "큐 설정이 사라졌나?" 착각 금지. 비어서 없는 것뿐.
- **TTL 동작 차이** — String의 `SET`은 TTL을 날리지만, List의 `LPUSH/RPUSH`는 **기존 키에 추가**라 TTL 유지. 단 **비었다가 다시 생긴 키는 TTL 없음**(새 키니까).
- **실무 영향** — "큐 길이로 헬스체크"할 때 `LLEN`은 안전(0 반환), `EXISTS`는 큐가 비면 0이라 오해 소지.

## §5. 수정 — LINSERT / LSET / LREM / LTRIM

### 문법 한눈에

| 명령어 | 동작 | 복잡도 | 반환값 |
|---|---|---|---|
| `LINSERT k BEFORE\|AFTER pivot v` | pivot 앞/뒤 삽입 | O(N) | 길이 (pivot없음 -1, 키없음 0) |
| `LSET k i v` | 인덱스 덮어쓰기 | O(N) | OK (범위밖 에러) |
| `LREM k count v` | 값으로 삭제 | O(N) | 제거한 개수 |
| `LTRIM k start stop` | 구간만 남기고 자름 | O(N) | OK |

### 핵심 포인트 — LREM count 부호 (헷갈림 1순위)

| count | 방향 | 동작 |
|---|---|---|
| `count > 0` | head(왼쪽)부터 | 앞에서 count개 제거 |
| `count < 0` | tail(오른쪽)부터 | 뒤에서 \|count\|개 제거 |
| `count = 0` | 전체 | 일치하는 값 **전부** 제거 |

### LTRIM — capped list의 핵심

- `LTRIM k 0 (N-1)`은 **앞 N개만 남기고 나머지 잘라냄**. `start > stop`이면 전체 삭제(키 사라짐).
- **"LPUSH + LTRIM 0 N-1"** = 최근 N개만 유지하는 **고정 크기 리스트(capped list)**. 메모리 자동 제한.

### 실무 활용

```
[최근 본 상품 — 최근 20개만]
LPUSH recent:user:42 "product:789"
LTRIM recent:user:42 0 19          ← 21번째부터 자동으로 밀려남

[작업 취소 — 큐에서 특정 작업 빼기]
LREM mail:queue 1 "spam@test.com"  ← 큐에서 해당 메일 1건 제거 (O(N) 비용 주의)
```

> 🚨 LSET/LINSERT/LREM은 **O(N)**. 큰 리스트에서 남발하면 단일 스레드를 잡아먹는다. 큐는 보통 "양끝만 건드리는" 게 정석.

## §6. 블로킹 — BLPOP / BRPOP / BLMOVE 🧱

### 문법 한눈에

| 명령어 | 동작 | 반환 |
|---|---|---|
| `BLPOP k [k...] timeout` | head 블로킹 팝 | (키, 값) 또는 nil(타임아웃) |
| `BRPOP k [k...] timeout` | tail 블로킹 팝 | (키, 값) 또는 nil |
| `BLMOVE src dst <f> <t> timeout` | 블로킹 이동 | 옮긴 값 또는 nil |
| `BLMPOP timeout numkeys k... <dir>` | 다중 키 블로킹 팝 (7.0+) | (키, 값들) |

### 핵심 포인트

- **블로킹의 본질** — 빈 큐에서 즉시 nil을 주는 RPOP과 달리, BRPOP은 **데이터가 들어올 때까지 클라이언트를 재운다**. push 되는 순간 깨어남.
  - → **폴링 제거**: `while(true){ RPOP }`로 CPU를 태우지 않고, push 이벤트에 반응. **이 프로젝트가 BRPOP 쓰는 이유.**
  - → 서버는 안 멈춘다. **대기하는 건 그 클라이언트뿐**. 다른 클라이언트는 정상 처리.
- **반환은 (키, 값) 2-element** — 어느 큐에서 나왔는지 알려준다. 단일 값 기대하고 짜면 버그.
- **여러 키 = 우선순위** — `BRPOP vip normal 0`은 vip 먼저 확인, 비었으면 normal. **앞 키 우선.**
- **🪤 timeout 0 = 무한 대기** (즉시 아님). 운영에선 적절한 타임아웃을 줘서 주기적으로 깨어나 헬스체크/인터럽트 확인하게 하는 게 보통.
- **🪤 트랜잭션/Lua 안에서는 블로킹 안 함** — MULTI/EXEC·스크립트는 멈출 수 없으므로, 그 안의 BRPOP은 데이터 없으면 즉시 nil처럼 동작.

## §7. 원자적 이동 — RPOPLPUSH / LMOVE / BLMOVE 🔁 (Reliable Queue의 심장)

### 문법 한눈에

| 명령어 | 동작 | 비고 |
|---|---|---|
| `RPOPLPUSH src dst` | src tail → dst head | **6.2부터 deprecated** |
| `LMOVE src dst <from> <to>` | 일반화된 이동 (방향 4조합) | 6.2+ 표준 |
| `BRPOPLPUSH src dst timeout` | 블로킹 RPOPLPUSH | 6.2부터 deprecated |
| `BLMOVE src dst <from> <to> timeout` | 블로킹 LMOVE | 6.2+ 표준 |

`<from>`/`<to>` = `LEFT`/`RIGHT`. `LMOVE src dst RIGHT LEFT` = RPOPLPUSH와 동일.

### 핵심 포인트

- **"빼기 + 넣기"가 원자적** — 두 리스트 사이를 한 명령으로 옮긴다. 중간에 끊기지 않음.
- **Reliable Queue(신뢰성 큐)의 핵심** — 그냥 BRPOP은 꺼낸 순간 값이 사라져서, 워커가 죽으면 유실. BLMOVE로 **"처리중(processing)" 리스트에 백업**하면서 꺼내면, 워커가 죽어도 처리중 리스트에 남아 복구 가능.
- **같은 키 = round-robin** — `LMOVE ring ring RIGHT LEFT`는 오른쪽 끝을 왼쪽으로 돌리는 회전. 라운드로빈 스케줄링에 쓸 수 있음.

### Reliable Queue 한 사이클

```
1. 꺼내며 백업:  BLMOVE mail:queue mail:queue:processing LEFT RIGHT 30
2. 작업 수행:    (이메일 발송 + DB 저장)
3. 백업 제거:    LREM mail:queue:processing 1 {처리한 값}

→ 1~3 사이에 워커가 죽으면? mail:queue:processing 에 남아있음.
→ 별도 reaper가 처리중 리스트의 stale 메시지를 다시 mail:queue로 되돌림.
```

> ⚠ 단, "복구 = 재처리"이므로 **메일이 2번 갈 수 있다** → 컨슈머는 **멱등성(dedup 키)** 이 의무. (자세히는 `02-실무.md`, `../01-string/부록-멱등성.md`)

## §8. 운영·인코딩 — OBJECT ENCODING / UNLINK / WRONGTYPE

### 핵심 포인트

- **인코딩**: 작은 리스트는 `listpack`(연속 메모리, 캐시 친화적), 커지면 `quicklist`. 경계는 `list-max-listpack-size`(기본 128개 또는 노드당 크기). 작게 유지하면 메모리 효율 ↑.
- **big key 주의**: 원소 수십만~수백만 개 리스트는 big key. `DEL`하면 동기 회수로 블로킹 → **`UNLINK`로 비동기 삭제**. `LRANGE 0 -1`도 금지(전부 직렬화).
- **WRONGTYPE**: String 키에 LPUSH/RPUSH 등은 에러. 키 단위 타입 고정. → 네이밍 컨벤션(`mail:queue` List, `auth:{email}` String)으로 사전 분리.

### 실무 활용 — 큐 모니터링

```
LLEN mail:queue            ← 대기 작업 수 (쌓이면 컨슈머 스케일아웃 신호)
LLEN mail:queue:processing ← 처리중 작업 수 (계속 안 줄면 stale/장애 의심)
```

## 🎯 List 핵심 패턴 8개 (실무 빈출)

암기/체득해야 할 패턴만 추리면:

1. **`LPUSH` + `RPOP/BRPOP`** — FIFO 메시지 큐 (이 프로젝트 mail:queue)
2. **`BRPOP key timeout`** — 폴링 없는 블로킹 소비 (CPU 절약)
3. **`BLMOVE 큐 처리중` + `LREM`** — Reliable Queue (메시지 유실 방지) ⭐ 실무 핵심
4. **`LPUSH` + `LTRIM 0 N-1`** — 최근 N개 (capped list): 최근 본 상품, 알림, 로그
5. **`LPUSH feed` + `LTRIM`** — Fan-out 타임라인 (팔로워 피드)
6. **`BRPOP vip normal`** — 우선순위 큐 (앞 키 우선)
7. **`LPOP key count`** — 배치 소비 (한 번에 N개)
8. **`LMOVE`(같은 키)** — round-robin 회전

---

## ⚠️ 운영에서 깨지기 쉬운 약속 6가지

1. **`LRANGE k 0 -1`을 큰 리스트에 쓰지 않는다** — 페이지네이션(`0 99`)으로.
2. **단순 BRPOP 큐는 메시지를 유실한다** — 내구성이 필요하면 BLMOVE + processing + 멱등성.
3. **big key 리스트는 `UNLINK`로 지운다** — `DEL`은 블로킹.
4. **빈 리스트는 키가 사라진다** — 모니터링/존재 체크 시 혼동 금지.
5. **LSET/LINSERT/LREM(O(N))을 큐 hot path에서 남발하지 않는다** — 큐는 양끝만.
6. **`timeout 0`은 무한 대기** — 운영에선 유한 타임아웃 권장.

## 📌 면접에서 잘 나오는 비교 질문

| 질문 | 답 |
|---|---|
| LPUSH vs RPUSH | head vs tail 삽입. 큐는 한쪽 push + 반대쪽 pop. |
| 큐 vs 스택 | 반대 쪽 = FIFO, 같은 쪽 = LIFO. |
| RPOP vs BRPOP | RPOP 즉시 nil, BRPOP 데이터 올 때까지 블로킹(폴링 제거). |
| RPOPLPUSH vs LMOVE | 동작 동일, RPOPLPUSH는 6.2부터 deprecated. LMOVE는 방향 자유. |
| 단순 큐 vs Reliable Queue | BRPOP은 유실 가능, BLMOVE+processing은 복구 가능. |
| List 큐 vs Kafka | List는 가볍지만 컨슈머그룹/재소비/ack 없음. 대규모/내구성은 Kafka. |
| List 큐 vs Redis Stream | Stream은 컨슈머그룹·ack·재처리 내장. 진짜 신뢰성 큐는 Stream. |
| LINDEX는 왜 느린가 | quicklist 노드를 따라가는 O(N). 양끝만 O(1). |
