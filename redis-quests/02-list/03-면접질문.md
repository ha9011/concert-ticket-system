> 각 답은 30초~1분 내 말할 수 있는 분량.
>

> 종이로 가리거나, 친구한테 질문만 읽어달라 부탁해도 좋음.
>
> 이 프로젝트의 실제 코드를 기준으로 한다:
> - **Producer**: `AuthService.java:85` → `LPUSH mail:queue {email}` (가입 축하 메일 큐 적재)
> - **Consumer**: `EmailMultiWorker.java:44` → `BRPOP mail:queue 10` (디스패처 1 + 워커풀 3)

## A. 기본 개념

### Q1. Redis List는 어떤 자료구조인가? 무엇에 좋은가?

✅ **답**:

> **순서가 보존되는 문자열들의 시퀀스(linked list 계열)**. 양 끝(head/tail) 삽입·삭제가 **O(1)** 이라 **큐(FIFO)와 스택(LIFO)**, **최근 N개 로그**, **메시지 큐**에 딱 맞음.
>
> 핵심은 *"양끝은 빠르고 가운데는 느리다"*. `LINDEX`·`LINSERT`·`LREM`처럼 위치로 접근하는 연산은 **O(N)** 이라 List를 인덱스 배열처럼 쓰면 안 됨.

> 💡 꼬리질문 대비: "그럼 가운데 접근이 잦으면?" → List 대신 ZSet(점수=순서)이나 Hash를 고려.

---

### Q2. List의 내부 인코딩은? quicklist / listpack이 뭔가?

✅ **답**:

- **작은 List** → **listpack** 하나에 통째로 저장 (Redis 7.0+, 그 이전엔 ziplist). 연속된 메모리 블록이라 캐시 친화적·메모리 효율적.
- **커지면** → **quicklist** 로 전환. quicklist는 **listpack 노드들을 잇는 doubly linked list**. 즉 "작은 배열 조각들의 연결 리스트".

전환 임계값은 `list-max-listpack-size`(노드당 원소 수 또는 바이트). 이 하이브리드 구조 덕에:
- 양끝(head/tail) 노드만 만지면 되니 **LPUSH/RPUSH/LPOP/RPOP이 O(1)**
- 포인터 + 압축 블록이라 순수 linked list보다 **메모리 오버헤드가 작음**

> 💡 "왜 그냥 doubly linked list가 아니라 quicklist냐?" → 노드마다 포인터 16~24바이트가 붙는 순수 linked list는 작은 값 수백만 개에 메모리 낭비가 큼. listpack 노드로 묶어 포인터 수를 줄인 절충안.

---

### Q3. 왜 양끝 연산은 O(1)인데 LINDEX는 O(N)인가?

✅ **답**:

> List는 **양끝 포인터(head/tail)를 직접 들고 있음** → 끝에서의 삽입·삭제는 포인터 한두 개만 갱신하면 됨 → **O(1)**.
>
> 반면 `LINDEX k 5000`은 임의 위치를 **순차 탐색**해야 함. quicklist는 어느 노드에 몇 번째가 있는지 바로 못 가므로 노드를 훑어 내려감 → **O(N)** (정확히는 가까운 끝에서부터 탐색해 min(i, N-i)).

→ **결론**: List는 "끝에서 넣고 끝에서 빼는" 워크로드에 최적화된 구조. 랜덤 액세스는 안티패턴.

---

### Q4. 빈 List가 되면 키는 어떻게 되나?

✅ **답**:

> **마지막 원소를 빼면 키 자체가 자동 삭제된다.** Redis는 빈 컬렉션을 두지 않음 (List/Set/Hash/ZSet 공통).

영향:
- `LPOP`/`RPOP`/`LREM`/`LTRIM` 등으로 원소가 0이 되면 `EXISTS k` → 0, `TYPE k` → `none`.
- 그래서 **큐가 비면 키가 사라졌다가, 다음 `LPUSH` 때 다시 생김**. 모니터링·TTL 설정 시 이 점을 전제해야 함.

> 💡 꼬리질문: "큐 키에 TTL을 걸면?" → 비어서 키가 사라지면 TTL도 함께 사라짐. 큐 자체엔 보통 TTL을 안 걸고, 길이(`LLEN`) 0을 "비었다"로 다룸.

## B. 명령어 비교

### Q5. `LPUSH` vs `RPUSH` 차이는? 큐 방향은 어떻게 정하나?

✅ **답**:

- `LPUSH` = **head(왼쪽/앞)** 삽입, `RPUSH` = **tail(오른쪽/뒤)** 삽입. 둘 다 반환값은 **연산 후 리스트 길이**.
- **방향 자체는 의미가 없고, 넣는 쪽과 빼는 쪽의 조합이 큐냐 스택이냐를 결정**:

| 패턴 | 의미 |
|---|---|
| `LPUSH` + `RPOP` | **FIFO 큐** (한쪽으로 넣고 반대쪽에서 뺌) — 이 프로젝트가 이 조합 |
| `RPUSH` + `LPOP` | FIFO 큐 (방향만 반대, 동일) |
| `LPUSH` + `LPOP` | **LIFO 스택** (같은 쪽) |

> 💡 함정: `LPUSH k a b c`는 `[c, b, a]` 순서가 됨. **여러 값을 한 번에 넣으면 인자 역순으로 들어감** (각 값을 순서대로 head에 밀어넣기 때문). 순서가 중요하면 RPUSH로 넣거나 한 개씩 push.

---

### Q6. 이 프로젝트는 `LPUSH` + `BRPOP` 조합이다. 왜 FIFO가 되나?

✅ **답**:

> 생산자가 **head(왼쪽)로 넣고**(`LPUSH`), 소비자가 **tail(오른쪽)에서 뺀다**(`BRPOP` = `RPOP`의 블로킹 버전).
>
> 먼저 들어간 메시지일수록 tail에 가깝게 밀려나므로 **먼저 빠짐 → FIFO**.

```
LPUSH:  [c] ← [b] ← [a]          (a가 가장 먼저 들어옴)
리스트:  head [c, b, a] tail
RPOP:                  → a 먼저   (가장 먼저 들어온 a가 먼저 나감)
```

→ `AuthService`가 `LPUSH mail:queue`, `EmailMultiWorker`가 `BRPOP mail:queue 10`. 가입 순서대로 메일이 처리됨.

> 💡 꼬리질문: "LPUSH + LPOP으로 바꾸면?" → 같은 쪽이라 LIFO(스택)가 되어 **늦게 가입한 사람 메일이 먼저** 나감. 큐 의도와 어긋남.

---

### Q7. `LPOP` vs `RPOP`, 그리고 `count` 인자는?

✅ **답**:

- `LPOP k` = head 1개, `RPOP k` = tail 1개 제거 후 반환. 키 없으면 `nil`.
- **Redis 6.2+** 부터 `LPOP k count` 지원 → **한 번에 N개** 꺼냄 (배열 반환). round trip 절약.

```
> RPUSH q a b c d e
> LPOP q 2        → ["a", "b"]   # 한 번에 2개
```

> 💡 배치 소비 시 `LPOP k 100`이 100번 `LPOP`보다 빠름 (네트워크 왕복 1회). 단 꺼낸 순간 소멸은 동일 → 신뢰성은 별개 문제(D 섹션).

---

### Q8. `RPOPLPUSH` vs `LMOVE` 차이는?

✅ **답**:

> 둘 다 **한 리스트에서 빼서 다른(또는 같은) 리스트로 원자적으로 이동**. `RPOPLPUSH src dst` = src의 tail을 빼서 dst의 head로.

| | RPOPLPUSH | LMOVE |
|---|---|---|
| 등장 | 구버전 | **6.2+** |
| 방향 | tail→head 고정 | `LEFT|RIGHT` × `LEFT|RIGHT` **자유 지정** |
| 상태 | **6.2에서 deprecated** | 권장 |

```
LMOVE src dst LEFT RIGHT   # src의 head를 빼서 dst의 tail로
LMOVE q q RIGHT LEFT       # 같은 리스트면 회전(rotate) — 원형 큐
```

블로킹 버전: `BRPOPLPUSH`(deprecated) → **`BLMOVE`**.

> 💡 핵심 용도: **Reliable Queue**. 작업 큐에서 빼는 동시에 "처리 중" 큐로 원자 이동 → 워커가 죽어도 메시지가 안 사라짐 (D 섹션 Q16).

---

### Q9. `BLPOP`/`BRPOP`은 어떻게 동작하나? `LPOP` 폴링과 뭐가 다른가?

✅ **답**:

- `BRPOP key [key...] timeout` = **리스트가 비어 있으면 원소가 들어올 때까지 클라이언트를 블로킹**. 데이터가 오면 즉시 반환. `timeout 0`이면 무한 대기.
- 반환은 **(키 이름, 값) 2-element 배열** — 여러 키를 감시할 수 있어 어느 키에서 나왔는지 알려줌. **앞쪽 키 우선**.

**`LPOP` 폴링 대비 장점**:

| | LPOP 폴링 (while + sleep) | BRPOP |
|---|---|---|
| 빈 큐일 때 | 계속 돌며 CPU·네트워크 낭비 | 조용히 대기 |
| 지연 | sleep 주기만큼 늦음 | 데이터 오면 즉시 |
| 코드 | 루프+슬립 직접 | 한 줄 |

```java
// EmailMultiWorker.java:44 — Spring Data Redis의 rightPop(key, timeout)이 BRPOP
String email = redisTemplate.opsForList().rightPop(MAIL_QUEUE, Duration.ofSeconds(10));
```

> 💡 함정: 블로킹 명령은 **MULTI/EXEC·Lua 안에서는 블로킹하지 않음** → 비어 있으면 즉시 `nil` 반환/실패. 트랜잭션 안에서는 "대기"가 불가능하기 때문(Q19/Q23 연결).

---

### Q10. `LRANGE`의 인덱스 규칙은? `LRANGE k 0 -1`은?

✅ **답**:

- `LRANGE k start stop` — **start, stop 양끝 모두 포함(inclusive)**.
- **음수 인덱스** 지원: `-1`=마지막, `-2`=뒤에서 두 번째.
- `LRANGE k 0 -1` = **처음부터 끝까지 = 전체 조회**.

```
> RPUSH q a b c d e
> LRANGE q 0 2    → [a, b, c]   # 0,1,2 모두 포함
> LRANGE q -2 -1  → [d, e]      # 뒤에서 2개
```

> 💡 **운영 경고**: `LRANGE k 0 -1`은 **O(N)** 이고 큰 리스트면 단일 스레드를 오래 점유 + 응답 폭증. 모니터링/디버깅 때도 `LRANGE q 0 9`처럼 일부만 봐야 함 (F 섹션 Q24).

---

### Q11. `LTRIM`은 무엇을 하나? "최근 N개" 유지에 어떻게 쓰나?

✅ **답**:

> `LTRIM k start stop` = **지정 범위만 남기고 나머지를 잘라버림**. 범위 밖은 전부 삭제.

**capped list (고정 길이) 패턴** — "최근 100개 활동 로그":

```
LPUSH recent:user:42 <new>     # 최신 항목을 head에 추가
LTRIM recent:user:42 0 99      # 앞 100개만 남기고 나머지 버림
```

→ 이 둘을 한 번에 하면 리스트가 **항상 최대 100개**로 유지됨 (메모리 무한 증식 방지).

> 💡 시간복잡도는 잘려나가는 원소 수에 비례해 **O(N)**. 한 번에 수십만 개를 trim하면 부담 → 매 push마다 조금씩 trim하는 게 안전.

---

### Q12. `LREM`의 `count` 부호는 무슨 의미인가?

✅ **답**:

> `LREM k count value` — **value와 같은 원소를 제거**. count의 **부호가 탐색 방향**, **절댓값이 개수**:

| count | 동작 |
|---|---|
| `count > 0` | **head(앞)부터** count개 제거 |
| `count < 0` | **tail(뒤)부터** |count|개 제거 |
| `count = 0` | **일치하는 전부** 제거 |

```
> RPUSH q a b a c a
> LREM q 2 a     → 앞에서 a 2개 제거 → [b, c, a]
> LREM q -1 a    → 뒤에서 a 1개 제거 → [b, c]   (앞 예시 결과 기준)
```

> 💡 O(N) 연산. Reliable Queue에서 processing 큐의 특정 메시지를 ack(제거)할 때 `LREM processing 1 <msg>` 형태로 쓰임 (D 섹션).

---

### Q13. `LINDEX`/`LSET`/`LINSERT`는 왜 조심해야 하나?

✅ **답**:

위치 기반 명령들은 전부 **O(N)** 이고 엣지케이스가 있음:

| 명령 | 동작 | 주의 |
|---|---|---|
| `LINDEX k i` | i번째 값 조회 | O(N), 음수 인덱스 가능 |
| `LSET k i v` | i번째를 v로 교체 | **범위 밖 인덱스면 에러** (`index out of range`) |
| `LINSERT k BEFORE|AFTER pivot v` | pivot 앞/뒤 삽입 | **pivot 없으면 -1 반환**, **키 자체 없으면 0**, O(N) 탐색 |

```
> LINSERT q BEFORE b X    # b 앞에 X 삽입, b 없으면 -1
```

> 💡 핵심: List를 "배열"처럼 인덱스로 휘젓는 설계는 모두 O(N)이라 핫패스에 부적합. 그런 접근이 필요하면 자료구조 선택을 다시 본다(Q1·Q3).

---

### Q14. `LPOS`, `LMPOP`은 언제 쓰나?

✅ **답**:

- **`LPOS k value`** (6.0.6+) — value의 **인덱스를 찾음**. `RANK`(몇 번째 일치), `COUNT`(여러 개 인덱스) 옵션. 기존엔 `LRANGE`로 받아와 앱에서 찾던 걸 서버에서 처리.
- **`LMPOP numkeys key... LEFT|RIGHT [COUNT n]`** / **`BLMPOP`** (7.0+) — **여러 키 중 첫 번째로 비어있지 않은 리스트**에서 pop. 여러 큐를 우선순위로 감시할 때.

```
LMPOP 2 q:high q:low LEFT COUNT 10
# q:high에 있으면 거기서, 비었으면 q:low에서 — 우선순위 큐(G 섹션)
```

> 💡 `BLPOP key1 key2`도 다중 키 감시지만 **키마다 1개씩**만, `LMPOP`은 **COUNT로 여러 개 + 방향 지정**이 가능해 더 유연.

## C. 큐 패턴

### Q15. Redis List로 메시지 큐를 어떻게 만드나? (이 프로젝트 구조)

✅ **답**:

> **생산자는 한쪽 끝에 `LPUSH`, 소비자는 반대쪽 끝에서 `BRPOP`** → FIFO 작업 큐.

이 프로젝트:
```
[api-server]  AuthService.java:85
  redisTemplate.opsForList().leftPush("mail:queue", email);   // LPUSH (생산)

[queue-server]  EmailMultiWorker.java:44
  redisTemplate.opsForList().rightPop("mail:queue", Duration.ofSeconds(10));  // BRPOP (소비)
```

구조: **디스패처 스레드 1개**가 `BRPOP`으로 꺼내 → **워커풀 스레드 3개**가 `ExecutorService`로 동시 처리.

> 💡 왜 디스패처를 1개만? → `BRPOP` 자체가 블로킹이라 한 스레드가 줄 서서 꺼내고, 무거운 처리(메일 발송)만 워커풀로 분산. 꺼내기(I/O 대기)와 처리(작업)를 분리한 패턴.

---

### Q16. 여러 컨슈머가 같은 큐를 `BRPOP`하면 메시지가 중복되나?

✅ **답**:

> **아니다. `RPOP`/`BRPOP`은 원자적 pop이라 한 메시지는 정확히 한 컨슈머에게만 간다.** Redis가 단일 스레드로 명령을 직렬화하므로 두 컨슈머가 같은 원소를 동시에 가져갈 수 없음.

→ 그래서 List 큐는 **워커를 여러 개 띄워 수평 확장**하기 좋음 (work queue / competing consumers 패턴). 단, 이건 *각 메시지를 한 워커가 처리*하는 모델이지, Pub/Sub처럼 *모든 구독자에게 broadcast*하는 게 아님.

> 💡 꼬리질문: "그럼 fan-out(같은 메시지를 N개 컨슈머 모두에게)이 필요하면?" → List 큐로는 부적합. Pub/Sub 또는 Stream의 컨슈머 그룹(또는 컨슈머별 List N개에 LPUSH)이 답(E 섹션).

---

### Q17. `BRPOP`으로 꺼낸 메시지를 처리하다 워커가 죽으면? 이게 List 큐의 약점이다.

✅ **답**:

> **메시지가 영구 소멸한다.** `BRPOP`은 **꺼내는 순간 리스트에서 제거**하므로, 그 직후 워커가 죽으면(JVM crash, OOM, 배포 중 kill) 그 메시지는 어디에도 없음. **at-most-once**(최대 한 번)에 가까운, ack 없는 모델.

이 프로젝트:
```java
String email = redisTemplate...rightPop(MAIL_QUEUE, ...);  // 여기서 이미 큐에서 사라짐
workerPool.submit(() -> processEmail(email));               // 처리 중 죽으면 → 메일 유실
```

**해결 = Reliable Queue 패턴 (LMOVE)**:
```
1. BLMOVE mail:queue processing:queue RIGHT LEFT   # 빼는 즉시 처리중 큐로 원자 이동
2. 메일 발송
3. LREM processing:queue 1 <email>                 # 성공 ack → 처리중 큐에서 제거
4. (죽으면) processing:queue에 남은 메시지를 별도 스레드가 재투입
```

→ "꺼냄 = 삭제"가 아니라 "꺼냄 = 다른 큐로 이동"이라 워커가 죽어도 메시지가 살아있음.

> 💡 이 패턴은 **at-least-once**(최소 한 번)로 바뀜 → 재처리 시 중복 가능 → **멱등성**이 필요(Q18).

---

### Q18. at-least-once와 멱등성(idempotency)은 왜 같이 가나?

✅ **답**:

> Reliable Queue로 유실을 막으면(재투입), **같은 메시지가 두 번 처리될 수 있음**(처리 성공 후 ack 직전 죽으면 재투입됨). 즉 **유실을 막는 대가로 중복이 생김**.
>
> 그래서 **컨슈머를 멱등하게** 만들어야 함 — "같은 메시지를 N번 처리해도 결과가 1번과 같게".

이 프로젝트 예: 가입 메일을 두 번 보내면 사용자가 환영 메일을 두 번 받음(경미). 결제 같은 critical 작업이라면:
- 메시지에 **고유 ID** 부여 → `SET dedup:<id> 1 NX EX ...` 로 "이미 처리했나" 체크
- 또는 DB **unique 제약**으로 중복 삽입 차단

> 💡 핵심 한 줄: **"exactly-once는 사실상 환상이고, 현실은 at-least-once + 멱등 컨슈머로 사실상 한 번처럼 만든다."**

---

### Q19. DLQ(Dead Letter Queue)가 뭔가? List로 어떻게 구현하나?

✅ **답**:

> **반복 실패한 메시지를 격리하는 별도 큐.** 계속 실패하는 메시지가 큐를 막거나 무한 재시도하는 걸 방지.

List 구현:
```
재시도 횟수 초과 메시지 → LPUSH mail:dlq <msg>
운영자가 LRANGE mail:dlq 0 -1 로 점검 후 원인 수정, 재투입 또는 폐기
```

설계 포인트:
- 메시지에 **시도 횟수(retry count)**를 같이 실어야 함 → JSON `{"email":"x","retry":3}`
- DLQ로 보낸 뒤엔 **알림(모니터링)** 을 띄워 사람이 본다

> 💡 꼬리질문: "왜 무한 재시도하면 안 되나?" → poison message(영원히 실패하는 메시지) 하나가 워커를 계속 점유하고 뒤 메시지를 굶김(head-of-line blocking).

---

## D. 신뢰성·내구성

### Q20. List 큐에서 메시지 유실이 생기는 시나리오를 정리해보라.

✅ **답** (3층):

| 층 | 시나리오 | 원인 |
|---|---|---|
| **컨슈머** | `BRPOP` 직후 워커 crash | 꺼내는 순간 큐에서 삭제, ack 없음 |
| **Redis 자체** | Redis 프로세스/노드 다운 | 인메모리 → 영속화 안 된 큐 내용 소실 |
| **failover** | master 죽고 replica 승격 | **비동기 복제**라 아직 복제 안 된 LPUSH 유실 |

→ 즉 유실은 **컨슈머 레벨 + 인프라 레벨** 양쪽에서 온다. 컨슈머 레벨은 Reliable Queue(Q17)로, 인프라 레벨은 영속화·복제 설정(Q21)으로 막는다.

> 💡 이 프로젝트의 `mail:queue`는 현재 ack도 영속화 보장도 없어서, 둘 다에 노출돼 있음. 메일이 *환영 메일*이라 유실 임팩트가 작아 용인 중인 것.

---

### Q21. List 큐는 AOF/RDB·replica와 어떤 관계인가? 영속성이 보장되나?

✅ **답**:

> List도 **다른 키와 똑같이 RDB 스냅샷·AOF 로그·replica 복제 대상**. 하지만 **큐의 "정확한 내구성"을 보장하진 못함**:

- **RDB**: 스냅샷 간격 사이의 `LPUSH`들은 스냅샷 전에 죽으면 유실.
- **AOF**: `appendfsync everysec`이면 최대 1초치 쓰기 유실 가능. `always`는 거의 안전하지만 throughput 급락.
- **replica**: **비동기**라 failover 시 복제 못 따라잡은 쓰기 유실.

→ **결론**: Redis List 큐는 *"빠르지만 메시지 단위의 강한 내구성·ack 보장은 약하다"*. 이게 전용 브로커(Kafka 등)와의 본질적 차이(E 섹션).

> 💡 꼬리질문: "그럼 AOF always면 안전한가?" → 메시지 유실은 줄지만 **ack/재처리/오프셋** 개념이 List엔 없음. 내구성과 메시징 시맨틱은 별개 문제.

---

### Q22. List 큐엔 왜 ack(확인 응답)가 없나? Stream은 뭐가 다른가?

✅ **답**:

> List는 단순 자료구조라 **"이 메시지를 누가 처리 중이고, 처리 완료됐는지"를 Redis가 추적하지 않음**. `RPOP` 하면 끝. 그래서 ack/재전송/오프셋이 없음 → 신뢰성은 **앱이 직접**(Reliable Queue 패턴) 구현해야 함.
>
> **Redis Stream**(5.0+)은 이걸 내장: **컨슈머 그룹**, **PEL(Pending Entries List, 미확인 메시지 추적)**, **`XACK`**, **`XCLAIM`(죽은 컨슈머 메시지 회수)**, **`XAUTOCLAIM`**, 메시지 보존(과거 메시지 재조회 가능).

| | List 큐 | Stream |
|---|---|---|
| ack | ❌ (직접 구현) | ✅ `XACK` |
| 컨슈머 그룹 | ❌ | ✅ |
| 메시지 보존 | pop하면 사라짐 | 명시적으로 보존(재조회 가능) |
| 죽은 컨슈머 회수 | 직접 (processing 큐 스캔) | ✅ `XCLAIM`/`XAUTOCLAIM` |

> 💡 한 줄: **"List로 신뢰성 큐를 만들려고 LMOVE·LREM·재투입을 손으로 짜다 보면, 그게 곧 Stream이 이미 해주는 것"** → 신뢰성이 중요하면 처음부터 Stream을 고려.

---

### Q23. 블로킹 큐 명령(`BRPOP`)을 트랜잭션·Lua 안에서 쓰면?

✅ **답**:

> **블로킹하지 않는다.** `MULTI/EXEC`나 Lua 스크립트 안의 `BRPOP`/`BLPOP`/`BLMOVE`는 **즉시 처리**됨 — 데이터가 있으면 pop, 없으면 그냥 `nil`(블로킹 없이).
>
> 이유: 트랜잭션·스크립트는 **전체가 원자적·단일 스레드로 실행**되어야 하는데, 여기서 "원소가 들어올 때까지 대기"하면 **Redis 전체가 멈춰버림**(다른 클라이언트가 push조차 못 함 → 영원한 데드락). 그래서 블로킹 시맨틱을 강제로 끈다.

→ **결론**: 대기가 필요한 블로킹 pop은 트랜잭션/스크립트 밖에서, 일반 명령으로 써야 함.

> 💡 String 면접 Q18 연결: "단일 스레드 = 한 번에 한 명령 실행" 원칙의 직접적 귀결.

---

### Q24. 큐가 밀리는지(컨슈머가 못 따라가는지) 어떻게 모니터링하나?

✅ **답**:

> **`LLEN mail:queue` (O(1))** 로 큐 적체 길이를 주기적으로 본다. 이 값이 **계속 증가**하면 생산 > 소비 → 컨슈머 부족/지연.

운영 지표:
- `LLEN`이 임계값 초과 시 알림 → 워커 스케일 아웃(워커풀 3 → 더 늘림)
- Reliable Queue면 `LLEN processing:queue`도 본다 → 처리중인데 안 줄면 워커가 멈췄거나 죽음
- DLQ `LLEN mail:dlq` > 0 → 실패 메시지 발생 알림

> 💡 함정: 큐 길이를 보겠다고 `LRANGE q 0 -1`로 전체를 받아 세면 안 됨(O(N), big key 위험). **개수는 무조건 `LLEN`(O(1))**.

## E. List 큐 vs 전용 브로커

### Q25. Redis List 큐 vs Kafka — 언제 무엇을 쓰나?

✅ **답**:

| | Redis List 큐 | Kafka |
|---|---|---|
| 모델 | pop하면 소멸 (큐) | 로그(offset), 메시지 보존·재생 |
| 내구성 | 인메모리(+AOF), 약함 | 디스크 기반, 강함·복제 |
| 처리량 | 매우 빠름(저지연) | 매우 높음(대용량 스트림) |
| 순서 | 큐 단위 FIFO | 파티션 단위 보장 |
| 재처리 | pop하면 끝(직접 구현) | offset 되감아 재생 |
| 운영 복잡도 | 낮음 | 높음(브로커·ZK/KRaft) |

→ **선택**: *가볍고 빠른 비동기 작업 디스패치(이 프로젝트 메일 큐처럼)* → Redis List로 충분. *이벤트 소싱·로그 보존·대량 스트림·여러 컨슈머의 독립 소비* → Kafka.

> 💡 한 줄: **Redis List = "작업 큐(work queue)", Kafka = "이벤트 로그(event log)"**. 목적이 다름.

---

### Q26. Redis List 큐 vs RabbitMQ 차이는?

✅ **답**:

> RabbitMQ는 **메시지 브로커 전용** — ack/재전송, 라우팅(exchange/binding), 우선순위, DLQ, persistent message가 **기본 내장**. Redis List는 자료구조라 이걸 다 직접 구현해야 함.

| | Redis List | RabbitMQ |
|---|---|---|
| ack/재전송 | 직접(Reliable Queue) | 내장 |
| 라우팅 | 없음(키로 분리) | exchange(topic/fanout/direct) |
| DLQ | 직접 | 내장 |
| 지연 | 더 낮음(인메모리) | 약간 높음 |

→ **트레이드오프**: Redis는 "이미 Redis를 쓰고 있고 가벼운 큐면 추가 인프라 없이 끝"의 매력. RabbitMQ는 "메시징 기능이 풍부하지만 별도 브로커 운영".

> 💡 "이미 캐시·세션으로 Redis 쓰는데 메일 큐 하나 때문에 RabbitMQ를 또 띄울까?" → 이 프로젝트가 List를 택한 현실적 이유.

---

### Q27. Redis Pub/Sub와 List 큐의 차이는?

✅ **답**:

> 가장 큰 차이는 **메시지 보존**과 **전달 모델**:

| | List 큐 (LPUSH/BRPOP) | Pub/Sub (PUBLISH/SUBSCRIBE) |
|---|---|---|
| 전달 | 한 메시지 → **한 컨슈머**(work queue) | 한 메시지 → **모든 구독자**(broadcast/fan-out) |
| 보존 | 컨슈머 없으면 **큐에 쌓임** | 구독자 없으면 **그냥 버려짐**(at-most-once) |
| 오프라인 컨슈머 | 나중에 켜서 처리 가능 | 그 사이 메시지 **영구 손실** |

→ **결론**: "작업을 누군가 한 명이 처리"는 List, "이벤트를 실시간으로 여러 명에게 알림(채팅·실시간 알림)"은 Pub/Sub. **Pub/Sub은 안 받으면 사라지므로 신뢰성 큐로 쓰면 안 됨**.

> 💡 신뢰성 + fan-out + 보존이 다 필요하면 → **Stream의 컨슈머 그룹**이 정답(Q22).

---

### Q28. 이미 Redis만 쓴다면, 신뢰성 큐는 Stream을 써야 하나 List를 써야 하나?

✅ **답**:

> **신뢰성(ack·재처리·소비자 추적)이 요구사항이면 List보다 Stream이 정석.** List로 Reliable Queue를 손코딩하면 결국 PEL·XCLAIM·컨슈머 그룹을 어설프게 재발명하게 됨.
>
> 다만 **요구사항이 "가볍고 단순한 작업 디스패치"면 List가 더 단순·저오버헤드**. 이 프로젝트 메일 큐처럼 유실 임팩트가 작으면 List + (필요 시) LMOVE 정도가 합리적.

판단 기준:
- 유실 절대 불가 / 재처리 / 여러 컨슈머 그룹 → **Stream**
- 빠른 fire-and-forget 작업 큐, 단순함 우선 → **List**

> 💡 시니어 포인트: **"자료구조를 고르는 게 아니라 메시징 시맨틱(at-most/at-least/exactly-once, ack, 보존)을 먼저 정하고 거기 맞는 도구를 고른다."**

---

## F. 운영·성능·함정

### Q29. List에서 big key는 어떻게 위험한가? 어떻게 예방·탐지하나?

✅ **답**:

> **원소가 수십만~수백만 개로 거대해진 List**가 big key. 위험:
> - `LRANGE 0 -1`·`LINDEX`·`LREM`·`LTRIM` 등 O(N) 명령이 **단일 스레드를 오래 점유** → 전체 지연.
> - `DEL`로 통째 삭제 시 동기 회수로 **블로킹** → 큰 List는 **`UNLINK`**(비동기 삭제).
> - 인코딩이 quicklist로 가며 메모리·복제 부담 증가.

**예방**: capped list — `LPUSH` 후 `LTRIM k 0 N`으로 길이 상한. **탐지**: `redis-cli --bigkeys`, `OBJECT ENCODING k`(quicklist 여부), `LLEN`.

> 💡 큐의 경우 big key는 보통 **컨슈머 적체의 증상** → `LLEN` 폭증 알림으로 사전 감지하고 워커 스케일 아웃.

---

### Q30. `LRANGE k 0 -1`을 운영에서 치면 왜 위험한가?

✅ **답**:

> **O(N)** 이라 큰 리스트면 **전체 데이터를 한 번에 직렬화해 반환** → 단일 스레드가 그 동안 막히고, 응답 페이로드가 거대해져 **네트워크·메모리 스파이크**. 사실상 List판 `KEYS *`.

대안:
- 길이만 필요 → **`LLEN`**(O(1))
- 일부만 보기 → `LRANGE q 0 99`처럼 **범위 제한**
- 페이지네이션 → start/stop를 옮겨가며 조각조각

> 💡 String 면접 Q30(`KEYS *`)과 같은 교훈: **"전체를 한 방에" 류의 명령은 단일 스레드 Redis에선 장애 트리거**.

---

### Q31. 큐가 비어 키가 사라지는 점·블로킹·트랜잭션 — List 운영의 미묘한 함정 3가지는?

✅ **답** (빠른 정리):

1. **빈 List = 키 자동 삭제** → 큐가 비면 `EXISTS`가 0. 길이는 `LLEN`으로 판단하고, 큐 키에 TTL을 의존하지 말 것(비면 같이 사라짐) (Q4).
2. **블로킹 명령은 MULTI/EXEC·Lua 안에서 블로킹 안 함** → 즉시 nil. 대기가 필요하면 트랜잭션 밖에서 (Q23).
3. **여러 값 `LPUSH k a b c`는 역순(`[c,b,a]`)** → 순서 의존 로직에서 버그. 순서 그대로면 `RPUSH`나 1개씩 (Q5).

> 💡 보너스: `LSET`/`LINSERT`의 범위 밖·pivot 없음 반환값(에러/-1/0)을 코드에서 안 보고 넘기면 조용한 버그 (Q13).

## G. 실전 응용

### Q32. 이 프로젝트의 `mail:queue`를 어떻게 "신뢰성 있게" 바꾸겠나?

✅ **답** (현재 → 개선):

**현재** (`AuthService.java:85` + `EmailMultiWorker.java:44`):
```
LPUSH mail:queue {email}          # 생산
BRPOP mail:queue 10               # 소비 — 꺼내면 즉시 소멸, ack 없음
```
→ 워커가 메일 발송 중 죽으면 그 메일 유실.

**개선 (Reliable Queue, List만으로)**:
```
1. BLMOVE mail:queue mail:processing RIGHT LEFT 10   # 꺼냄+처리중큐로 원자 이동
2. 메일 발송 (성공 시)
3. LREM mail:processing 1 {email}                    # ack: 처리중큐에서 제거
4. [회수 스레드] 주기적으로 mail:processing의 오래된 항목을
   mail:queue로 재투입 (워커 사망분 복구)
5. [재시도 한도 초과] LPUSH mail:dlq {email} + 알림   # DLQ 격리
```
→ at-least-once가 되므로 **컨슈머를 멱등하게**(중복 발송 방지: dedup 키 or 로그 unique).

**또는** 신뢰성 요구가 더 크면 **Redis Stream**(컨슈머 그룹 + XACK)으로 교체.

> 💡 현재 메일이 *환영 메일*이라 유실 임팩트가 작아 List + BRPOP로 충분하지만, **결제 영수증 메일**이었다면 위 신뢰성 설계가 필수.

### Q33. 우선순위 큐 / "최근 본 상품" / Fan-out 타임라인을 List로 설계해보라.

✅ **답** (세 가지 응용):

**1) 우선순위 큐** — 큐를 등급별로 나누고 `LMPOP`으로 우선순위대로 소비:
```
LPUSH q:high <urgent>    LPUSH q:low <normal>
LMPOP 2 q:high q:low LEFT COUNT 10   # high 먼저, 비면 low (Q14)
# (BLMPOP이면 블로킹 대기까지)
```

**2) 최근 본 상품 (capped list)** — 유저별 최근 20개:
```
LREM recent:user:42 0 <productId>    # 이미 있으면 제거(중복 방지)
LPUSH recent:user:42 <productId>     # 맨 앞에 추가
LTRIM recent:user:42 0 19            # 20개로 상한 (Q11)
```

**3) Fan-out-on-write 타임라인** — 글 쓰면 팔로워들 타임라인 List에 미리 뿌림:
```
# 작성자가 글 쓸 때, 팔로워 각각의 타임라인에 LPUSH
for follower in followers:
    LPUSH timeline:{follower} {postId}
    LTRIM timeline:{follower} 0 999   # 최근 1000개만
# 조회는 LRANGE timeline:{me} 0 49 (O(S+N), 일부만)
```

> 💡 Fan-out-on-write의 트레이드오프: **읽기는 빠름(이미 만들어둠)** but **팔로워 수백만인 셀럽이 글 쓰면 write 폭증**(hot user 문제) → 셀럽은 fan-out-on-read로 분리하는 하이브리드가 실무 정석. ZSet(시간 점수)으로 가는 경우도 많음.

## 🎯 면접 직전 30초 체크리스트

암기보단 흐름으로:

1. **List는 뭐에 좋은가** → 양끝 O(1) → 큐/스택/최근 N개
2. **내부 구조** → 작으면 listpack, 크면 quicklist(listpack 노드들의 linked list) → 그래서 양끝 O(1), 가운데 O(N)
3. **큐 방향** → `LPUSH` + `RPOP`(=FIFO). 이 프로젝트는 `LPUSH` + `BRPOP`
4. **BRPOP vs 폴링** → 블로킹 대기라 빈 큐 CPU 낭비 없음, 즉시 반응. 반환은 (키, 값)
5. **RPOPLPUSH → LMOVE/BLMOVE** → 원자 이동, Reliable Queue의 핵심
6. **List 큐의 치명적 약점** → ack 없음, pop=소멸 → 워커 죽으면 유실(at-most-once)
7. **신뢰성 패턴** → `LMOVE`로 processing 큐 이동 → 성공 시 `LREM` ack → 죽은 건 재투입 → at-least-once → **멱등성** 필수
8. **List vs Stream** → Stream은 ack/컨슈머그룹/PEL/보존 내장. 신뢰성 크면 Stream
9. **List vs Kafka/RabbitMQ/PubSub** → 작업큐 vs 이벤트로그 / 메시징 기능 풍부 / broadcast(보존X)
10. **운영 금지·함정** → `LRANGE 0 -1`(O(N)), 개수는 `LLEN`, big key는 `UNLINK`, 빈 큐=키삭제, 블로킹은 트랜잭션 안에서 안 됨
11. **모니터링** → `LLEN`으로 적체 감시 → 워커 스케일 아웃
12. **failover ↔ 큐 유실** → 비동기 복제라 승격 시 미복제 LPUSH 유실(인프라 레벨 유실, Q20)

## 자주 나오는 후속 질문 패턴

면접관이 추가로 파고드는 단골 흐름:

```
Q. Redis로 큐 어떻게 만들어요?
→ LPUSH + BRPOP (FIFO) 답함
Q. 워커가 메시지 처리하다 죽으면요?
→ pop하면 소멸이라 유실 → LMOVE로 processing 큐 이동(Reliable Queue)
Q. 그럼 재투입하면 같은 메시지 두 번 처리될 텐데?
→ at-least-once라 맞음 → 컨슈머를 멱등하게(dedup 키 / DB unique)
Q. 그거 결국 직접 만드는 거잖아요? 더 나은 건?
→ Redis Stream(컨슈머그룹·XACK·PEL) 또는 Kafka/RabbitMQ
```

```
Q. List vs Pub/Sub 차이는?
→ List는 한 명이 처리(보존), Pub/Sub은 모두에게 broadcast(안 받으면 소멸)
Q. 그럼 실시간 알림 + 유실 방지 둘 다 필요하면?
→ Stream 컨슈머 그룹
```

```
Q. 큐가 밀리는지 어떻게 알아요?
→ LLEN으로 적체 길이 모니터링 (O(1))
Q. LRANGE로 다 받아서 세면 안 되나요?
→ O(N) + big key 위험. 개수는 무조건 LLEN
Q. 큐가 너무 길어지면?
→ 워커 스케일 아웃 + capped list(LTRIM)로 상한
```

```
Q. List 큐도 영속화돼요?
→ RDB/AOF/replica 대상이지만 메시지 단위 ack·내구성은 약함
Q. failover 시 메시지 유실 가능?
→ 비동기 복제라 미복제 LPUSH 유실 가능 (String 면접 Q33과 동일 구조)
```

→ **꼬리잡기 답을 미리 준비해두면 면접관이 "어, 이 친구 깊네" 하는 인상.**
