# 🎬 시나리오 1 ⭐ 보스급. 큐 컨슈머가 죽어서 환영 메일이 사라졌다

## 📋 상황

금요일 오후 6시, 롤링 배포가 막 끝났다. 30분 뒤 CS 채널에 글이 올라온다.

> **CS 팀**: "회원가입은 됐는데 환영 메일이 안 왔다는 문의가 12건 들어왔어요. 가입 시각이 전부 6시 ~ 6시 3분 사이예요."

배포 로그를 본다. `queue-server`가 6시 정각에 롤링 재시작(SIGTERM → 새 인스턴스 기동)됐다. 그 순간, `EmailMultiWorker`의 워커 스레드 3개는 **각자 이메일 하나씩을 5초짜리 발송 작업 중**이었다.

현재 코드 흐름을 다시 보자.

```java
// 프로듀서 — AuthService.java:85
redisTemplate.opsForList().leftPush(MAIL_QUEUE, email);   // LPUSH

// 디스패처 — EmailMultiWorker.java:44
String email = redisTemplate.opsForList()
        .rightPop(MAIL_QUEUE, Duration.ofSeconds(10));     // BRPOP 10
if (email != null) {
    workerPool.submit(() -> processEmail(email));          // 워커에 던짐
}
```

**문제의 핵심**: `BRPOP` 으로 꺼내는 **순간** 메시지는 큐에서 **완전히 사라진다.** 디스패처가 꺼내서 워커에게 넘긴 그 이메일은 이제 **자바 힙의 람다 변수 안에만** 존재한다. 워커가 `processEmail`을 도는 5초 사이에 프로세스가 죽으면? 그 메시지는 Redis에도, DB에도, 어디에도 안 남는다. **흔적 없이 증발.**

`EmailWorker.java:72` 에 이미 누군가 주석으로 경고를 남겨놨다.

```java
} catch (Exception e) {
    log.error("이메일 발송 실패: {}", email, e);
    // 실패 시 다시 큐에 넣거나(DLQ), 별도 처리가 필요함   ← 이 TODO가 터진 것
}
```

게다가 이 catch는 **예외(sleep 중 InterruptedException 등)** 만 잡는다. SIGTERM으로 JVM이 통째로 내려가면 catch도 안 돈다. 더 막을 수가 없다.

**월요일 회고에 "왜 메일이 사라졌고, 어떻게 다신 안 사라지게 할지"를 가져가야 한다.**

## 🔒 제약

- **at-least-once는 보장해야 한다.** 메일이 사라지는 건 절대 안 됨. 두 번 가는 건 (사용자가 짜증은 내도) 사라지는 것보단 낫다.
- 분산 환경 — `queue-server` 인스턴스 여러 대, 워커 풀 3개.
- 롤링 배포는 앞으로도 매일 일어난다 (= 컨슈머는 **언제든 죽는다**고 가정).
- Redis만으로 (Kafka/RabbitMQ 같은 신규 인프라 도입은 이번 분기 불가).

## 🛡️ Reliable Queue 패턴 (BRPOP → BLMOVE)

핵심 발상은 단 하나:

> **"꺼낸다(pop)"와 "처리한다(ack)"를 분리한다.**
> 꺼낼 때 메시지를 *지우지 말고* **처리 중(processing) 리스트로 원자적으로 옮긴다.**
> 처리가 끝나야 비로소 processing에서 지운다(ack).

`BRPOP`은 이걸 못 한다. 꺼내면서 동시에 사라지니까. 이걸 가능하게 하는 게 **`BLMOVE`** (구버전 `BRPOPLPUSH`, 6.2부터 deprecated).

### Step 1: BRPOP → BLMOVE 로 교체

```java
private static final String MAIL_QUEUE   = "mail:queue";
private static final String PROCESSING   = "mail:processing";   // 작업 중 보관소

// [Dispatcher] — 꺼냄과 동시에 processing 리스트로 원자 이동
String email = redisTemplate.opsForList().move(
        MAIL_QUEUE,   RedisListCommands.Direction.RIGHT,   // src tail 에서 꺼내고
        PROCESSING,   RedisListCommands.Direction.LEFT,    // dst head 로 넣고
        Duration.ofSeconds(10));                           // 블로킹 10초 (BLMOVE)

if (email != null) {
    workerPool.submit(() -> processEmail(email));
}
```

> `LPUSH mail:queue` + `BLMOVE ... RIGHT LEFT` = 여전히 **FIFO** 유지.
> 그리고 이 이동은 **원자적**이다 — 꺼내는 순간과 processing에 들어가는 순간 사이에 메시지가 "공중에 뜨는" 틈이 없다. 여기서 죽어도 메시지는 `mail:queue` 아니면 `mail:processing` **둘 중 한 곳엔 반드시 있다.**

### Step 2: 처리 성공 시 ack (processing 에서 제거)

```java
private void processEmail(String email) {
    try {
        sendEmail(email);
        emailLogRepository.save(...);

        // ✅ ack — processing 리스트에서 이 메시지 제거 (LREM)
        //    count = 1: head 부터 첫 1개만 제거 (전부 다 지우면 안 됨)
        redisTemplate.opsForList().remove(PROCESSING, 1, email);

    } catch (Exception e) {
        // 실패 시엔 ack 하지 않는다 → processing 에 남아 있다가
        //   아래 reaper 가 큐로 되돌려준다
        log.error("발송 실패, processing 에 남김: {}", email, e);
    }
}
```

### Step 3: Stale Reaper — 죽은 작업 회수 (이게 진짜 신뢰성의 본체)

processing 에 들어갔는데 워커가 죽어서 ack 못 한 메시지는 **영원히 거기 갇힌다.** 주기적으로 청소하는 별도 스레드(또는 스케줄러)가 필요하다.

```java
// 30초마다 실행. processing 에서 오래 묵은 놈을 다시 mail:queue 로 되돌림
@Scheduled(fixedDelay = 30_000)
public void reapStaleJobs() {
    // processing 의 가장 오래된 것(tail)을 큐의 tail 로 되돌림
    //   LMOVE PROCESSING(RIGHT) → MAIL_QUEUE(LEFT) 면 다시 FIFO 자리로
    String stale = redisTemplate.opsForList().move(
            PROCESSING, RedisListCommands.Direction.RIGHT,
            MAIL_QUEUE, RedisListCommands.Direction.LEFT);
    if (stale != null) {
        log.warn("좀비 메시지 회수 → 재처리 큐로 복귀: {}", stale);
    }
}
```

> ⚠️ 위 단순 reaper의 결정적 약점: **"방금 정상 처리 중인 것"과 "죽어서 방치된 것"을 구분 못 한다.** 멀쩡히 일하는 워커의 메시지까지 큐로 끌어와 중복 처리를 만든다. → **"얼마나 오래 묵었는지(나이)"** 정보가 필요하다. 이게 String 큐의 한계이자, 다음 단계(Stream)로 넘어가는 이유다(Q3 참고).

### 정리 — 전체 라이프사이클

```
[ LPUSH ]                                   AuthService (프로듀서)
   ↓
mail:queue  ──BLMOVE(RIGHT→LEFT)──▶  mail:processing
   ▲                                        │
   │                                   processEmail
   │                                        │
   │  성공 → LREM (ack, 제거) ◀─────────────┘
   │  실패/크래시 → ack 안 됨, processing 에 잔류
   │
   └── reaper: 오래 묵은 놈 LMOVE 로 되돌림 (재처리)
```

이제 워커가 처리 중 죽어도, 메시지는 `mail:processing`에 살아 있고 → reaper가 `mail:queue`로 되돌리고 → 다른 워커가 다시 처리한다. **at-least-once 달성.**

## 🪤 면접관이 깊이 파고들면

### Q1. "reaper 가 처리 중인 메시지를 멀쩡한데도 끌어오면 중복 처리 폭주 아닌가요? '나이'를 어떻게 압니까?"

→ String 리스트엔 원소의 "들어온 시각"이 없다. 두 가지 보완:
- **(a) 페이로드에 메타 박기**: 큐에 넣을 때 `{"id":"uuid","email":"...","poppedAt":...}` JSON으로. processing 에 들어갈 때 `poppedAt`을 갱신하고, reaper는 `now - poppedAt > visibilityTimeout` 인 것만 회수. 단, BLMOVE는 "옮기기"만 하고 값 수정은 못 하므로, processing 에는 사실상 **별도 ZSET(`mail:processing:zset`, score=deadline)** 으로 마감시한을 관리하는 게 깔끔하다.
- **(b) visibility timeout** 개념(SQS와 동일): "processing 에 들어간 지 N초 지나면 죽은 걸로 간주". 이 N은 작업 최대 소요시간(여기선 5초)보다 충분히 커야 정상 작업을 안 건드린다.
→ 결론: **순수 String 리스트만으론 visibility timeout을 깔끔히 못 만든다.** 이 지점이 List의 한계 → Q3.

### Q2. "그럼 중복 처리는 결국 생기잖아요. 같은 사람한테 환영 메일 두 번 가는 건요?"

→ at-least-once 큐의 **숙명**이다. 큐에서 "정확히 한 번"을 보장하려 애쓰지 말고, **컨슈머를 멱등(idempotent)하게** 만든다.
- 메시지에 `messageId`(UUID)를 넣고, 컨슈머 진입 시 `SET dedup:email:{id} 1 NX EX 86400` 로 dedup.
- 또는 처리의 부수효과(메일 발송) 자체를 멱등키로 가드.
→ **"큐는 at-least-once, 멱등성은 컨슈머 책임"** — 자세한 패턴은 `../01-string/부록-멱등성.md` 와 `03-면접질문.md`.

### Q3. "이거 결국 Redis Stream 흉내네요. 그냥 Stream 쓰면 안 돼요? List vs Stream 언제 뭘 씁니까?"

→ 정확한 지적. 우리가 손으로 만든 게 Stream의 **Consumer Group**이 기본 제공하는 기능이다.

| | **List (BLMOVE 패턴)** | **Stream (XREADGROUP)** |
|---|---|---|
| ack | LREM 수동 구현 | `XACK` 내장 |
| 미처리 추적 | processing 리스트 + reaper 수작업 | `PEL`(Pending Entries List) 내장, 나이까지 기록 |
| 죽은 워커 회수 | reaper 직접 짜야 함 | `XPENDING` + `XCLAIM` (idle time 기준) |
| 멀티 컨슈머 | 워커끼리 같은 큐 경쟁(OK) | Consumer Group으로 분배 + 컨슈머별 오프셋 |
| 메시지 영속/재처리 | pop 하면 사라짐 | 로그처럼 보존(`XRANGE`로 과거 조회 가능) |
| 무게 | 가볍다, 단순 작업 큐에 충분 | 무겁다, 본격 메시징에 적합 |

→ 한 줄 요약: **"단순 작업 큐엔 List, ack·재처리·소비자 그룹이 진지하게 필요하면 Stream."** 우리 환영 메일은 List + 멱등성으로도 충분하지만, "왜 사라졌나"가 반복되면 Stream으로 갈 타이밍이다. (이건 추후 별도 자료구조 단계)

### Q4. "운영 중에 메시지가 쌓이는지/막히는지 어떻게 압니까? 모니터링은요?"

→ **`LLEN`** 이 1차 지표.
- `LLEN mail:queue` 가 계속 우상향 → 컨슈머가 못 따라감(스루풋 부족) → 워커 풀 증설 또는 처리 최적화.
- `LLEN mail:processing` 이 0으로 안 떨어지고 누적 → ack 안 되는 좀비 다수 → reaper 점검, 발송 실패율 점검.
- 둘 다 메트릭으로 빼서(Prometheus 등) 알람. **함정**: `LLEN`은 리스트가 비면 키 자체가 사라져 0을 반환하므로, "키 없음 == 비어있음"으로 안전하게 해석하면 된다(시나리오 3 참고).

### Q5. "워커를 N대로 늘리면 메일 발송 순서가 보장됩니까?"

→ **안 된다, 그리고 그래도 괜찮다.**
- 디스패처가 FIFO로 꺼내 주더라도, 워커 3개가 **병렬로** `processEmail`(각 5초)을 돌면 끝나는 순서는 뒤섞인다. A를 먼저 꺼냈어도 A 발송이 B보다 늦게 끝날 수 있다.
- 환영 메일은 **순서가 무의미**하므로 문제없다. → 처리량(throughput) 우선.
- 만약 "사용자별로는 순서 보장"이 필요하면(예: 같은 유저의 이벤트 A→B 순서) → **샤딩**: `mail:queue:{hash(userId) % N}` 로 키를 N개로 쪼개고, 워커 1개가 한 샤드만 단독 소비. 같은 유저는 항상 같은 샤드 → 그 안에선 순서 보장. (Kafka 파티션 키와 같은 발상)

## 🎯 핵심 takeaway

> **"BRPOP은 꺼내는 순간 메시지를 죽인다. 신뢰성 큐는 '꺼냄'과 'ack'를 분리한다."**
>
> - `BRPOP` → `BLMOVE`(BRPOPLPUSH) 로 바꿔 **processing 리스트**에 원자 보관
> - 성공 시 `LREM`으로 ack, 실패/크래시 시 reaper가 `LMOVE`로 큐 복귀 = **at-least-once**
> - 단, "나이"를 모르는 List의 한계 → visibility timeout은 절름발이 → 진지해지면 **Stream**
> - at-least-once의 짝꿍은 항상 **컨슈머 멱등성**

# 🎬 시나리오 2. 큐가 LIFO로 동작해서 메일 순서가 뒤집혔다

## 📋 상황

신규 입사자가 컨슈머를 "성능 개선"한다며 디스패처를 이렇게 바꿨다.

```java
// 프로듀서는 그대로 — AuthService.java:85
redisTemplate.opsForList().leftPush(MAIL_QUEUE, email);    // LPUSH (head 삽입)

// 컨슈머만 바꿈
String email = redisTemplate.opsForList()
        .leftPop(MAIL_QUEUE, Duration.ofSeconds(10));      // BLPOP (head 제거) ← 변경
```

이후 QA에서 "먼저 가입한 사람의 메일이 더 늦게 처리된다"는 리포트가 떴다. 트래픽이 몰릴 때 특히 심하다.

## ❓ 질문

왜 순서가 뒤집혔나? `LPUSH` 쪽을 건드릴까, `POP` 쪽을 건드릴까?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

리스트를 **양 끝이 있는 줄**로 그려보면 끝난다.

```
LPUSH a → [a]
LPUSH b → [b, a]          (head 쪽에 쌓임)
LPUSH c → [c, b, a]
        head ────▶ tail

BLPOP (head 제거): c, b, a 순  → 마지막에 넣은 게 먼저 나옴 = LIFO (스택)
BRPOP (tail 제거): a, b, c 순  → 먼저 넣은 게 먼저 나옴 = FIFO (큐)
```

- **같은 쪽**에서 push/pop = **LIFO(스택)**
- **반대쪽**에서 push/pop = **FIFO(큐)**

이 프로젝트는 원래 `LPUSH`(head 삽입) + `BRPOP`(tail 제거) = **FIFO**였다. 신규 입사자가 pop을 `BLPOP`(head 제거)로 바꾸면서 push/pop이 **같은 쪽**이 됐고 → LIFO로 변질. 먼저 가입한 사람(줄 안쪽 깊숙이 밀린)이 뒤로 밀린 것.

## ✅ 올바른 패턴

원래 코드(`EmailMultiWorker.java:44`)대로 **반대쪽**을 유지한다. push와 pop의 방향이 짝이 맞는지가 전부.

```java
// FIFO 조합 1 (현재 프로젝트): LPUSH + BRPOP
redisTemplate.opsForList().leftPush(MAIL_QUEUE, email);     // 프로듀서
redisTemplate.opsForList().rightPop(MAIL_QUEUE, Duration.ofSeconds(10));  // 컨슈머 ✅

// FIFO 조합 2 (대칭): RPUSH + BLPOP — 이것도 FIFO. 팀 컨벤션만 통일하면 됨
```

> 외우는 법: **"넣는 문과 빼는 문이 다르면 줄서기(FIFO), 같으면 스택(LIFO)."**

## 🪤 함정 한 줄

> **push/pop 방향이 같으면 LIFO, 다르면 FIFO.** "LPUSH니까 LPOP" 같은 글자 짝맞추기 직관이 정확히 틀리는 함정이다.

# 🎬 시나리오 3. `LLEN mail:queue` 가 0인데 키가 안 보여요

## 📋 상황

큐 모니터링 대시보드를 만들던 중, 운영 Redis에서 직접 확인한다.

```
> LLEN mail:queue
(integer) 0

> EXISTS mail:queue
(integer) 0          ← ??? 큐 키가 아예 없다?

> TYPE mail:queue
none                 ← 타입조차 none
```

대시보드 코드는 `if (redisTemplate.hasKey("mail:queue")) { ... }` 로 큐 존재를 먼저 확인한 뒤 `LLEN`을 호출하는데, 큐가 다 비워지면 이 분기가 통째로 안 타서 **"큐 미초기화" 오류 알림**이 잘못 뜨고 있다.

## ❓ 질문

큐를 만든 적이 있는데 왜 키가 사라졌나? 대시보드 로직을 어떻게 고치나?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

Redis의 철칙: **컬렉션 타입(List/Set/Hash/ZSet) 키는 원소가 0개가 되는 순간 키 자체가 자동 삭제된다.**

마지막 메시지를 `BRPOP`/`LREM`으로 빼서 리스트가 비면 → `mail:queue` 키는 그 자리에서 사라진다. 그래서:

- `LLEN` → `0` (없는 키의 길이는 0)
- `EXISTS` → `0` (진짜 없음)
- `TYPE` → `none`

이 셋이 **모두 같은 "비어있음" 상태**를 가리킨다. "비어있는 리스트가 키로 남아있는 상태"라는 건 Redis에 **존재하지 않는다.** (String은 빈 문자열 `""`로 키가 남을 수 있지만, 컬렉션은 다르다.)

## ✅ 올바른 패턴

`hasKey`로 큐 존재를 먼저 묻는 것 자체가 잘못된 전제다. 그냥 `LLEN`을 바로 호출하면 된다. 빈 큐든 없는 큐든 동일하게 `0`이고, 그게 정상이다.

```java
// ❌ 잘못: 큐가 비면 키가 사라져서 이 분기가 안 탐
if (redisTemplate.hasKey(MAIL_QUEUE)) {
    Long len = redisTemplate.opsForList().size(MAIL_QUEUE);
    ...
}

// ✅ 올바름: LLEN 을 직접. 0 == 비어있음(정상)으로 해석
Long len = redisTemplate.opsForList().size(MAIL_QUEUE);   // 없으면 0
gauge("mail.queue.length", len);                           // 0도 정상 지표
```

> 부수 효과: "빈 리스트에 push 하면 키가 자동 생성"되고, "마지막 원소를 pop 하면 자동 삭제"된다. 큐 키의 생성/소멸을 직접 관리할 필요가 전혀 없다 — Redis가 알아서 한다.

## 🪤 함정 한 줄

> **빈 컬렉션은 키째로 사라진다.** `LLEN == 0`, `EXISTS == 0`, `TYPE == none` 은 전부 "비었음"의 다른 얼굴. `hasKey`로 큐 존재를 가드하지 말고 `LLEN`을 직접 읽어라.

</details>

# 🎬 시나리오 4. "최근 본 콘서트"가 무한히 쌓여 메모리 누수

## 📋 상황

"사용자별 최근 본 콘서트" 기능을 List로 구현했다. 사용자가 콘서트 상세를 볼 때마다:

```java
String key = "recent:concert:" + userId;
redisTemplate.opsForList().leftPush(key, concertId);   // 본 순서대로 head 에 쌓기
// 조회는 LRANGE 0 9 로 최근 10개만 보여줌
```

화면엔 최근 10개만 나오니 잘 동작하는 것처럼 보였다. 그런데 한 달 뒤 인프라에서 경고가 왔다.

> **인프라**: "`recent:concert:*` 키들이 비대해요. 어떤 헤비 유저의 리스트는 원소가 4만 개가 넘어요."

## ❓ 질문

화면엔 10개만 쓰는데 왜 4만 개가 쌓였나? 어떻게 10개로 고정하나?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

**`LRANGE 0 9`는 "읽기"일 뿐, 리스트를 자르지 않는다.** push는 무한히 일어나는데 누구도 뒤를 잘라내지 않으니, 헤비 유저는 본 콘서트 수만큼 원소가 영원히 누적된다. 화면에 10개만 보이는 건 그저 "읽을 때 10개만 떼서 본" 것뿐, 저장소엔 다 쌓여 있다.

게다가 **TTL도 없으니** 이 키들은 영구 잔류한다(메모리 누수의 전형 — String 시나리오 8과 같은 뿌리).

## ✅ 올바른 패턴 — push 직후 LTRIM

push 할 때마다 **`LTRIM 0 9`** 로 앞 10개만 남기고 잘라낸다. 이게 "고정 길이 윈도우" 리스트의 정석.

```java
String key = "recent:concert:" + userId;
ListOperations<String, String> ops = redisTemplate.opsForList();

ops.leftPush(key, concertId);          // 최근 것을 head 에 추가
ops.trim(key, 0, 9);                   // LTRIM 0 9 — head 쪽 10개만 남기고 뒤는 버림
redisTemplate.expire(key, Duration.ofDays(30));   // 비활성 유저 정리용 TTL

// 더 원자적으로 묶고 싶으면 파이프라인/Lua 로 LPUSH+LTRIM 한 번에
```

> `LTRIM key 0 9` = "인덱스 0~9(총 10개)만 남기고 나머지는 다 제거". 음수 인덱스도 됨(`LTRIM key -10 -1` = tail 10개만). 리스트를 **고정 크기 슬라이딩 윈도우**로 쓰는 1순위 도구다.

## 🪤 함정 한 줄

> **`LRANGE`(읽기)는 리스트를 줄이지 않는다.** 길이를 고정하려면 push 직후 반드시 `LTRIM`. 안 그러면 화면엔 10개여도 저장소엔 무한히 쌓인다.

</details>

# 🎬 시나리오 5. 워커가 LPOP으로 하나씩 꺼내 너무 느려요

## 📋 상황

이벤트 알림 메일 100만 건을 큐에 밀어넣는 캠페인이 잡혔다. 컨슈머는 `mail:queue`에서 하나씩 꺼내 처리한다.

```java
while (running) {
    String msg = redisTemplate.opsForList().rightPop(MAIL_QUEUE);  // RPOP 1건
    if (msg != null) process(msg);
}
```

처리 자체는 빠른데(메일 한 건 1ms), **큐 소진 속도가 안 난다.** 프로파일링하니 시간의 대부분이 **Redis 왕복(RTT)** 에서 새고 있다. 100만 건 = 100만 번 네트워크 왕복.

## ❓ 질문

한 번에 하나씩 말고, 어떻게 배치로 빨리 비울래?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

병목은 처리 로직이 아니라 **명령 1건당 네트워크 왕복(RTT)** 이다. 1건 꺼낼 때마다 0.2ms RTT라도 100만 건이면 200초가 통째로 왕복에만 날아간다. **한 번에 여러 개를 꺼내** 왕복 횟수를 줄이는 게 답.

### 방법 1: LPOP/RPOP count (Redis 6.2+) — 가장 직접적

```java
// RPOP mail:queue 100 — tail 에서 한 번에 최대 100개
List<String> batch = redisTemplate.opsForList().rightPop(MAIL_QUEUE, 100);
if (batch != null && !batch.isEmpty()) {
    batch.forEach(this::process);   // 100건을 1왕복으로 가져와 로컬에서 처리
}
```

→ 왕복이 100배 줄어든다. 큐 소진 속도 급상승.

### 방법 2: LMPOP / BLMPOP (Redis 7.0+)

```
LMPOP 1 mail:queue RIGHT COUNT 100
BLMPOP 5 1 mail:queue RIGHT COUNT 100   # 비어있으면 5초 블로킹
```

→ 여러 키 중 비어있지 않은 곳에서 배치로 꺼내기 + 블로킹까지. 가장 현대적.

### ⚠️ 배치의 트레이드오프

배치로 100개 꺼낸 직후 워커가 죽으면 **100개가 한꺼번에 유실**된다(시나리오 1의 규모 확대판). 배치 크기는 "처리량 ↑"과 "크래시 시 유실 폭 ↑"의 트레이드오프다. 신뢰성이 중요하면 시나리오 1의 processing 패턴과 **배치 크기를 작게** 병행한다.

## 🪤 함정 한 줄

> **느린 큐 소비의 범인은 처리 로직이 아니라 RTT인 경우가 많다.** `LPOP count`(6.2+)/`LMPOP`(7.0+)로 배치 소비. 단, 배치가 클수록 크래시 시 유실 폭도 커진다.

</details>

# 🎬 시나리오 6. 인기 큐가 폭주해서 리스트 하나가 수백만 원소 (big key)

## 📋 상황

티켓 오픈 직후, 알림 큐 `notify:queue` 하나에 원소가 **300만 개**까지 치솟았다. 컨슈머가 못 따라가는 사이 프로듀서만 미친 듯이 밀어넣었다.

그 와중에 한 개발자가 "큐에 뭐가 들었나 보자"며 운영 Redis에 쳤다.

```
> LRANGE notify:queue 0 -1
```

그 순간 Redis 응답이 수 초간 멈췄다. api-server 타임아웃 알람 폭발.

## ❓ 질문

(a) `LRANGE 0 -1` 이 왜 운영을 멈췄나? (b) 300만짜리 big key 자체를 어떻게 다룰까?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

### (a) `LRANGE 0 -1` 의 죄

`0 -1`은 "처음부터 끝까지 **전부**"다. 300만 원소를 한 번에 직렬화해서 네트워크로 토해낸다. Redis는 **단일 스레드** — 이 한 명령이 도는 동안 다른 모든 명령이 줄 서서 대기한다. 결과는 운영 정지. (String 시나리오 10의 `KEYS *`와 정확히 같은 부류: "한 방에 거대한 작업"을 단일 스레드에 던진 죄.)

→ 큐 내용 확인은 **`LRANGE key 0 9`**(앞 10개만)나 **`LLEN`**(개수만)으로. 전체 덤프는 절대 금물.

### (b) big key 자체 다루기

**왜 위험한가**:
- 단일 키라 **샤딩/분산 불가** — 클러스터에서 한 노드에만 부하 집중(hot key).
- `LRANGE 전체`, `DEL` 같은 단일 명령이 그 키를 건드리면 그 시간만큼 전 서버 블로킹.
- List 내부 인코딩은 원소가 많아지면 **listpack → quicklist**(연결된 listpack 노드들)로 바뀐다. 메모리는 효율적이지만 거대해지면 그 자체로 무겁다.

**대응**:
1. **근본 원인 — 컨슈머 스루풋 부족**. 워커 증설 + 배치 소비(시나리오 5)로 큐가 안 쌓이게.
2. **큐 분할(샤딩)**: `notify:queue:{0..N}` 로 쪼개 프로듀서는 라운드로빈/해시로 분산, 컨슈머는 `LMPOP`으로 여러 샤드를 한 번에 소비. hot key 해소.
3. **삭제는 `UNLINK`로**: 거대한 리스트를 `DEL`하면 그 큰 객체 메모리 회수를 동기로(블로킹) 한다. `UNLINK`는 키 참조만 끊고 실제 회수는 백그라운드로 → 블로킹 없음.

## 🪤 함정 한 줄

> **`LRANGE 0 -1`은 운영 Redis의 `KEYS *`다** — 단일 스레드를 한 방에 마비. 큰 리스트는 분할로 예방하고, 지울 땐 `UNLINK`.

</details>

# 🎬 시나리오 7. VIP 메일을 일반 메일보다 먼저 보내야 해요

## 📋 상황

PM 요구사항: "VIP 회원의 알림 메일은 일반 회원보다 **먼저** 발송돼야 한다. 단일 큐 `mail:queue`에 섞여 들어가면 일반 메일이 잔뜩 쌓였을 때 VIP가 한참 뒤로 밀린다."

지금 컨슈머는 `BRPOP mail:queue` 하나만 본다. 우선순위 개념이 없다.

## ❓ 질문

복잡한 우선순위 큐 미들웨어 없이, Redis List로 "VIP 먼저"를 어떻게 만드나?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

큐를 **우선순위별로 분리**하고, 블로킹 명령에 **여러 키를 우선순위 순서로** 넘긴다.

`BRPOP`(및 `BLPOP`/`BLMOVE` 계열)은 **여러 키를 받으며, 앞에 적은 키를 우선**한다. 비어있지 않은 첫 키에서 즉시 꺼내고, 전부 비어있을 때만 블로킹한다.

```java
// 프로듀서 — 등급에 따라 큐를 나눠 넣음
String queue = isVip ? "mail:queue:high" : "mail:queue:low";
redisTemplate.opsForList().leftPush(queue, email);
```

```java
// 컨슈머 — high 를 먼저 검사. high 에 있으면 무조건 그것부터.
//   둘 다 비면 5초 블로킹. (반환은 어느 키에서 나왔는지 + 값)
// redis-cli 기준:  BRPOP mail:queue:high mail:queue:low 5
//
// Spring Data Redis 에는 다중키 BRPOP 가 1급으로 노출돼 있지 않아
//   보통 RedisCallback 로 raw 명령을 쓴다:
List<byte[]> popped = redisTemplate.execute((RedisCallback<List<byte[]>>) conn ->
    conn.listCommands().bRPop(5,
        "mail:queue:high".getBytes(),
        "mail:queue:low".getBytes()));
// popped[0] = 꺼낸 키, popped[1] = 값
```

> 동작: `mail:queue:high`에 하나라도 있으면 **항상** 그것부터 소진된다. high가 완전히 비어야 low를 본다. = **엄격한 우선순위(strict priority)**.

### ⚠️ Starvation(기아) 주의

VIP가 끊임없이 들어오면 일반 메일은 **영원히 밀린다**(starvation). 실무 보완:
- "high N건 처리할 때마다 low 1건 강제 처리" 같은 **가중치/쿼터** 로직을 컨슈머에 둔다.
- 또는 등급이 진짜 점수(나이/지연시간 가중)면 **Sorted Set**으로 score 기반 우선순위 큐를 만드는 게 더 정밀하다(추후 ZSet 단계).

## 🪤 함정 한 줄

> **`BRPOP key1 key2 ...`는 앞 키 우선** — 그대로 우선순위 큐가 된다. 단, 고순위가 마르지 않으면 저순위는 **굶어 죽는다(starvation)**. 쿼터로 보완하라.

</details>

# 🎬 시나리오 8. RPOP while 루프가 CPU 100%를 먹어요

## 📋 상황

누군가 컨슈머를 이렇게 짰다. 큐가 비어있는 평상시에도 `queue-server`의 CPU 코어 하나가 **100%** 로 박혀 있다.

```java
while (running) {
    String msg = redisTemplate.opsForList().rightPop(MAIL_QUEUE);  // RPOP (논블로킹)
    if (msg != null) {
        process(msg);
    }
    // else: 그냥 다시 루프
}
```

큐가 텅 빈 새벽에도 이 루프는 쉬지 않고 돌며 Redis에 `RPOP`을 초당 수만 번 날린다.

## ❓ 질문

CPU와 Redis QPS를 둘 다 잡아먹는 이 패턴, 무엇이 문제이고 어떻게 고치나?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

이건 **busy-waiting(바쁜 대기)** 안티패턴이다. `RPOP`은 **논블로킹** — 큐가 비어 있으면 즉시 `null`을 반환한다. 그럼 루프는 `null`을 받자마자 다시 `RPOP`을 날리고… 이걸 **무한 반복**한다. 큐가 빈 동안 의미 없는 폴링으로:
- CPU 코어 하나를 100% 점유,
- Redis에 무의미한 `RPOP`을 폭격(QPS 낭비, 다른 명령 방해).

(`sleep(50)`을 끼우면 CPU는 잡히지만 이번엔 **지연(latency)** 이 생긴다 — 메시지가 들어와도 최대 50ms 늦게 잡힘. 폴링 간격은 항상 CPU vs 지연의 타협.)

## ✅ 올바른 패턴 — 블로킹 명령(BRPOP)

`BRPOP`은 **큐가 빌 때 Redis 서버 쪽에서 대기**한다. 메시지가 들어오면 그 즉시 깨워 반환한다. 폴링이 사라진다 — 이게 이 프로젝트의 원래 코드(`EmailMultiWorker.java:44`)가 옳게 한 부분이다.

```java
// ✅ 블로킹 pop — 비어있으면 서버에서 대기, 들어오면 즉시 반환
String msg = redisTemplate.opsForList()
        .rightPop(MAIL_QUEUE, Duration.ofSeconds(10));   // BRPOP mail:queue 10
if (msg != null) {
    process(msg);
}
// timeout(10초) 되면 null 반환 → 루프 한 바퀴 돌고 다시 BRPOP (Thread.interrupted 체크 기회)
```

- 큐가 비면: CPU도 안 쓰고 Redis QPS도 안 쓰며 조용히 대기.
- 메시지 도착: 폴링 지연 없이 **즉시** 깨어남.
- `timeout 0`이면 무한 대기지만, 보통 10초쯤 줘서 주기적으로 루프를 돌려 종료 플래그(`Thread.interrupted()`)를 점검할 틈을 준다.

## 🪤 함정 한 줄

> **`RPOP` while 루프 = busy-wait 안티패턴.** 빈 큐를 폴링하느라 CPU·Redis QPS를 태운다. 큐 소비는 항상 블로킹 `BRPOP`/`BLMOVE`로.

</details>

# 🎬 시나리오 9. 독성 메시지(poison message)가 무한 재시도로 큐를 막아요

## 📋 상황

시나리오 1의 신뢰성 큐(실패 시 큐로 되돌림)를 적용한 뒤, 새 장애가 생겼다.

어떤 메시지 하나가 **항상 실패**한다(예: 이메일 주소 포맷이 깨져서 발송 라이브러리가 매번 예외). 이 메시지는:
처리 → 실패 → 큐로 복귀 → 다시 처리 → 또 실패 → 복귀 … 를 **영원히** 반복한다. 그동안 워커 하나가 이 좀비에 묶여 다른 정상 메일 처리가 지연된다. 로그엔 같은 에러가 초당 수백 줄.

## ❓ 질문

이 "독성 메시지(poison message)"의 무한 재시도를 어떻게 끊나?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

핵심: **"무한 재시도"를 "유한 재시도 + 격리"로 바꾼다.** 재시도 횟수를 세고, 한계를 넘으면 정상 큐에서 빼내 **DLQ(Dead Letter Queue)** 로 보낸다.

### Step 1: 재시도 카운터 (메시지별)

메시지에 `messageId`를 박아두고(시나리오 1), 실패할 때마다 카운트.

```java
private static final int MAX_RETRY = 3;

private void processEmail(EmailMessage msg) {
    try {
        sendEmail(msg.getEmail());
        emailLogRepository.save(...);
        redisTemplate.opsForList().remove(PROCESSING, 1, msg.raw());   // ack
        redisTemplate.delete("retry:" + msg.getId());                  // 카운터 정리

    } catch (Exception e) {
        Long retries = redisTemplate.opsForValue().increment("retry:" + msg.getId());
        if (retries == 1) {
            redisTemplate.expire("retry:" + msg.getId(), Duration.ofHours(1));
        }

        if (retries >= MAX_RETRY) {
            // ☠️ 독성 메시지 격리 → DLQ 로 이동, 정상 큐 흐름에서 제거
            redisTemplate.opsForList().leftPush("mail:queue:dlq", msg.raw());
            redisTemplate.opsForList().remove(PROCESSING, 1, msg.raw());
            log.error("DLQ 격리: {} (재시도 {}회 초과)", msg.getId(), MAX_RETRY);
        } else {
            // 아직 여유 있으면 큐로 되돌려 재시도
            redisTemplate.opsForList().leftPush(MAIL_QUEUE, msg.raw());
            redisTemplate.opsForList().remove(PROCESSING, 1, msg.raw());
        }
    }
}
```

### Step 2: DLQ 운영

`mail:queue:dlq`에 쌓인 메시지는 **사람이 본다.** 알람을 걸고(예: `LLEN mail:queue:dlq > 0`), 원인을 고친 뒤 수동/배치로 재투입(`LMOVE dlq → mail:queue`)하거나 폐기한다. 핵심은 **독성 메시지가 정상 큐를 막지 않도록 빼내는 것.**

> 멱등성 dedup 키(시나리오 1 Q2)와 retry 카운터는 **다른 키**다. dedup은 "이미 성공 처리했나", retry는 "몇 번 실패했나". 둘 다 있어야 깔끔하다.

## 🪤 함정 한 줄

> **재시도엔 반드시 상한(max retry) + DLQ가 있어야 한다.** "실패 시 무조건 재큐잉"은 독성 메시지 하나가 큐와 워커를 영원히 점거하게 만든다.

</details>

# 🎬 시나리오 10. Pub/Sub로 큐를 만들었다가 메시지가 사라졌어요

## 📋 상황

다른 팀이 "환영 메일도 우리처럼 Pub/Sub로 바꾸자, 더 실시간이다"라고 제안했다. PoC로 `mail:queue` List를 걷어내고 Redis **Pub/Sub** 채널로 바꿨다.

```java
// 프로듀서
redisTemplate.convertAndSend("mail:channel", email);   // PUBLISH

// 컨슈머: mail:channel 구독(SUBSCRIBE)해서 받음
```

배포 후 며칠은 잘 됐는데, queue-server를 재배포(롤링)한 **그 1분 동안** 발행된 메일이 전부 사라졌다. 또, 컨슈머를 2대로 늘렸더니 같은 메일이 **양쪽 다** 발송됐다.

## ❓ 질문

Pub/Sub로 작업 큐를 만들면 왜 안 되나? List(또는 Stream)와 본질적으로 뭐가 다른가?

---

<details>
<summary>💭 펼치기</summary>

## 💡 답안

Redis **Pub/Sub는 "지금 듣고 있는 구독자에게만, 저장 없이" 뿌리는 fire-and-forget 방송**이다. 작업 큐의 요건과 정면으로 충돌한다.

### 차이 1: 보관(persistence) 없음 → 유실

- **Pub/Sub**: `PUBLISH` 시점에 구독자가 없으면 메시지는 **그냥 버려진다.** 어디에도 안 남는다. 컨슈머가 재배포로 잠깐 끊긴 사이 발행된 건 영원히 소멸. (TV 생방송 — 안 보고 있으면 끝.)
- **List**: `LPUSH`로 넣으면 컨슈머가 없어도 **큐에 쌓여 기다린다.** 컨슈머가 돌아오면 `BRPOP`으로 차곡차곡 가져간다. (녹화 — 나중에 본다.)

→ 재배포 중 유실의 원인이 바로 이것. List는 컨슈머 부재를 견딘다.

### 차이 2: 전달 모델 — fan-out vs work-queue

- **Pub/Sub**: 한 메시지를 **모든 구독자에게 복제 전달**(fan-out, 1:N). 컨슈머 2대면 둘 다 받는다 → 메일 2번 발송. 부하 분산이 **안 된다.**
- **List**: 한 메시지는 **한 컨슈머만** 가져간다(work-queue, 경쟁 소비). 컨슈머 2대면 자연스럽게 일이 **나눠진다.**

→ 컨슈머 증설로 중복 발송된 원인이 이것.

### 정리 — 무엇을 쓰나

| 용도 | 맞는 도구 |
|---|---|
| 작업을 **나눠서 한 번씩** 처리(워커 풀) | **List** (LPUSH/BRPOP) — 이 프로젝트 |
| 유실 안 되고 + ack/재처리/소비자그룹 필요 | **Stream** (XADD/XREADGROUP) |
| 모든 인스턴스에 **실시간 브로드캐스트**(캐시 무효화 신호 등), 유실 무방 | **Pub/Sub** |

→ 환영 메일은 "나눠서 한 번씩 + 유실 불가"이므로 **List가 정답**, 더 엄격해지면 Stream. Pub/Sub는 **작업 큐로 쓰면 안 된다.**

## 🪤 함정 한 줄

> **Pub/Sub은 저장 없는 fan-out 방송** — 구독자 없으면 유실, 구독자 여럿이면 전원 중복 수신. 작업 큐엔 **List(또는 Stream)** 를 써라.

</details>
