# Redis와 DB 저장 기준

> Redis 자료구조를 고를 때 먼저 물어볼 질문:
> **"이 데이터가 Redis에서 사라져도 서비스가 복구 가능한가?"**

## 한 줄 원칙

- **사라지면 안 되는 데이터**: DB가 원본(source of truth), Redis는 캐시·보조 인덱스·락·속도 계층.
- **사라져도 되는 데이터**: Redis만 사용 가능. 보통 TTL이 있거나, 다시 계산할 수 있거나, 현재 상태만 의미가 있다.
- **빠른 1차 관문**: Redis를 먼저 써도 되지만, 중요한 결과는 DB가 최종 판정해야 한다.

## 어디에 저장할까

| 데이터 성격 | 예시 | 저장 위치 |
|---|---|---|
| TTL이 본질인 임시값 | 인증 코드, 발송 rate limit, 로그인 실패 횟수 | Redis만 |
| 재생성 가능한 캐시 | 사용자 프로필 캐시, 콘서트 상세 캐시, 인기 목록 캐시 | DB 원본 + Redis 캐시 |
| 사용자 영구 의도 | 찜, 좋아요, 응모 이력, 권한/차단 | DB 원본 + Redis 보조 인덱스 |
| 금전/권리/재고 확정 | 결제, 티켓 발급, 좌석 점유 확정, 포인트 | DB 트랜잭션 중심, Redis는 락/카운터 보조 |
| 순서 있는 임시 작업 | 환영 메일 큐, 썸네일 생성 큐 | Redis 가능, 중요하면 Stream/브로커/DB outbox 고려 |
| 감사·추적 이력 | 당첨자, 알림 발송 결과, 결제 콜백 기록 | DB 저장 권장 |

## 쓰기 순서 기본값

영구 데이터는 보통 **DB 먼저, Redis 나중**이다.

```text
쓰기:
1. DB 트랜잭션 / UNIQUE 제약 / 상태 변경
2. 성공하면 Redis 캐시 삭제 또는 보조 인덱스 갱신
3. Redis 갱신 실패 시 재시도하거나, 다음 조회에서 DB 기준으로 재생성

읽기:
1. Redis 조회
2. 없으면 DB 조회
3. Redis에 TTL과 함께 채움
```

이유는 단순하다. **DB가 틀리면 원본이 깨진 것**이고, **Redis가 틀리면 캐시/인덱스를 다시 만들면 된다.**

## Redis 먼저 쓰는 예외

Redis를 먼저 쓰는 경우도 있다. 이때 Redis는 최종 저장소가 아니라 **빠른 선검사**다.

| 상황 | Redis 선사용 | 보완책 |
|---|---|---|
| 중복 클릭/응모 차단 | `SET NX EX`, `SADD` 반환값 | DB 저장 실패 시 롤백 또는 TTL/reconcile |
| 분산락 | `SET lock NX EX` | 락 안에서도 DB 제약/트랜잭션으로 최종 방어 |
| 재고 선차감 | Lua `DECR` 음수 방어 | 결제/발권 확정은 DB, 실패 시 보상 |
| rate limit | `INCR` + TTL | Redis 장애 시 fail-open/fail-closed 정책 결정 |

## 자료구조별 감각

| 자료구조 | Redis만 적합 | DB와 같이 쓰는 경우 |
|---|---|---|
| String | 인증 코드, rate limit, 임시 락, 짧은 멱등성 키 | 조회 캐시, 조회수 write-behind, 재고 보조 카운터 |
| List | 최근 본 목록, 최근 에러 로그, 가벼운 작업 큐 | 알림 피드 캐시, 발송 작업 결과/이력은 DB |
| Set | 오늘 본 항목, 임시 중복 방지, 온라인 사용자 | 찜/좋아요/권한/태그 인덱스, 응모/당첨 결과 |

## 장애 기준

- Redis 장애 시에도 **영구 데이터 조회/수정은 DB로 우회 가능**해야 한다.
- Redis에만 둔 데이터는 장애 시 사라질 수 있음을 기능 요구사항으로 받아들여야 한다.
- Redis를 캐시로 쓰면 **TTL, 무효화, 재생성 경로**가 반드시 있어야 한다.
- Redis를 큐로 쓰면 **처리 중 유실, 중복 처리, DLQ, 멱등성**을 같이 설계해야 한다.
- Redis를 락/카운터로 쓰더라도 결제·좌석·포인트 같은 최종 상태는 DB 제약으로 한 번 더 막는다.
