# Sorted Set 실무 — 실제 서비스에서 어떻게 쓰는가

> 요약에서 명령어를 정리했다면, 여기선 **"이 명령어들을 조합해 실제 기능을 어떻게 만드나"**가 주제.
> 무대는 이 프로젝트(콘서트 티켓)의 **선착순 대기열 / Rate Limit / 가중 추첨 / 실시간 랭킹.**

## 이 문서에서 다루는 7대 패턴

1. **리더보드 / 랭킹** — ZADD GT + ZREVRANGE + ZREVRANK
2. **선착순 대기열** — score=진입시각, ZRANK 순번, ZREMRANGEBYRANK 통과
3. **우선순위 큐** — score=우선순위, ZPOPMIN / BZPOPMIN
4. **Rate Limit (Sliding Window Log)** — score=요청시각, ZREMRANGEBYSCORE + ZCARD
5. **지연 큐 (delayed job)** — score=실행시각, ZRANGEBYSCORE -inf now
6. **가중 추첨** — score=누적 가중치 (Set SPOP의 균등 한계 해결)
7. **최근 목록 / 멤버 만료** — score=timestamp + ZREMRANGEBY*

## 먼저 잡을 기준 — ZSet은 원본인가, 보조 인덱스인가

ZSet은 랭킹·대기열의 "실시간 뷰"로 강력하지만, 영구 진실은 보통 DB다. 기준은 [Redis와 DB 저장 기준](../00-redis-db-저장기준.md)을 따른다.

| 패턴 | Redis만 가능? | DB 관계 |
|---|---|---|
| 실시간 랭킹/리더보드 | 가능 (휘발 시 재집계 가능하면) | 원본 점수는 DB, ZSet은 빠른 순위 조회 캐시 |
| 선착순 대기열 | 가능 | 진입/통과 이력 감사 필요하면 DB 로그 병행 |
| Rate Limit | 가능 | 휘발돼도 무방(짧은 윈도우), Redis 단독 OK |
| 지연 큐 | 신뢰성 필요하면 비추천 | 작업 원본은 DB, ZSet은 스케줄 인덱스. 진짜 신뢰성은 전용 큐 |
| 가중 추첨 | 후보 풀은 가능 | 당첨 결과·감사 로그는 DB |

> 외우기: **ZSet은 "정렬·순위·범위가 필요한 실시간 인덱스"에 강하고, 영구 진실/감사는 DB에 남긴다.**

# §1. 리더보드 / 랭킹 — ZADD GT + ZREVRANGE + ZREVRANK

## 문제

게임 점수, 실시간 차트, 좌석 인기 랭킹. "TOP N"과 "내 등수"를 빠르게.

## 패턴

```java
// 점수 기록 — GT로 "기록 경신할 때만" 갱신 (낮은 점수로 덮어쓰기 방지)
redisTemplate.opsForZSet().add("game:ranking", "player:42", 2100);
// 또는 누적: ZINCRBY game:ranking 300 player:42  (좋아요/조회수 랭킹)

// TOP 10 (높은 점수 순)
Set<ZSetOperations.TypedTuple<String>> top =
    redisTemplate.opsForZSet().reverseRangeWithScores("game:ranking", 0, 9);
// ZREVRANGE game:ranking 0 9 WITHSCORES

// 내 등수 (0-based → +1)
Long rank = redisTemplate.opsForZSet().reverseRank("game:ranking", "player:42");
long myRank = rank + 1;  // ZREVRANK
```

## 왜 ZSet인가

- **O(log N) 순위/범위.** 1000만 명이어도 "내 등수"와 "TOP 10"이 즉시. RDB `ORDER BY score LIMIT`은 데이터가 커지면 느려지고, "내 등수"는 `COUNT(*) WHERE score > 내점수`로 풀스캔에 가까워진다. ZSet은 항상 일정.
- **GT 옵션**으로 "최고 기록만 유지"가 명령 하나로.

> 🪤 **동점 처리**: 같은 score면 멤버 사전순이라, "먼저 달성한 사람이 위"가 안 된다. tie-break이 필요하면 **score에 시간 정보를 인코딩**(예: `score = points * 1e11 - timestamp`)하거나 별도 규칙. 면접 단골.

> ⚠ 랭킹 원본 점수는 DB에 두고 ZSet은 캐시로 보는 게 안전(휘발 시 재집계). 시즌 종료 등 영구 기록은 DB 스냅샷.

# §2. 선착순 대기열 — score=진입시각 (이 프로젝트 핵심)

## 문제

콘서트 티켓 오픈 시 수만 명 동시 진입. 공정한 **순번**을 매기고, 상위 N명씩 예매 페이지로 **통과**.

## 패턴

```java
// 진입: score = 진입 시각(ms) → 먼저 온 사람이 낮은 score = 앞 순번
long now = System.currentTimeMillis();
redisTemplate.opsForZSet().add("queue:concert:" + concertId, userId, now);
// ZADD queue:concert:1 {now} user:42

// 내 순번 (앞에 몇 명) — 0-based
Long rank = redisTemplate.opsForZSet().rank("queue:concert:" + concertId, userId);
// ZRANK (오름차순: 먼저 온 사람이 0)

// 상위 N명 통과 처리 (스케줄러가 주기적으로)
Set<String> passers = redisTemplate.opsForZSet()
    .range("queue:concert:" + concertId, 0, N - 1);          // ZRANGE 0 N-1
redisTemplate.opsForZSet()
    .removeRange("queue:concert:" + concertId, 0, N - 1);     // ZREMRANGEBYRANK 0 N-1
// 통과자는 별도 Set(passed)이나 토큰으로 예매 자격 부여
```

## 왜 ZSet인가

- **score=timestamp → 자동 선착순 정렬.** ZRANK로 "내 앞에 몇 명"이 O(log N).
- List 큐로도 FIFO는 되지만, **"내 순번 조회"**(중간 위치 검색)는 List가 O(N). ZSet은 ZRANK로 즉시.

> 🪤 **동시 진입(같은 ms)**: score가 같으면 멤버(userId) 사전순이 된다. 완벽한 진입 순서가 필요하면 score에 시퀀스를 더하거나 `INCR`로 전역 순번을 score로. 보통 ms 해상도면 충분.

> ⚠ 진입/통과 **이력 감사**가 필요하면 DB 로그를 병행. ZSet은 "현재 대기 상태"의 실시간 뷰.

> 이 프로젝트 로드맵 **Phase 3 Unit 5**가 정확히 이 패턴. 여기서 익히면 바로 구현 가능.

# §3. 우선순위 큐 — score=우선순위, ZPOPMIN

## 문제

작업을 우선순위 순으로 처리. List BRPOP은 FIFO만 되고 "중요한 것 먼저"가 안 된다.

## 패턴

```java
// 작업 추가 (score = 우선순위, 낮을수록 먼저)
ZADD jobs 1 "urgent-job"
ZADD jobs 5 "normal-job"
ZADD jobs 10 "low-job"

// 가장 우선(낮은 score) 작업 꺼내기
ZPOPMIN jobs          // → urgent-job
// 블로킹 소비 (비면 대기)
BZPOPMIN jobs 0       // List BRPOP의 ZSet판, 단 기준은 score 최소
```

## 왜 ZSet인가

- **ZPOPMIN = 우선순위 + 원자적 추출.** List는 삽입 순서(FIFO)만, ZSet은 score 순.
- **BZPOPMIN으로 블로킹 소비** — 워커가 "우선순위 높은 작업이 들어올 때까지" 대기.

> List 우선순위 큐(`BRPOP vip normal`)는 "큐 2~3개 단계"만 가능했다. ZSet은 **연속적·동적 우선순위**가 된다. 단 단순 FIFO면 List가 가볍다(ZSet은 오버킬).

# §4. Rate Limit — Sliding Window Log (score=요청시각)

## 문제

"사용자당 10초에 5회"처럼 **정확한 슬라이딩 윈도우** 요청 제한. (String 부록의 Fixed Window보다 정밀)

## 패턴

```
[윈도우=10초, 한도=5. score=요청 시각(ms)]
1. ZREMRANGEBYSCORE rl:user:1 -inf (now - 10000)   // 윈도우 밖(오래된) 제거
2. ZCARD rl:user:1                                  // 현재 윈도우 내 요청 수
3. if count < 5:
       ZADD rl:user:1 now {now}-{uuid}              // 허용 + 기록
       return ALLOW
   else:
       return DENY (429)
4. EXPIRE rl:user:1 10                               // 키 자체도 TTL
```

## ⚠ 반드시 Lua로 원자화

1~3단계를 따로 실행하면 **동시 요청 사이에 카운트가 어긋나** 한도를 초과 허용할 수 있다. **Lua 스크립트로 묶어 원자 실행**:

```lua
-- KEYS[1]=키, ARGV[1]=now, ARGV[2]=window, ARGV[3]=limit, ARGV[4]=member
redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', ARGV[1] - ARGV[2])
local count = redis.call('ZCARD', KEYS[1])
if count < tonumber(ARGV[3]) then
    redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4])
    redis.call('EXPIRE', KEYS[1], math.ceil(ARGV[2] / 1000))
    return 1   -- 허용
end
return 0       -- 거부
```

## Fixed Window와 비교

- **Fixed Window**(String INCR, 부록-rate-limit): 가볍지만 경계에서 2배 폭주 가능.
- **Sliding Window Log**(ZSet): 정확하지만 요청마다 멤버 저장 → 메모리↑. 한도가 작을 때 적합.

> 이 프로젝트 로드맵 **Phase 3 Unit 6**이 이 패턴. Lua 원자화는 **Phase 4 Unit 7**과 직결.

# §5. 지연 큐 (Delayed Job) — score=실행시각

## 문제

"30분 뒤 발송", "예약 결제 정각 실행"처럼 **미래 시각에 처리**할 작업. List 큐는 "지금 처리"만 된다(지연 불가).

## 패턴

```java
// 작업 등록: score = 실행할 시각(ms)
ZADD delayed:jobs {executeAt} "job:123"

// 워커(폴러): "지금 실행할 때가 된" 작업만 조회
long now = System.currentTimeMillis();
Set<String> due = redisTemplate.opsForZSet()
    .rangeByScore("delayed:jobs", 0, now);     // ZRANGEBYSCORE 0 now
// 꺼낸 작업 처리 후 제거 (원자성 위해 Lua 또는 ZPOPMIN 패턴)
```

## 왜 ZSet인가

- **score=실행시각 → "지금 이전" 작업만 ZRANGEBYSCORE로 즉시 조회.** 미래 작업은 자동으로 안 나옴.
- List는 시간 개념이 없어 지연 처리가 불가. ZSet의 score가 "스케줄"이 된다.

> 🪤 **신뢰성 한계**: 조회→처리→제거가 원자적이지 않으면 유실/중복. Lua로 "due 작업을 processing으로 원자 이동" 또는 ZPOPMIN + 멱등성. **진짜 내구성 있는 지연 큐는 전용 솔루션**(예: Redis Stream + 스케줄러, 혹은 메시지 브로커의 지연 기능)이 정석. → [도구 선택 가이드](../../MESSAGING_TOOL_GUIDE.md).

# §6. 가중 추첨 — score=누적 가중치

## 문제

Set의 `SPOP`은 **균등 추첨**만 됐다. "응모를 많이 한 사람이 더 유리한" **가중 추첨**이 필요.

## 패턴 (구간 매핑 방식)

```java
// 각 응모자의 가중치를 "누적 합"으로 score에 저장
// user:A 가중치 3, user:B 5, user:C 2  → 누적: A=3, B=8, C=10
ZADD raffle:weighted 3 "user:A" 8 "user:B" 10 "user:C"

// 추첨: 0 ~ 총합(10) 사이 랜덤 r 뽑고, score >= r 인 첫 멤버 선택
double r = random(0, 10);   // 예: 6
Set<String> picked = redisTemplate.opsForZSet()
    .rangeByScore("raffle:weighted", r, "+inf", 0, 1);  // ZRANGEBYSCORE r +inf LIMIT 0 1
// r=6 → B(8)가 첫 멤버 → 가중치 큰 B가 뽑힐 확률↑
```

## 왜 ZSet인가

- **score를 "누적 가중치 구간"으로 쓰면** 랜덤 값이 떨어지는 구간 = 가중 확률. ZRANGEBYSCORE LIMIT 1로 O(log N) 선택.
- Set SPOP은 균등만 → 가중은 ZSet이 정석. (Set 챕터 추첨의 "한 걸음 더"가 여기로 연결)

> ⚠ 추첨 결과·감사 로그는 DB에. 공정성 증빙이 필요하면 seed·후보 스냅샷 기록.

# §7. 최근 목록 / 멤버 만료 — score=timestamp

## 패턴 ① 최근 N개 (capped)

```java
// 최근 본 공연 (score=본 시각, 최근 20개만 유지)
ZADD recent:user:42 {now} "concert:100"
// 오래된 것 제거: 순위 하위(오래된) 잘라내기
ZREMRANGEBYRANK recent:user:42 0 -21   // 최근 20개(인덱스 -20~-1)만 남김
```

## 패턴 ② 멤버 만료 흉내

```java
// ZSet 멤버엔 개별 TTL이 없다 → score=만료시각으로 흉내
ZADD sessions {expireAt} "session:abc"
// 주기적으로(또는 조회 시) 만료된 것 제거
ZREMRANGEBYSCORE sessions -inf {now}
```

> 💡 "멤버별 TTL"이 필요한 모든 곳(기간제 차단, 임시 세션, 만료되는 점수)에 **score=만료시각 + 주기적 ZREMRANGEBYSCORE** 관용구. Set 시나리오 3(기간제 차단)의 해법이 바로 이것.

# §8. 프로젝트 적용 미션 (선택)

이 프로젝트에 ZSet을 직접 이식하는 미션 (로드맵 Phase 3와 직결):

1. **선착순 대기열** — `POST /api/queue/enter`(`ZADD score=now`) + `GET /api/queue/rank`(`ZRANK`) + 스케줄러 통과(`ZRANGE`+`ZREMRANGEBYRANK`). (Unit 5)
2. **Rate Limit 인터셉터** — 좌석 예매 API에 Sliding Window Log(Lua 원자화). (Unit 6)
3. **실시간 좌석 인기 랭킹** — 좌석/공연 조회 시 `ZINCRBY`, `ZREVRANGE`로 인기 TOP.
4. **가중 추첨 이벤트** — 응모 가중치 score 누적 + 구간 매핑 추첨.
