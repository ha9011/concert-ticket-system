## 시나리오 1 (보스급 🔥) — "콘서트 오픈 순간 대기열이 터졌어요"

**상황**

인기 콘서트 티켓 오픈 10:00:00. 그 순간 **5만 명이 동시 진입**한다. 대기열을 ZSet(`queue:concert:1`, score=진입 시각 ms)으로 구현했고, 사용자는 `ZRANK`로 자기 순번을 1초마다 폴링한다. 스케줄러가 1초마다 상위 100명을 통과시킨다. 그런데:
- 순번 조회가 느려지고, 가끔 같은 사람이 두 번 통과되거나, 통과 인원이 100명을 넘는다.

**질문**: 무엇이 문제이고 어떻게 풀겠는가?

<details>
<summary>펼쳐서 답 보기</summary>

### 원인

1. **순번 폴링 폭주** — 5만 명 × 1초마다 `ZRANK` = 초당 5만 read. ZRANK 자체는 O(log N)이지만, 거대한 동시 폴링이 단일 스레드에 몰린다.
2. **통과 처리의 비원자성** — "상위 100명 조회(`ZRANGE 0 99`) → 제거(`ZREMRANGEBYRANK 0 99`)"가 **두 명령**이라, 그 사이 새 진입/다른 스케줄러 실행이 끼면 **중복 통과**나 **100명 초과**가 발생.
3. **동시 진입 같은 ms** — score가 같으면 멤버 사전순 → 진입 순서가 userId 알파벳순으로 왜곡.

### 해결

1. **통과 처리를 원자화** — `ZRANGE 0 99` + `ZREMRANGEBYRANK 0 99`를 **Lua 스크립트 한 방**으로. "조회와 동시에 제거"가 원자적이면 중복/초과 없음. 또는 `ZPOPMIN 100`(7.0+, 최소 score 100개를 원자적으로 꺼냄)으로 한 번에.
2. **순번 폴링 부하 완화** — (a) 폴링 주기를 늘리고(1초→3~5초), (b) 순번을 **근사치로** 보여줘도 됨(`ZRANK` 대신 캐시된 구간), (c) **WebSocket/SSE 푸시**로 폴링 자체를 제거, (d) 읽기를 **replica로 분산**.
3. **진입 순서 정밀화** — score를 단순 ms 대신 **전역 시퀀스**(`INCR seq`를 score로)나 `ms * 1e6 + seq`로 → 동점 제거.
4. **통과자 자격 관리** — 통과한 사용자는 별도 Set/토큰(`passed:concert:1` 또는 단기 TTL 토큰)으로 예매 자격 부여. 대기열에서 빠진 것만으로 끝내지 않음.

### 면접관 후속 질문 (보스전)

**Q1. "`ZPOPMIN 100`과 `ZRANGE+ZREMRANGEBYRANK` Lua, 둘 중 뭘?"**
> 통과자 목록을 알아야 하면(자격 부여) 둘 다 멤버를 돌려준다. `ZPOPMIN 100`은 단일 명령이라 가장 간단·원자적. 단 "score 최소 100개"라 대기열 의미(먼저 온 순)와 일치. Lua는 더 복잡한 로직(통과 동시에 다른 키 갱신)이 필요할 때.

**Q2. "5만 명 순번을 실시간으로 정확히 보여줘야 하나?"**
> 대부분 아니다. "약 1,200번째"처럼 **근사·구간 표시**면 충분하고 부하가 급감한다. 정확한 실시간 순위는 비용 대비 가치가 낮다. UX는 "예상 대기시간"이 더 중요.

**Q3. "Redis가 죽으면 대기열이 통째로 날아가는데?"**
> ZSet은 휘발성. (a) AOF/replica로 내구성 강화, (b) 진입 로그를 DB/Kafka에 병행 적재해 재구성 가능하게, (c) 대기열은 "재진입 가능"하게 설계(치명적이지 않게). 완벽한 내구성이 필요하면 ZSet 단독은 부족 → 영구 저장 병행. → [00-redis-db-저장기준](../00-redis-db-저장기준.md).

**Q4. "ZRANK가 O(log N)인데 왜 느려지나?"**
> 단일 명령은 빠르지만 **초당 수만 건의 동시 호출**이 단일 스레드 큐에 쌓이면 지연. 문제는 명령 복잡도가 아니라 **호출 빈도**. → 폴링 제거(푸시)·주기 완화·replica 분산.

### 한 줄 교훈
> **대기열 통과는 "조회+제거"를 원자화(Lua/ZPOPMIN)하고, 순번 폴링은 푸시·근사·replica로 부하를 줄인다. ZSet은 휘발성이라 내구성이 필요하면 DB/로그 병행.**

</details>

## 시나리오 2 (라이트) — "리더보드에서 점수가 거꾸로 갱신돼요"

**상황**

게임 점수를 `ZADD board {score} {user}`로 저장하는데, 네트워크 재전송으로 **예전(낮은) 점수가 나중에 도착**해 최고 기록을 덮어썼다.

**질문**: 어떻게 막나?

<details>
<summary>펼쳐서 답 보기</summary>

- **`ZADD board GT {score} {user}`** — GT(greater than)는 **새 score가 기존보다 클 때만** 갱신. 낮은 점수가 와도 무시.
- 누적 점수라면 `ZINCRBY`(더하기)라 순서 무관. "최고 기록"이면 GT.

> 💡 **한 걸음 더**: GT/LT는 멱등성에도 유용 — 같은 최고 점수가 여러 번 와도 결과 동일. 단 "정확히 이 값으로 세팅"이 필요하면 GT 말고 일반 ZADD. 도메인이 "최고치 유지"인지 "현재값 동기화"인지 구분.

</details>

## 시나리오 3 (라이트) — "동점자 순위가 이상해요"

**상황**

리더보드에서 같은 점수(2000점)인 두 명의 등수가 "먼저 달성한 사람"이 아니라 이름 순으로 매겨진다.

**질문**: 왜? 어떻게 의도대로?

<details>
<summary>펼쳐서 답 보기</summary>

- **ZSet은 같은 score면 멤버 이름 사전순(lexicographical) 정렬.** 시간 개념이 없다.
- 해결: **score에 시간 정보를 인코딩.** 예) `score = points * 1e11 - timestamp_ms` → 점수 같으면 먼저 달성(작은 timestamp)이 더 큰 score → 위로.
- 또는 점수와 시간을 분리 관리하고 tie-break을 애플리케이션에서.

> 💡 **한 걸음 더**: score는 double(64비트)이라 **정밀도 한계**(약 2^53까지 정수 안전). `points*1e11`이 이 범위를 넘으면 정밀도 손실로 tie-break이 깨진다. 점수 범위와 timestamp 자릿수를 계산해 인코딩 폭을 잡아야 한다. 안 맞으면 정수 score를 문자열로 다루는 별도 설계.

</details>

## 시나리오 4 (라이트) — "Rate Limit가 가끔 한도를 넘겨요"

**상황**

ZSet Sliding Window로 "10초 5회"를 구현했는데, 동시 요청이 몰리면 가끔 6~7개가 통과한다. 코드는 `ZREMRANGEBYSCORE` → `ZCARD` → (5 미만이면) `ZADD` 순.

**질문**: 원인과 해결?

<details>
<summary>펼쳐서 답 보기</summary>

- **세 명령이 원자적이 아님.** 동시 요청 A,B가 둘 다 `ZCARD`에서 "4"를 읽고, 둘 다 5 미만이라 판단해 둘 다 `ZADD` → 6개.
- **Lua 스크립트로 묶어 원자 실행.** Redis는 Lua를 단일 명령처럼 처리하므로 중간 끼어듦이 없다.

```lua
redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', ARGV[1]-ARGV[2])
if redis.call('ZCARD', KEYS[1]) < tonumber(ARGV[3]) then
    redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4]); return 1
end
return 0
```

> 💡 **한 걸음 더**: "확인 후 처리(check-then-act)"는 Redis에서 거의 항상 Lua가 답(String 챕터 분산락과 같은 원리). MULTI/EXEC는 조건 분기가 안 되니 Lua. 멤버는 시각이 같을 수 있어 `{now}-{uuid}`로 유일하게.

</details>

## 시나리오 5 (라이트) — "지연 작업이 실행이 안 되거나 두 번 돼요"

**상황**

지연 큐를 `ZADD delayed {executeAt} {job}` + 폴러가 `ZRANGEBYSCORE 0 now`로 due 작업 조회 후 처리 → `ZREM`. 워커가 여러 대인데, 같은 작업이 두 번 실행되거나 처리 중 워커가 죽으면 유실된다.

**질문**: 어떻게 개선?

<details>
<summary>펼쳐서 답 보기</summary>

- **조회→처리→제거가 비원자 + 멀티 워커** → 두 워커가 같은 due 작업을 동시에 집음(중복), 처리 중 사망 시 유실.
- 개선:
  - **원자적 클레임**: Lua로 "due 작업을 꺼내며 동시에 `processing` ZSet으로 이동"(score=클레임 시각). 한 워커만 가져감.
  - **처리 완료 시 `processing`에서 제거**, 미완료(타임아웃)는 reaper가 되돌림 → **List Reliable Queue와 같은 구조**.
  - **멱등성**: 작업 ID로 중복 실행 방지(dedup).

> 💡 **한 걸음 더**: 이쯤이면 ZSet 손코딩으로 "신뢰성 큐 + 스케줄러"를 재발명하는 것. 진짜 내구성이 필요하면 **전용 솔루션**(Redis Stream + 스케줄러, 또는 메시지 브로커 지연 큐)이 정석. ZSet 지연 큐는 "유실 약간 허용 + 가벼움"에 적합. → [도구 선택 가이드](../../MESSAGING_TOOL_GUIDE.md).

</details>

## 시나리오 6 (라이트) — "ZRANGE로 전체를 가져왔더니 멈칫해요"

**상황**

관리자 페이지에서 대기열 전체를 `ZRANGE queue 0 -1 WITHSCORES`로 가져온다. 대기자 50만 명일 때 Redis가 잠깐 멈춘다.

**질문**: 문제와 해결?

<details>
<summary>펼쳐서 답 보기</summary>

- **`ZRANGE 0 -1`은 O(N)** — 50만 멤버+score를 한 번에 직렬화·전송. 단일 스레드 블로킹. (Set의 SMEMBERS, List의 LRANGE 0 -1과 같은 함정)
- 해결:
  - **페이지네이션**: `ZRANGE k 0 99`, 다음 `100 199` ... 또는 `ZRANGEBYSCORE ... LIMIT offset count`.
  - 대개 전체가 아니라 **상위 N(`ZRANGE 0 N`)·개수(`ZCARD`)·구간(`ZCOUNT`)** 이면 충분.

> 💡 **한 걸음 더**: 큰 ZSet 삭제도 `DEL`은 블로킹 → `UNLINK`. 모니터링은 `--bigkeys`. 대기열이 수십만이면 키 분할이나 애초에 "통과로 빠르게 비워지는" 설계가 중요.

</details>

## 시나리오 7 (라이트) — "기간제 멤버십이 안 사라져요"

**상황**

VIP 멤버를 ZSet에 넣고 "30일 후 만료"시키려는데, ZSet 멤버에 TTL을 못 건다.

**질문**: 어떻게 만료를 흉내 내나?

<details>
<summary>펼쳐서 답 보기</summary>

- **ZSet 멤버엔 개별 TTL 없음** (TTL은 키 단위).
- **score=만료 시각(ms)** 으로 저장 → 주기적으로(또는 조회 시) `ZREMRANGEBYSCORE vip -inf {now}`로 만료된 멤버 제거.
- 조회할 때도 "현재 유효한 VIP"는 `ZRANGEBYSCORE vip {now} +inf`(아직 안 만료된 것).

> 💡 **한 걸음 더**: 이 "score=만료시각" 패턴은 기간제 차단(Set 시나리오 3), 임시 세션, 분산 세마포어(만료되는 점유) 등에 두루 쓰인다. 정리 주기를 짧게 하면 정확하지만 부하↑, 길면 만료된 게 잠깐 남음 → 조회 시 score 필터를 같이 걸어 보정.

</details>

## 시나리오 8 (라이트) — "두 랭킹을 합치고 싶어요"

**상황**

"이번 주 점수"와 "지난 주 점수" ZSet을 합쳐 "최근 2주 통합 랭킹"을 만들고 싶다. 그런데 단순히 합치니 같은 유저 점수가 더해져 의도와 다르거나, 최신 주에 가중치를 주고 싶다.

**질문**: 어떻게?

<details>
<summary>펼쳐서 답 보기</summary>

- **`ZUNIONSTORE total 2 week:this week:last`** — 같은 유저 score는 **기본 SUM(합산)**. "2주 누적"이면 이게 맞다.
- **최신 주 가중**: `ZUNIONSTORE total 2 week:this week:last WEIGHTS 2 1` → 이번 주 ×2.
- **"최고 주 점수만"**: `AGGREGATE MAX` → 두 주 중 큰 점수.

> 💡 **한 걸음 더**: numkeys(2)를 빼먹으면 에러. 결과가 크면 STORE 연산 자체가 무거우니(O(N)) 배치/오프피크에. 자주 쓰면 결과 캐싱 + TTL. `ZUNION`(STORE 없는 6.2+)으로 저장 없이 바로 받을 수도 있지만 큰 결과는 전송 비용.

</details>

## 시나리오 9 (라이트) — "가중 추첨을 만들고 싶어요"

**상황**

Set으로 `SPOP` 추첨을 했는데 모두 같은 확률이다. "응모 많이 한 사람이 더 유리한" 가중 추첨이 필요하다.

**질문**: ZSet으로 어떻게?

<details>
<summary>펼쳐서 답 보기</summary>

- **score = 누적 가중치**로 저장: 가중치 A=3,B=5,C=2 → 누적 A=3,B=8,C=10.
- 추첨: `0~총합(10)` 랜덤 r → `ZRANGEBYSCORE raffle r +inf LIMIT 0 1`로 r 이상 첫 멤버 선택. 가중치 큰 사람의 구간이 넓어 더 자주 뽑힘.

> 💡 **한 걸음 더**: 뽑은 뒤 제거하고 누적을 다시 계산하면 비용이 크다. 소규모면 매번 재계산, 대규모·반복이면 별도 알고리즘(Fenwick tree 등)이나 미리 계산. 추첨 결과·seed는 DB 감사 로그. (Set 추첨의 "한 걸음 더"가 여기로 연결)

</details>

## 시나리오 10 (라이트) — "score가 큰 정수인데 값이 틀어져요"

**상황**

고유 ID(예: 나노초 타임스탬프, 19자리)를 score로 넣었는데, 조회하면 끝자리가 0으로 바뀌거나 정렬이 미묘하게 틀린다.

**질문**: 원인과 대안?

<details>
<summary>펼쳐서 답 보기</summary>

- **ZSet score는 64비트 double(부동소수점).** 정수는 **약 2^53(≈9×10^15, 16자리)까지만 정확.** 그보다 큰 정수(19자리 나노초)는 **정밀도 손실**로 끝자리가 뭉개진다.
- 대안:
  - score 해상도를 낮춤(나노초→밀리초, 자릿수 축소).
  - 큰 ID를 score로 쓰지 말고 **멤버에** 두고, score는 정렬 기준(밀리초 등)만.
  - 사전순 정렬이면 ZRANGEBYLEX(고정폭 zero-padding 문자열).

> 💡 **한 걸음 더**: tie-break으로 `score = points*1e11 - timestamp` 같은 인코딩을 할 때도 이 2^53 한계를 항상 계산해야 한다(시나리오 3과 연결). "ZSet score=double"은 면접 단골 함정.

</details>

> 1. **시간을 score로 쓰면** 대기열·Rate Limit·지연 큐·만료가 한 자료구조로 풀린다.
> 2. **"확인 후 처리"(통과·Rate Limit·지연 클레임)는 Lua로 원자화** — 비원자면 중복/초과/유실.
> 3. **score=double의 정밀도 한계, 동점=사전순, 큰 ZRANGE 블로킹, 멤버 개별 TTL 없음** — ZSet의 4대 함정. 그리고 휘발성이라 내구성은 DB/로그 병행.
