> 영역: A 기본구조 · B 명령어 비교 · C 랭킹/리더보드 · D 대기열/RateLimit · E 집합연산 · F 인코딩/운영 · G 실전

## A. 기본 구조

### Q1. Sorted Set을 한 문장으로 정의하라.
<details><summary>답</summary>

**멤버마다 score(점수)가 붙어, score 순으로 자동 정렬되는 집합.** 멤버는 유일(Set처럼 중복 없음), score는 64비트 double. 순위·범위·top-N이 O(log N).
</details>

### Q2. Set과 ZSet의 차이는?
<details><summary>답</summary>

Set은 정렬 없음(순서 무의미), ZSet은 **score로 정렬**돼 순위(ZRANK)·범위(ZRANGEBYSCORE)·top-N(ZREVRANGE)이 가능. ZSet = "Set + score 정렬".
</details>

### Q3. ZSet 내부 자료구조는?
<details><summary>답</summary>

**skiplist(정렬된 순위/범위 조회) + 해시테이블(멤버→score O(1) 조회)** 의 조합. (작을 땐 listpack)
</details>

### Q4. 🪤 같은 멤버를 다른 score로 ZADD 하면?
<details><summary>답</summary>

멤버는 유일하므로 **score가 갱신(덮어씀)**. 반환값 기본은 "새로 추가된 멤버 수"(갱신은 0). `CH` 옵션 주면 변경된 수.
</details>

### Q5. 멤버가 모두 제거되면 키는?
<details><summary>답</summary>

**키 자동 삭제** (List/Set/Hash/ZSet 공통). "빈 ZSet" 상태 없음.
</details>

## B. 명령어 비교

### Q6. ZRANK와 ZREVRANK 차이는?
<details><summary>답</summary>

`ZRANK`=score **오름차순** 순위(작은 게 0위), `ZREVRANK`=**내림차순**(큰 게 0위). 리더보드 등수=`ZREVRANK+1`, 대기열 순번=`ZRANK`.
</details>

### Q7. 🪤 ZADD의 NX / XX / GT / LT는?
<details><summary>답</summary>

- `NX`: 멤버 없을 때만 추가(기존 안 건드림)
- `XX`: 있을 때만 갱신(신규 추가 안 함)
- `GT`: 새 score가 더 **클 때만** 갱신(최고 기록 유지)
- `LT`: 더 **작을 때만** 갱신
</details>

### Q8. ZRANGE로 조회하는 3가지 축은?
<details><summary>답</summary>

① **인덱스(rank)**: `ZRANGE k start stop` / ② **score**: `BYSCORE`(ZRANGEBYSCORE) / ③ **사전순(lex)**: `BYLEX`(ZRANGEBYLEX, score 동일 전제). 6.2+ ZRANGE 하나로 통합(+REV/LIMIT).
</details>

### Q9. 🪤 `ZRANGEBYSCORE k (20 40` 의 `(`는?
<details><summary>답</summary>

**경계 배타(exclusive)** — `(20`=20 초과(20 제외). 기본은 포함. `-inf`/`+inf`로 무한대. 시간 윈도우 "이상/초과" 구분에 중요.
</details>

### Q10. ZPOPMIN과 ZPOPMAX는?
<details><summary>답</summary>

`ZPOPMIN`=최소 score 멤버 꺼내며 제거(우선순위 큐 소비), `ZPOPMAX`=최대 score. `BZPOPMIN`은 블로킹 버전.
</details>

### Q11. 🪤 ZREMRANGEBYRANK와 ZREMRANGEBYSCORE 차이는?
<details><summary>답</summary>

`BYRANK`=순위 구간 제거("상위 N만 유지" capped). `BYSCORE`=score 구간 제거("윈도우 밖/만료 정리"). 전자는 List LTRIM, 후자는 Rate Limit/지연 큐 정리에.
</details>

## C. 랭킹 / 리더보드

### Q12. 1000만 명 리더보드에서 "내 등수"를 어떻게 빠르게?
<details><summary>답</summary>

`ZREVRANK`. **O(log N)** 으로 즉시. RDB는 `COUNT(*) WHERE score>내점수`로 풀스캔에 가까워 느림.
</details>

### Q13. "최고 점수만 유지"하려면?
<details><summary>답</summary>

`ZADD board GT {score} {user}`. 새 점수가 기존보다 클 때만 갱신 → 낮은 점수로 덮어쓰기 방지. 누적이면 `ZINCRBY`.
</details>

### Q14. 🪤 동점(같은 score) 처리는?
<details><summary>답</summary>

같은 score면 **멤버 사전순(lexicographical)** 정렬. "먼저 달성 우선"이 필요하면 **score에 시간 인코딩**(예: `points*1e11 - timestamp`). 단 double 정밀도(2^53) 한계 주의.
</details>

### Q15. TOP 10과 각자 점수를 한 번에?
<details><summary>답</summary>

`ZREVRANGE board 0 9 WITHSCORES`. (또는 `ZRANGE board 0 9 REV WITHSCORES`)
</details>

## D. 대기열 / Rate Limit

### Q16. 선착순 대기열을 ZSet으로 어떻게?
<details><summary>답</summary>

score=진입 시각(ms) → `ZADD`. 내 순번=`ZRANK`(먼저 온 사람=낮은 score=앞). 통과=`ZRANGE 0 N-1` + `ZREMRANGEBYRANK 0 N-1`.
</details>

### Q17. 🪤 대기열 "통과 처리"의 동시성 문제와 해결은?
<details><summary>답</summary>

`ZRANGE`(조회)+`ZREMRANGEBYRANK`(제거)가 **두 명령**이라 그 사이 끼어들면 중복 통과/초과. **Lua로 원자화** 또는 `ZPOPMIN N`(원자적으로 최소 N개 추출).
</details>

### Q18. Rate Limit Sliding Window Log를 ZSet으로?
<details><summary>답</summary>

score=요청 시각. ① `ZREMRANGEBYSCORE -inf (now-window)`(오래된 제거) ② `ZCARD`(윈도우 내 수) ③ 한도 미만이면 `ZADD`. **Lua로 원자화 필수.**
</details>

### Q19. Fixed Window(String INCR)와 Sliding Window(ZSet) 차이는?
<details><summary>답</summary>

Fixed=가볍지만 경계에서 2배 폭주 가능. Sliding Log(ZSet)=정확하지만 요청마다 멤버 저장→메모리↑. 한도가 작을 때 ZSet 적합.
</details>

### Q20. 지연 큐(미래 시각 실행)를 ZSet으로?
<details><summary>답</summary>

score=실행 시각. 폴러가 `ZRANGEBYSCORE 0 now`로 "지금 실행할 것"만 조회. 미래 작업은 자동으로 안 나옴. (제거는 원자화/멱등성 필요)
</details>

### Q21. 🪤 ZSet 멤버에 개별 TTL을 걸 수 있나?
<details><summary>답</summary>

**불가**(TTL은 키 단위). 멤버 만료는 **score=만료시각 + 주기적 `ZREMRANGEBYSCORE -inf now`** 로 흉내. 조회 시 score 필터 병행.
</details>

## E. 집합 연산

### Q22. 🪤 ZUNIONSTORE의 두 가지 주의점은?
<details><summary>답</summary>

① **numkeys 먼저**(`ZUNIONSTORE dest 2 a b`) ② 같은 멤버 **score는 기본 SUM(합산)**. 의도와 다르면 AGGREGATE로 조정.
</details>

### Q23. WEIGHTS와 AGGREGATE는?
<details><summary>답</summary>

`WEIGHTS`=각 집합 score에 가중치(`WEIGHTS 2 1`=첫째 ×2). `AGGREGATE SUM(기본)/MIN/MAX`=합산 방식. "최신 주 2배"·"최고 점수만(MAX)" 등.
</details>

### Q24. 교집합 개수만 효율적으로?
<details><summary>답</summary>

`ZINTERCARD numkeys k... [LIMIT n]` (7.0+). 멤버 전체 안 만들고 개수만, LIMIT으로 조기 종료.
</details>

### Q25. 가중 추첨을 ZSet으로 어떻게?
<details><summary>답</summary>

score=누적 가중치 → `0~총합` 랜덤 r → `ZRANGEBYSCORE r +inf LIMIT 0 1`. 가중치 큰 사람 구간이 넓어 더 자주 뽑힘. (Set SPOP은 균등만)
</details>

## F. 인코딩 / 운영

### Q26. ZSet 인코딩 2종과 전환 경계는?
<details><summary>답</summary>

작으면 **listpack**, 커지면 **skiplist(+해시)**. 경계: `zset-max-listpack-entries`(기본 128), `zset-max-listpack-value`(기본 64바이트).
</details>

### Q27. 🪤 큰 `ZRANGE 0 -1`이 위험한 이유는?
<details><summary>답</summary>

O(N)으로 전 멤버+score를 한 번에 직렬화·전송 → **단일 스레드 블로킹**(SMEMBERS/LRANGE 0 -1과 같은 함정). LIMIT 페이지네이션으로.
</details>

### Q28. 🪤 score가 큰 정수일 때 문제는?
<details><summary>답</summary>

score는 **double** → 정수는 **약 2^53(16자리)까지만 정확**. 19자리 나노초 등은 정밀도 손실로 끝자리 뭉개짐. 해상도 낮추거나 멤버에 ID 저장.
</details>

### Q29. big key ZSet 삭제 시 주의는?
<details><summary>답</summary>

`DEL`은 동기 블로킹 → **`UNLINK`로 비동기**. 모니터링 `--bigkeys`.
</details>

### Q30. ZRANGEBYLEX는 언제 쓰나?
<details><summary>답</summary>

**모든 멤버 score가 같을 때**의 사전순 범위 조회(자동완성·사전 인덱스). score가 다르면 결과 미정의.
</details>

## G. 실전

### Q31. ZSet vs List 우선순위 큐는?
<details><summary>답</summary>

List `BRPOP`은 FIFO만(또는 큐 2~3개 단계 우선순위). ZSet은 score로 **연속·동적 우선순위**, `ZPOPMIN`/`BZPOPMIN`으로 "가장 우선" 소비. 단 단순 FIFO면 List가 가벼움.
</details>

### Q32. 🪤 ZSet 대기열/랭킹은 Redis가 죽으면? 내구성 대책은?
<details><summary>답</summary>

ZSet은 휘발성 → 통째로 소실 가능. AOF/replica로 강화하거나, 진입/점수 원본을 **DB/Kafka 병행 적재**해 재구성 가능하게. 완벽한 내구성 필요하면 ZSet 단독 부족 → 영구 저장 병행. (진실은 DB, ZSet은 실시간 인덱스)
</details>

### Q33. 리더보드를 RDB로 안 하고 ZSet으로 하는 이유는?
<details><summary>답</summary>

RDB `ORDER BY score LIMIT`은 데이터 커지면 느리고, "내 등수"는 풀스캔에 가까움. ZSet은 순위/범위/top-N이 **항상 O(log N)** 으로 일정. 단 영구 기록은 DB, ZSet은 빠른 조회 캐시.
</details>

## 마무리 — 한 줄 정리들

- **ZADD GT** = 최고 기록만, **ZINCRBY** = 누적, **같은 멤버 = score 갱신**.
- **ZRANK(오름차순)=대기열 순번 / ZREVRANK(내림차순)=리더보드 등수(+1)**.
- **ZRANGE 3축**: 인덱스 / BYSCORE / BYLEX(score 동일 전제). `(`=배타, `-inf/+inf`.
- **시간을 score로** → 대기열·Rate Limit·지연 큐·만료가 한 자료구조로.
- **"확인 후 처리"는 Lua 원자화** (통과·Rate Limit·지연 클레임).
- **4대 함정**: score=double 정밀도(2^53), 동점=사전순, 큰 ZRANGE 블로킹, 멤버 개별 TTL 없음.
- **집합연산**: numkeys 필수 + score SUM 기본 + WEIGHTS/AGGREGATE.
- **휘발성** → 내구성·감사는 DB/로그 병행.

> ZSet을 완주하면 → 마지막 자료구조 **Hash**(필드-값 묶음, 객체 저장). 그 뒤 로드맵 **Phase 1~4 구현**(Cache-Aside·분산락·대기열·Rate Limit·Pub/Sub)으로. ZSet의 대기열·Rate Limit이 Phase 3에서 바로 코드가 된다.
